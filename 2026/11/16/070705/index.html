第1幕: 泥と目盛り

三日で三回直した。三回とも、出して、苦情が来て、戻した。深夜に入った翌朝便の注文が、締め切りの前なのに「締め切りを過ぎました」で断られる。直したはずの不具合の苦情が、いま四件目として届いた。

港から乾ドックへ下りる坂の途中で、上着のポケットが二度震えた。両手に弁当の箱を三段ずつ重ねて提げていたから、すぐには見られなかった。道の手すりに片方の箱を預け、空いた手でスマートフォンを出す。問い合わせ窓口から回ってきた転送が一件。その下に、東京にいる上司から Slack が一行。

――例の翌朝便、どんな感じ？

責める調子ではない。だからよけいに堪えた。返事は打たずにポケットへ戻した。

風が出ていた。十一月の半ばに入って、港の風は急に北から吹くようになる。坂の下から、錆と潮の混じった匂いが上がってくる。高圧洗浄機の唸りと、何かを硬い物で削る音。乾ドック――船を水の外に出して底まで直せるように、海水を抜いた船渠――の底で、誰かが貝殻を削っている。

今日の僕は、祖母の代わりに弁当を届けに来ただけだ。食堂「とみや」は、この引き揚げ会社の作業員の昼の弁当を毎日届けている。いつもは祖母の富が坂を下りてくるのだが、今朝は腰が痛いと言って、帳場の奥の椅子から立たなかった。

二年前、祖母が腰を悪くしたのをきっかけに、僕は風待浦へ戻ってきた。都市部のスーパーが運営しているネットスーパーの、注文の受付と配達枠のバックエンドを、食堂の奥の席からリモートで書いている。チームは東京にいて、港町から入っているのは僕一人だ。

弁当を届けて、戻って、仕事をする。それだけのはずだった。

ドックの底へ下りる鉄の階段は、泥で滑った。底には、船を載せる台――盤木という、木と鋼でできた枕のような台――が一列に並び、その上に、錆と泥の塊のような船体が載っている。

盤木の脇で、作業着の人が船体に巻尺を当てていた。上半身を脱いで腰で結んだ作業つなぎ、首にタオル。束ねた黒髪。両手から肘の上まで泥で汚れていて、小指だけが乾いている。片方の手で巻尺の端を船底の下の端に押さえ、もう片方の手で巻尺の本体を上へ伸ばしていた。

食堂に弁当を取りに来る人だ、と分かった。言葉を交わしたことはほとんどない。伝票の受領欄の署名で、汐見という名字だけ知っている。

汐見さんは、僕が提げている風呂敷の包みに目をやって、小さく頷いた。

「とみやさんの、お孫さんですね」

「あ、はい。今日、祖母が来られなくて」

「すみません。受け取る前に、一つお願いしてもいいですか」

汐見さんは巻尺のほうへ顎を少し動かした。

「手が塞がっていて。目盛りを読んでもらえますか」

急いでいる、とは言い出せなかった。弁当の箱を盤木の端に置いて、汐見さんの手元に顔を寄せる。巻尺は船底の下の端から上へ伸びていて、汐見さんの指が押さえているのは、船体の色が変わる所だった。下は茶色い塗膜と泥。上は、白っぽい貝殻がびっしりと重なっている。

「……八十二センチ、です」

「八十二」

汐見さんはそれを繰り返すと、胸ポケットから防水の野帳（屋外の作業で使う、硬い表紙の記録帳）を出した。泥の付いていない小指でページを押さえて書き込む。それから巻尺を巻き取り、二メートルほど船首のほうへ移って、同じように当てる。

「ここもお願いします」

「七十九です」

汐見さんがまた二メートルほど移る。

「……七十八、かな。七十八です」

三か所。読んだ数字を汐見さんが野帳に書く。測っているのは、貝殻が付いている所と付いていない所の境目の高さらしかった。何のためかは分からない。ポケットの中のスマートフォンが、また一度震えた。

三か所目を読み終えると、汐見さんは野帳を閉じずに、船体の反対側へ回っていった。

置いていかれた形になって、僕は初めて船を見上げた。

鋼の船体は茶色く、ところどころ白い貝殻の層が厚く盛り上がっている。甲板の縁から泥が垂れたまま乾いていて、船首の近くに、名前を書いた板らしいものがある。泥に埋もれて、文字は一つも読めない。

二十年前、僕は九歳だった。あの日の翌朝、港の岸壁に大人たちが集まっていたのを覚えている。何が起きたのか、そのときはよく分からなかった。分かったのは、もっと後になって、食堂の常連の話からだ。

この船の話になると、常連たちは昔から決まって同じことを言う。

「警報を受けても、帆を降ろさなかった船長がいたって。港の人はみんなそう言ってますよね」

反対側から戻ってきた汐見さんに、話の接ぎ穂のつもりで言った。汐見さんは相槌を打たなかった。巻尺を持ち直して、船体の向こう側を指した。

「向こうも、読んでもらえますか」

聞こえなかったのかもしれない、と思った。

汐見さんが国の調査官だったらしい、という噂も、食堂で聞いたことがある。確かめたことはない。

反対側へ回る途中で、作業員が二人、洗浄の段取りを話していた。船首の名前の板は、いちばん最後に洗うらしい。泥ごと削ると、字が一緒に剥がれるかもしれないから、と。

こちら側の三か所も、僕が目盛りを読んだ。百十四、百十八、百二十。さっきより、四十センチ近く高い。

汐見さんは野帳を開いたまま、僕にも見える角度で持った。

ページには、表が引いてあった。列の見出しは、仮説、予測、やったこと、見たこと、結論。仮説の欄にはこう書いてある。

――見た目の濃い側の舷（船の左右の側面のこと）が下。

予測の欄には、その舷の境目が高く、反対の舷の境目が低い、とあった。

僕は、さっき汐見さんが巻尺を当てる前に、野帳にペンを走らせていたのを思い出した。この二行は、測る前に書かれていた。見た目が濃く汚れて見えたのは、最初に測ったほうの舷だった。そちらが下だったなら、そちらの境目が高く出るはずだった。

読んだ数字は、逆だった。

汐見さんは、消しゴムを使わなかった。仮説の行に横から一本、まっすぐな線を引いた。その横に小さく「棄却」と書いた。その下の行に、新しい仮説を書いた。反対の舷が下。

それから、泥の手のまま、洗浄の作業員のほうへ顔を向けた。

「洗う順番を入れ替えます。見た目の濃いほうから先に」

作業員が手を上げて応えた。

「外れたのに、消さないんですか」

僕は思わず聞いていた。

「消しておいたほうが、見やすくないですか」

汐見さんは、野帳の線を引いた行を、泥の付いていない小指の先で示した。

「消さずに、線を引く。同じ所を、もう一度測らないためです」

それだけだった。

そのときの僕には、帳面の付け方の話にしか聞こえなかった。

汐見さんはそこでやっと手を作業つなぎの腰の布で拭い、盤木の端に置いた弁当の箱を受け取った。数を確かめる目が、ふと僕のポケットに向いた。さっきから何度も震えているのに、気づかれていたらしい。

「何か、急ぎのお仕事ですか」

それで、言わなくていいことまで言ってしまった。

「ネットスーパーの、翌朝便の受付を作っているんです」

注文した日の翌日の午前に届く便で、締め切りは注文した日の夜10時。その便の注文が、締め切りの前なのに断られる。そういう苦情が三日前から来ている、と僕は続けた。

汐見さんは、弁当の箱を抱えたまま小さく頷いた。

一回目は、締め切りの比較が一秒ずれているのだと思った。10時ちょうどの扱いを変えた。二回目は、締め切りの時刻を読んで持っておいた値が古いまま残っているような気がして、毎回読み直すようにした。三回目は、設定の締め切りの時刻が別の値になっているのではないかと思って、設定の読み込みを直した。

どれも、直したあとにちゃんと注文を通して確かめた。通った。だから出した。それでも次の苦情が来て、戻して、次を直した。

早口になっているのが自分でも分かった。汐見さんは遮らずに、最後まで聞いていた。

「確かめたのは、何時でしたか」

「夜の9時台です。9時半とか、9時50分とか。一回目は9時59分」

汐見さんは少し間を置いた。

「その時刻は、直す前でも通りましたか」

スマートフォンを持った手が、下がった。

「……通ります」

声に出してから、自分の言ったことの意味が分かった。9時台の注文は、直す前から普通に受け付けられていた。

三回とも、直す前でも通る時刻で確かめていた。通るに決まっている所を通して、直ったと思っていた。三回とも、何も確かめていなかった。

汐見さんは答えを言わなかった。

「昼休みに、もう一度来られますか。事務所の机が空いています」

食堂には戻らなかった。いつも食堂の隅で仕事をするから、鞄にノートパソコンが入っている。

第2幕: 分ける

ドックの事務所は、プレハブの二階だった。石油ストーブが焚かれていて、窓の外に船が見える。作業員たちは長机で弁当を開けていた。汐見さんは作業つなぎの上半身を腰で結んだまま、机の端で弁当を食べ始めた。

僕はノートパソコンを開いて、汐見さんのほうへ画面を向け直した。受付の処理は僕が書いたものだ。翌朝便の受付の関数は、注文を受けた時刻を受け取り、受け付けたら配達日を返し、締め切りを過ぎていたら断る。現在の時刻は、受付のハンドラが日本の時刻に直してから渡している。テストのしやすさを考えて、関数の中で時計を読まないようにしてある。

// Accept は注文を受け付け、配達日（JST の 0 時）を返す。
// now の 22:00:00 より前なら翌日の配達日、以降なら ErrPastDeadline。
func Accept(now time.Time) (time.Time, error) {
	today := now.Truncate(24 * time.Hour) // 「今日の0時」のつもり
	y, m, d := today.Date()
	deadline := time.Date(y, m, d, DeadlineHour, 0, 0, 0, now.Location())
	if !now.Before(deadline) {
		return time.Time{}, ErrPastDeadline
	}
	return time.Date(y, m, d+1, 0, 0, 0, 0, now.Location()), nil
}

DeadlineHour は 22。今日の0時を作り、その日の22時を締め切りにして、締め切りより前なら翌日を配達日として返す。わざわざテストが全部緑になっている画面まで開いて見せた。夜9時半の注文は受け付ける、夜10時半の注文は断る。ちゃんと通っている。

汐見さんは画面を読んだ。スクロールが速かった。関数を一つ読み終えるたびに指が止まり、また次へ進む。コードを読める人の読み方だった。

「苦情の文面を、全部見せてもらえますか」

四件を並べた。汐見さんは自分の野帳を出さずに、事務所の棚から裏紙を一枚取って、縦に一本線を引いた。左と右に分かれた紙と、ボールペンを僕に渡す。

「左に、苦情の文面を、そのまま写してください。一字も変えずに」

写しながら、気づいた。

――昨日の夜に頼もうとしたら、締め切りを過ぎましたと出ました。 ――夜中に注文したら断られました。 ――寝る前に翌朝の分を頼もうとしたのですが。 ――朝いちばんに頼もうとしたら、もう締め切りだと。

どれにも、時刻が書いていない。

僕はこれを、ずっと締め切りの10時前後の話だと読んでいた。夜、と書いてあれば10時のあたり。だから一回目に、10時ちょうどの扱いを疑った。

「でも、夜は夜ですよね」

半分笑って言った。

「何時ですか」

汐見さんはそれだけ言った。

答えられなかった。客は「夜」と書いた。10時という数字は、どこにもない。客の言った「夜」を、僕が自分の頭の中で10時に置き換えていた。置き換えたのは僕だった。

注文のログを引いた。苦情の四件の注文が、実際に何時に入ったのか。三日間、一度も見ていなかった。

01:32。00:47。02:15。05:40。

「……なんで、今まで見なかったんだ」

声が大きくなった。長机の作業員が一人、こちらを見た。汐見さんは何も言わなかった。裏紙を、僕のほうへ少し滑らせた。右の列が空いている。

右の列に、見たこととして、ログの四つの時刻と、テストが通っている事実を書き足した。

紙の左右を見比べて、一つずつ分けた。

見たことは、苦情が四件あったこと。注文の時刻は、四件とも夜中の0時台から朝の5時台の間だったこと。夜9時半と夜10時半で書いたテストは、全部通ること。

思っていたことは、締め切りの境界のずれ。設定の値の間違い。古い値が残っていること。二回目は、何を疑ったのかが自分でも言えない。

まだ分からないことは、なぜ早朝の注文だけが断られるのか。

もう一つ、気づいた。僕はこの三日、苦情に返事を書くたびに「直りました」と書いていた。けれど、それは右の列のどこにも入らない。直った、というのは見たことではなく、僕の判断だった。

すぐにコードを開きたくなった。夜中だ。日付が変わったあとに何かある。

手が、キーボードの上で止まった。巻尺を当てる前に、汐見さんがペンを動かしていたのを思い出したからだ。測る前に、書いていた。

僕は裏紙を裏返して、汐見さんの野帳と同じ五つの列の表を引いた。やったことは実験、見たことは観察と、仕事で使う言葉に書き換えた。仮説、予測、実験、観察、結論。自分の三回の修正を、そこへ写してみる。

一回目。仮説は、締め切りの比較が一秒ずれている。予測は書ける。9時59分59秒か10時ちょうどの、どちらかで答えが仕様と違うはずだ。書きながら、気づいた。それなら、夜中の1時半の注文は関係ない。1時半は締め切りから三時間半も離れている。この仮説は、01:32 を説明できない。

三回目。仮説は、設定の締め切りの時刻が10時になっていない。予測も書ける。断られ始める時刻が、10時以外のどこかにあるはずだ。これも、日付が変わったあとの1時半を説明できない。日付が変われば、新しい日の締め切りまで、まだ二十時間あまりある。

二回目。仮説の欄に、何を書けばいいか分からなかった。値を捨てて読み直すようにした。何を疑って、そうしたのか。古い値が残っている気がした。どの値が、いつ、何のせいで古くなるのか。言えない。だから予測の欄が書けない。

ペンが止まった。

汐見さんが、二回目の行の空いた予測の欄を、指で一度だけ叩いた。何も言わなかった。

僕は、ログの時刻から、新しい候補を二つ、表の下に書き足した。

一つめは、「今日」の計算が、早朝だけ前の日になっている。

二つめは、早朝に走る在庫の更新の間だけ、受付が止まっている。うちの会社では、毎晩、夜中から朝にかけて、店舗の在庫を一括で更新している。その間、受付が何かに引っかかっていてもおかしくない。

どちらも、01:32 を説明できる。

番号を振った。境界のずれを H1、設定の時刻を H2、「今日」の計算を H3、在庫の更新を H4。二回目の修正は予測が書けないので、番号を振らなかった。だから三回目の修正が H2 になる。

H3 と H4 の予測の欄の前で、ペンがまた止まった。

汐見さんが、弁当の蓋を閉めた。

「少し、外に出ましょうか」

第3幕: 予測を先に書く

ドックの縁は、風が強かった。下では作業員が高圧洗浄機を構えて、さっき汐見さんが入れ替えた順番どおりに、見た目の濃い側の舷を洗っている。水が当たった所から、泥と貝殻が剥がれて、茶色い水になって流れていく。

「さっき、予測を書いたら二つ落ちました」

僕は言った。

「でも、全部測ってから、それに合う説明を探しても、同じように落とせませんか。そのほうが速い気がするんです」

汐見さんは、船体のほうを見たまま答えた。

「さっきの境目を、先に測ったとします。高い舷と低い舷が出ます。どちらが下だったか、それから決めれば、決めた仮説はいつも数字に合います」

「合うなら、いいじゃないですか」

「どんな数字が出ても合います。逆の数字が出ても、逆の仮説を書けば合います」

汐見さんは、そこで少し間を置いた。

「先に書いた予測だけが、外れることができます。外れた仮説だけが、確実に候補から落ちます」

僕はすぐには何も返せなかった。洗浄機の水しぶきの向こうで、さっき下だと書かれて、線を引かれた側の舷が、少しずつ鋼の色に戻っていくのを見ていた。

「これ、何ていう調べ方なんですか」

ようやくそう聞くと、汐見さんは調べ方の名前と、本の名前だけを言った。科学的デバッグ。Andreas Zeller の『Why Programs Fail』の6章。

あとで調べた。

科学的デバッグ（Scientific Debugging）は、失敗を観察し、その原因の仮説を立て、仮説から予測を立て、実験で予測を確かめ、仮説がそれ以上絞れなくなるまで繰り返す調べ方だ。Zeller は6章で、デバッグに当てはめた手順を次の五段で書いている。

  1. 失敗を観察する（Observe a failure）
  2. 観察と矛盾しない、失敗の原因の仮説を立てる（Invent a hypothesis as to the failure cause that is consistent with the observations）
  3. 仮説を使って予測する（Use the hypothesis to make predictions）
  4. 実験とさらなる観察で仮説を確かめる（Test the hypothesis by experiments and further observations）。予測どおりなら仮説を絞り込み、予測どおりでなければ別の仮説を立てる
  5. 仮説がそれ以上絞れなくなるまで、3と4を繰り返す（Repeat steps 3 and 4 until the hypothesis can no longer be refined）

同じ章の 6.5 は、記録の付け方を扱っている。書き残すのは、問題の報告、原因の仮説、仮説の予測、予測を確かめるための実験、実験で観察した結果、結果から出した結論。Zeller はこれを logbook と呼ぶ。汐見さんの野帳の列は、これだった。

確証バイアス、という言葉も、そのとき知った。自分の仮説を、否定するより確かめようとする傾向のことだ。

テストを書いた。仮説一つにつき、テストを一本。どのテストも、予測そのものではなく、仕様どおりに正しく動くことを確かめる形にした。仕様の形で書いておけば、原因が見つかって直したあと、そのまま再発を見張るテストとして残せる。テストの冒頭には、裏紙の表と同じ五つの列を、t.Log（テストの中から出力に一行を書き出す関数）で書いた。

第4幕: 九時の境目

Accept を、もう一度頭から読んだ。

早朝だけ「今日」が前の日になるのなら、怪しいのは日付を作っている行しかない。today := now.Truncate(24 * time.Hour)。今日の0時を作るつもりで書いた行だ。

Truncate は、時刻を指定した長さの倍数に切り捨てる関数だ。日の頭に揃えるときに、これまで何度も、何の疑いもなく書いてきた。前の職場ではサーバーも時刻も UTC で扱っていて、それで困ったことは一度もなかった。だからこそ、仕様を読み直した。Go の標準ライブラリの説明（pkg.go.dev の time パッケージ）には、こう書いてある。

Truncate returns the result of rounding t down to a multiple of d (since the zero time).

Truncate operates on the time as an absolute duration since the zero time; it does not operate on the presentation form of the time.

Truncate は、ゼロ時刻からの絶対的な経過時間に対して切り捨てる。表示上の時刻、つまり日本の時刻で見た何時何分に対してではない。そして、Go のゼロ時刻は「1年1月1日 0時0分0秒 UTC」、協定世界時（UTC）の時刻だ。

そこから、仮説を絞った。24時間ごとの切れ目は、UTC の0時に来る。日本の時刻は UTC より9時間進んでいるから、UTC の0時は、日本の時刻では朝の9時だ。Truncate は時刻が持っている場所（日本の時刻）を付けたまま、値だけを UTC の区切りに丸める。だから、表示は日本の時刻のまま、朝9時に揃う。

紙に、値を一つずつ追ってみた。

11月16日の0時47分（日本の時刻）は、UTC では11月15日の15時47分だ。24時間の倍数に切り捨てると、UTC の11月15日0時。日本の時刻で言えば11月15日の朝9時になる。today.Date() はこれを11月15日と読む。締め切りは11月15日の夜10時になり、0時47分はそれより後だから、断られる。

同じ日の夜9時半は、UTC では11月16日の12時30分だ。切り捨てると UTC の11月16日0時、日本の時刻で11月16日の朝9時。日付は11月16日のままで、締め切りは11月16日の夜10時。夜9時半はその前だから、受け付けられる。

紙の上で追った二つの時刻を、横に並べて書き直した。

二本の筋が分かれる時刻帯を、僕はこの三日間、一度もテストで通っていなかった。

昼や夜の時刻で書いたテストが全部緑だったのは、このためだった。朝9時から夜12時の手前までは、切り捨てても日付が変わらない。日付が一日ずれるのは、0時から朝9時の手前までだけだ。Truncate で日を切っても正しいのは、時刻を UTC で扱っているときだけになる。日本の時刻の値に使うと、日の区切りが9時間ずれる。
