コードサルベージャー シリーズ目次【困りごとから探す案内板】

「コードサルベージャー」シリーズの案内板です。原因の分からない障害をどう調べるか、科学的デバッグからブレームレス・ポストモーテムまでの調べ方を、沈没船を引き揚げて修復する物語で扱う連載を、困りごとから探せます。

2026-11-16
読了時間: 6分

「コードサルベージャー」は、原因の分からない障害をどう調べるかを扱う連載です。直し方ではなく、調べ方を扱います。港の乾ドックに引き揚げられた沈没船を、元海難事故調査官の引き揚げ屋・汐見澪（ミオ）が一年かけて修復していきます。毎回、船に縁のある人がドックを訪れて自分のバグを持ち込み、ミオが船体で行う調べ方を、自分のコードに持ち帰ります。実装は Go で、検証は go test だけで確かめます。

このページは目次を兼ねた案内板です。いま困っていることが決まっているなら「困りごとから探す」から、順に通して読むなら「全話一覧」から選んでください。公開に合わせて、回を足していきます。

まず読むなら

  • 深夜の注文が締め切り前なのに断られる。3回直したのは、どれも見当違いの場所だった — 科学的デバッグ。 思いつきの修正を当てては外し続けるとき、観察と仮説を分け、予測を先に書いてから実験する回。どんなバグにも最初に効く調べ方

困りごとから探す

直しても直しても、同じ苦情が来る

  • 深夜の注文が締め切り前なのに断られる。3回直したのは、どれも見当違いの場所だった — 科学的デバッグ。 3回直しても直らない。仮説ごとにテストを書き、外れた仮説も残して原因まで絞る

報告されたエラーが、手元では起きない

  • 同じCSVなのに、ある月だけ取り込めない。違っていたのは中身ではなかった — 再現手順の確立。 同じファイルなのに、ある月だけ取り込めない。報告者との差を表にして上から揃え、毎回起きる状態にしてから原因を比べる

大きい入力のときだけ落ちて、どこが悪いのか分からない

  • 800行のデータを流すとだけ落ちる。原因は1行ではなかった — Delta Debugging。 800行の部材表を流すとだけ panic する。一部と残りで同じ壊れ方かを確かめながら入力を削り、落ちる最小の組まで絞る

前は動いていたのに、いつの変更で壊れたか分からない

  • 去年の報告書を計算し直すと、数字が合わない。怪しいと読んだ変更は無実だった — git bisect。 去年の版は合い、今の版は合わない。判定プログラムに良い・悪い・調べられない（125）を返させ、git bisect run で最初に壊れたコミットを特定する

処理の出口で値が違うが、途中のどこで壊れたか分からない

  • グラフの最高潮位が、気象台の発表と合わない。途中に立てた検査は、壊れた値を通していた — Wolf Fence。 8段の集計の出口で最高潮位が3cm低い。その地点で何であるはずかを持った柵を段の間に立て、前か後かで半分ずつ絞って壊した段を特定する

複数のログを時刻で並べると、起きたはずのない順になる

  • 複数サーバーのログを時刻順に並べたら、返信が問い合わせより前の時刻で記録されていた — happened-before。 返信が問い合わせより前に並んだ。時計は合っていた。同じ局の中の順と、送信と受信の対だけを辿って順を組み直し、記録から決まらない組は順不同として分けて出す

値がいつの間にか書き換わるが、どこで書いたのか分からない

  • どこにも代入していないのに、マスタの単価が勝手に安くなる — ウォッチポイント。 単価の名前で全部探しても、書いた行が見つからない。値の置かれた場所を delve の watch -w で見張り、書き込みの瞬間に止めて、名前の出ない append の行を特定する

同じテストが、コードを変えていないのに落ちたり通ったりする

  • 50回に3回落ちるテストを、再実行で通すのをやめて原因を分ける — Flaky テストの切り分け。 再実行で通すのをやめ、単独で流す・順序を変える・-race・遅延の注入を一つずつ当てて、非同期の待ち・並行性・順序依存のどれに依存しているかを分ける

ログを足したり止めたりすると、バグが起きなくなる

  • ログを足すと消えるバグは、もう一度起こさなくていい — 記録と再生。 締め切り直前の入札が漏れるのに、ログを足すと起きない。外から入る到着順・時刻・くじだけを受け手で記録し、失敗した一回を再生の中で止めて調べる

落ちた行に誤りが無い。壊れたのは、ずっと前の別の操作だった

  • 落ちないように足した一行が、壊れた値を数時間先へ運んでいた — Fail Fast。 明け方のジョブが範囲外アクセスで落ちるのに、落ちた行は正しい。常に成り立つべき台数の関係を表明として操作ごとに検め、破れた瞬間にその要求だけを止めて、壊れた操作を特定する

本番でだけ遅く、手元では何度測っても速い

  • 本番でだけAPIが遅い。推測で直すのをやめ、本番のプロセスを30秒だけ測った — 本番でのプロファイリング。客の本番でだけ朝に計算が遅く、手元で見つけた遅い所を直しても効かない。本番のプロセスから低い負荷で30秒の CPU プロファイルを取り、本番のデータでだけ重くなる関数を特定する

障害の振り返りが「誰のミスか」で終わり、同じ事故の芽が残る

  • なぜなぜ分析を5回やったら、新人のせいで終わった — ブレームレス・ポストモーテムとスイスチーズモデル。なぜなぜ分析が新人の確認不足で止まった振り返りを、その時点で合理的だった判断と、穴の揃った防護の層として書き直し、次に誰が打っても止まる対策にする
