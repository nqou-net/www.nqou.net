落ちないように足した一行が、壊れた値を数時間先へ運んでいた

明け方のジョブが範囲外アクセスで落ちるのに、落ちた行に誤りがない。台帳が壊れたのは数時間前の別の操作でした。常に成り立つべき台数の関係を表明として書き、破られた瞬間にその操作だけを止めます（Fail Fast）。

第1幕: 吊られた白い包み

毎朝4時半に走る再配置計画のジョブが、今週二度、範囲外アクセスで落ちた。落ちた行は分かっている。でも、その行に間違いが無い。間違いの無い行で落ちるプログラムを、自分は五年かけて一人で育ててきたらしい。

ドックの門の外に、自販機が一台ある。自分はそこで缶コーヒーを買い、取り出し口に手を入れたまま、携帯の画面をもう一度読んだ。朝5時に鳴った運用の通知だ。今週二度目の通知だった。

自分の勤め先は、地方都市でシェアサイクルを運営している。シェアサイクルは、街のあちこちにあるステーションで自転車を借りて、どこかのステーションに返す仕組みだ。社員は十数人で、アプリの裏側を書いているのは自分一人しかいない。貸出も返却も回送の記録も、明け方の再配置計画も、全部自分が書いた。再配置計画は、偏った自転車をトラックで朝のうちに積み直すための計画だ。どのステーションから何台積んで、どこへ下ろすか。それを毎朝4時半に計算する。

その計算が、落ちる。

缶を取り出して、顔を上げた。

門の向こうで、白い包みが宙に浮いていた。クレーンのワイヤの先で、帆布の包みが風を受けて、ゆっくり回っている。ワイヤがきしむ音が、門のこちらまで届いた。晴れていて、風がある。五月の上旬の、少し冷たい風だ。

風下にいたせいで、新しい布の匂いがした。工房の糊の匂いだと思う。

包みの下に、人がいた。作業つなぎの上を腰で結んだ女の人が、片手を上げて、クレーンの運転席に向けて手首を小さく回している。包みが、その手の動きに合わせて下りていく。

自分は門をくぐった。

包みが甲板に着いた。女の人が手を下ろして、こちらを見た。首にタオル、胸ポケットに小さな野帳。

「包みの片方の端を持てる方を、探していました」

誰ですか、とは訊かれなかった。自分は缶を足元に置いた。

「持てます」

梯子で甲板に上がって、包みの端をつかんだ。思ったより重い。布が詰まった重さだ。

「昔も、こうやって持たされました」と自分は言った。「高校のとき、この船の体験航海に二週間、訓練生で乗ったんです。帆の端を持ってるだけで褒められる身分でした。甲板長の号令ひとつで全員の手が止まって、止まるのが遅れたやつが怒鳴られて。だいたい自分でしたけど」

女の人は、一度頷いた。

「汐見です。引き揚げの会社の者です」

それだけ言って、包みの紐の結び目に指を入れた。手は止まらなかった。訓練生だった、と聞いて手を止める人は多い。この人は止めなかった。

「久住です」と、結び目を見ている横顔に名乗った。

紐をほどく間、汐見さんは作業員の人たちと、帆のどちらが上かを確かめていた。帆布に書かれた小さな印を、指でたどっている。自分には話しかけてこない。自分の仕事は端を持っていることだけになった。

さっき梯子を上がる途中で、一度だけ帆柱を見上げていた。前のほうの帆柱だ。そこから先は見なかった。

端を持つ手が空いたのは、作業員の人が包みの反対側を引いて、布がたるんだ数十秒だった。自分は片手で携帯を出して、スタックトレースを開き直した。朝から何度も開いているので、指が勝手にそこへ行く。

自転車がいる場所は、三つしかない。ステーションのラックに止まっている（在庫）か、利用者が借りている（貸出中）か、回送のトラックに積まれている（回送中）か。この関数は、その三つを順に数えて枠に詰める。35行目は、貸出中の自転車を詰めるループだ。ステーションの在庫を詰め終えた時点で、枠はもう残り少なかったことになる。

明け方の帳簿を手で足してみると、三つの合計は保有台数より11台多かった。

計画のコードは、保有台数より多い自転車がいるはずがない、という前提で書いた。その前提は正しい。会社の自転車は、勝手に増えない。新車を入れる日は、自分が保有台数を書き換える。

だから、どこかで帳簿の上の自転車が増えている。増えたのは、落ちた4時半より前のどこかだ。日中の操作は数千件ある。貸出、返却、トラックの積み込み、荷下ろし。どれも、利用者のアプリやトラックの端末から、HTTP の要求としてサーバに届く。一つの要求が、一つの操作になる。

落ちたのは明け方でも、増えたのは昼かもしれない。スタックトレースに出てくるのは、落ちたときに走っていた関数だけだ。増やした操作の名前は、どこにも出てこない。

それでも、落ちないよりはましだと思っている自分がいた。夜中にサーバが落ちるのがいちばん困る。夜中にサーバが落ちれば、朝の通勤の人が自転車を借りられない。だから、これまでおかしな値はその場で丸めて、先へ進むようにしてきた。それで朝が守られた日も、実際にあった。

「上を、持っていてください」

顔を上げると、包みが解けていた。帆が甲板に広がっている。白い三角の帆だった。長い一辺に、真鍮の金具が等間隔に縫い付けてある。丸い金具だ。日の光を返して、列になって光っている。

汐見さんが、作業員の人たちに段取りを言った。

「ステイの下の端から、順に掛けていきます」

それから自分のほうへ、帆のいちばん上の角を指した。自分は携帯をしまって、そこを持った。

帆の端を持ったまま、真鍮の列を指でなぞった。一つ、二つ、三つ。七つ目あたりで、指を止めた。数えて何になる、と自分につっこむ。数えたって、自転車は減らない。

第2幕: 掛けた直後

前の帆柱から船首へ、ワイヤが一本、斜めに張られている。帆柱を前に引いて支えるワイヤで、ステイと呼ぶのだと、汐見さんが作業員の人に確かめる声で知った。今日はこのステイに、新しい帆を付ける。

帆は二種類あると、昔、訓練生のときに教わった。帆柱から横に渡した棒に吊る横帆と、船の前後の向きに張る縦帆だ。

今日の帆は縦帆のほうだ。ステイに沿って張る三角の帆を、ステイスルと呼ぶ。

さっき光っていた真鍮の金具は、帆環という。帆の前の縁に、一定の間隔で付いている。一つずつステイに掛けると、帆はステイに沿って滑って上がり下りする。

作業員の人が、いちばん下の帆環をステイに掛けた。

帆環の並んだ前の縁を、ラフと呼ぶ。英語の言葉で、ステイスルならステイ側の縁のことだ。汐見さんは、帆環が一つ掛かるたびに下から帆の縁を目で追った。帆環から帆環へ、縁がステイに沿ってまっすぐ伸びているかを見ている。手は動かさない。目だけが、縁に沿って上へ行き、下へ戻る。作業員の人は次の帆環を掛ける。汐見さんの目がまた上がる。

四つ目。五つ目。

六つ目を掛けた直後に、汐見さんが短く声を掛けた。

「そこ、止めてください」

作業員の人の手が止まった。

汐見さんが梯子を一段上がって、六つ目の帆環を指した。自分の位置からでも、言われれば分かった。その帆環だけ、裏返しに掛かっている。そこで縁がわずかにねじれて、帆布に斜めの皺が一本、走っていた。

「六つ目だけ、外して、向きを直してください」

作業員の人が六つ目を外し、向きを返して掛け直した。汐見さんがもう一度、下から縁を目で追った。皺は消えていた。汐見さんが手を上げて、再開の合図をした。

止めてから再開まで、一分も無かったと思う。

「上げてから、まとめて直したほうが早くないですか」と自分は言った。「素人の案ですけど。全部掛けて、引っ張り上げて、変なとこだけ直す。自分ならそうします。仕事でもそうしてます」

汐見さんは、七つ目を掛ける作業員の人の手を見たまま答えた。

「上げると、ねじれは帆の上のほうへ行きます。上で引っかかります。そのときは、どの環だったか、下から見えません」

それだけ言って、目を縁に戻した。七つ目。縁がまっすぐかを見る。八つ目。

早いな、とだけ思った。上げてから気づくより、掛けたその場で気づくほうが早い。それはそうだ。そう思って、帆の端を持ち直した。

ポケットで、携帯が鳴った。

運用の通知の音だ。自分は通知の音を、わざと耳障りな音にしてある。夜中に起きられるように。その音が、晴れた甲板に響いた。

汐見さんの目が、一瞬、縁から離れた。汐見さんがこちらを見た。

「すみません」と自分は言った。言ってから、画面を見た。明け方のジョブを手で再実行しておいたのが、また落ちたという通知だった。同じ行で、同じ範囲外アクセス。当たり前だ。帳簿が直っていないのだから。

「すみません、仕事の通知で。明け方に、自転車の割り振りを計算するプログラムが落ちるんです。今週二回。落ちた行は分かってて、その行は正しいんですよ。自転車の台数が、会社が持ってる台数より多くなってて、それで枠からはみ出して落ちる。自転車が、帳簿の上で、増えてるんです。勝手に。増えるなら現実でも増えてほしいんですけど」

汐見さんは、作業員の人に合図して、次の帆環を掛けさせた。縁を目で追いながら、こちらの話を聞いていた。遮らなかった。

「日中の操作が数千件あって、そのどこかで増えてる。明け方に落ちる前の、どこかで。たぶん、トラックの積み下ろしのどれかだと思うんですけど」

汐見さんの目が、縁の上から下へ戻った。

「どこで増えたかは、まだ見ていないんですね」

「……見てないです。トラックのどれか、は自分の勘です」

汐見さんは頷いて、九つ目の帆環に目を移した。自分の話から、見たことと、思ったことが分けられて、思ったことのほうだけが手の中に残った。

昼になった。

作業員の人たちが、甲板の日陰で弁当を広げた。自分は帆の陰に腰を下ろして、ノートパソコンを開いた。帆はステイに半分まで掛かっていて、その影が甲板に三角に落ちている。

会社は、操作を全件、操作の記録として残している。時刻、操作名、ステーション、台数。監査のために、前からある仕組みだ。昨日一日分を開いた。数千行ある。

前から読むことにした。在庫の合計と、貸出中と、回送中を、自分で足し合わせながら、保有台数と比べていく。メモ帳に、時刻と合計を書く欄を作った。

7時台の三十行で、手が止まった。

この調子で数千行。一行ずつ足し算。しかも、どこかで一度でも足し間違えたら、そこから先が全部ずれる。ずれたのが自分の足し算なのか、帳簿なのか、見分けがつかなくなる。

やり方を変えた。行を読むのではなく、帳簿を動かすコードのほうを読む。台数が増えうるのは、ステーションの在庫を足す所だけのはずだ。

最初に目に入ったのは、空きラック数を返す Free() だった。

// Free は空きラックの数を返す。
func (s Station) Free() int {
	free := s.Racks - s.Docked
	if free < 0 {
		free = 0
	}
	return free
}

この丸めは、自分が足した。去年の秋、ダッシュボードの空きラック数に、マイナスが一瞬出たことがある。-2。ラックのセンサーの知らせが遅れて届いたせいだろうと思って、0にそろえるようにした。それきり、マイナスは見ていない。

この丸めは、外から来た値に掛けたものではない。ラック数から在庫を引いた、自分のコードが計算した空きの数に掛けた丸めだ。

ここで丸めているから、ここは大丈夫。そう思って、次へ進みかけた。

func (f *Fleet) unload(id string, n int) error {
	st, ok := f.stations[id]
	if !ok {
		return ErrNoStation
	}
	if n <= 0 || n > f.inTransit {
		return ErrBadCount
	}
	if over := st.Docked + n - st.Racks; over > 0 {
		// ラックに入りきらない分は、隣のステーションへ回す
		next, ok := f.stations[st.Next]
		if !ok || next.Racks-next.Docked < over {
			return ErrNoRoom
		}
		next.Docked += over
	}
	st.Docked += n
	f.inTransit -= n
	return nil
}

隣に空きがあれば、入りきらない分を隣に足す。下ろした分を在庫に足して、回送中から引く。読んで、頷いた。ここも書いたのは自分だ。満車の荷下ろしは、一日に数件しか無い。書いた日のことは、よく覚えていない。

荷下ろしを読み終えて、貸出と返却に進んだ。どちらも一台ずつ足して引くだけで、足す数と引く数は揃っている。

全部読んだ。どこも正しく見えた。

ふと、明け方のジョブの先頭で切り捨てればいい、と思った。数えた台数が保有台数を超えていたら、超えた分を数えない。枠からはみ出さないから、ジョブは落ちない。三行で済む。

キーボードに指を置いたところで、止めた。

それをやると、どこかで増えた自転車が、どこかで消える。切り捨てた11台がどのステーションの何台目なのか、誰にも分からなくなる。トラックは、帳簿にしかいない自転車を取りに行く。現場にいる自転車は、帳簿から消える。

画面を閉じかけて、また開いた。

夜中にサーバを落としたくない。でも、明け方にはジョブが落ちた。

二つの事実を並べてみても、どちらからどちらへ線を引けばいいのか分からなかった。丸めて先へ進めると、明け方にジョブが落ちる。丸めずにその場で落とせば、夜中にサーバが落ちる気がする。どちらを選んでも、朝の利用者に迷惑がかかる気がした。

弁当を食べている作業員の人の向こうに、甲板の後ろのほうが見えた。

甲板の上に、小さな建物が載っている。窓が並んでいる。周りの外板と比べると、そこだけ鋼の色が少し違った。錆の出方も違う。後から載せたものだと、一目で分かる。

「あれ、まだ残ってるんだ」と声が出た。

汐見さんが、弁当箱の蓋を閉めたところだった。こちらを見て、自分の視線の先を見た。

「訓練生の部屋だったんですよ、あそこ」と自分は言った。「二段の寝台がずらっと並んでて。窓があって、下の船室より明るいんです。だから当たりの部屋って呼ばれてて、くじで決めました。自分は当たりました。人生で数少ない当たりです」

汐見さんは黙って聞いていた。

「定員を増やすために、後から載せたんだって、甲板長が言ってました。もとは無かった部屋だって。夜、船が揺れると、当たりの部屋はよく分かりました。下の部屋のやつらより、よく揺れた。当たりの代償です」

笑ったけれど、汐見さんは笑わなかった。胸ポケットから野帳を出して、建物のほうを一度見て、一行書いた。

「寝台は、いくつありましたか」

「八つです。片側に二段が二つずつ。上の段を取り合いました」

汐見さんはそれも書いた。

自分は建物の窓を見た。窓は、引き揚げの泥が拭われて、日を返していた。

「船が沈んだあと、調査の人たちが、自分らのところにも話を聞きに来ました。訓練生だった全員のところに。どんな人だったかは、覚えてないです。名前も。訊かれたのは、船での暮らしの話でした。何時に起きて、どこで寝て、何を食べてたか」

汐見さんは、野帳を閉じかけた指を止めなかった。ペン先を帆のほうへ向けたまま、自分の話の終わりを待った。

この船が沈んだのは、自分が乗った次の年の航海だった。自分は、その航海には乗っていない。

汐見さんは野帳をしまい、立ち上がる前に、建物の窓を一度見た。それから帆のほうへ戻っていった。

第3幕: 待て

午後は、帆の残りの帆環を掛ける作業だった。自分は帆の上の端を持つ係に戻った。

十いくつ目かの帆環で、汐見さんがまた作業員の人の手を止めた。今度の帆環は、ほかの環とは逆の側から、ステイに掛かっている。

手が止まった。自分は甲板を見回した。

帆はステイに半分以上掛かったまま、そこにある。甲板の作業員の人たちは、それぞれの持ち場で、綱を握ったまま待っている。誰も持ち場を離れていない。汐見さんは、その一つの帆環だけを外させて、掛け直させた。

それを見ていて、思い出した。

訓練生のとき、帆を上げる綱を、みんなで引いていた。掛け声に合わせて、腕が痛くなるまで引いた。そのとき、甲板長が叫んだ。

// sane は、常に成り立つべき関係を検める。破れていれば、どの値がいくつかを返す。
//  1. 全ステーションの在庫の合計 + 貸出中 + 回送中 = 保有台数
//  2. 各ステーションで 0 <= 在庫 <= ラック数
//  3. 貸出中 >= 0、回送中 >= 0
func (f *Fleet) sane() error {
	docked := 0
	for _, id := range f.order {
		s := f.stations[id]
		if s.Docked < 0 || s.Docked > s.Racks {
			return fmt.Errorf("station %s docked=%d racks=%d", id, s.Docked, s.Racks)
		}
		docked += s.Docked
	}
	if f.rented < 0 || f.inTransit < 0 {
		return fmt.Errorf("rented=%d inTransit=%d", f.rented, f.inTransit)
	}
	if docked+f.rented+f.inTransit != f.owned {
		return fmt.Errorf("docked=%d rented=%d inTransit=%d owned=%d", docked, f.rented, f.inTransit, f.owned)
	}
	return nil
}

// mustBeSane は、破れていたら panic する。自分のコードの誤りだけがここに来る。
func (f *Fleet) mustBeSane(op, when string) {
	if err := f.sane(); err != nil {
		panic(fmt.Sprintf("%s: %s: %v", op, when, err))
	}
}

// apply は、操作を写しに当てて、検めて通ったときだけ本体に置き換える。
func (f *Fleet) apply(op string, do func(c *Fleet) error) error {
	f.mu.Lock()
	defer f.mu.Unlock()
	f.mustBeSane(op, "before")
	c := f.clone()
	if err := do(c); err != nil {
		return err
	}
	c.mustBeSane(op, "after")
	f.stations, f.rented, f.inTransit = c.stations, c.rented, c.inTransit
	return nil
}

func (f *Fleet) clone() *Fleet {
	c := &Fleet{stations: make(map[string]*Station, len(f.stations)), order: f.order,
		owned: f.owned, rented: f.rented, inTransit: f.inTransit}
	for id, s := range f.stations {
		v := *s
		c.stations[id] = &v
	}
	return c
}

// newServer は、口のハンドラを登録する。操作はすべて recoverOp を通る。
func newServer(f *fleet.Fleet, logger *log.Logger) http.Handler {
	mux := http.NewServeMux()
	handle := func(pattern string, do func(r *http.Request) error) {
		mux.Handle(pattern, recoverOp(logger, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			if err := do(r); err != nil {
				http.Error(w, err.Error(), http.StatusConflict)
				return
			}
			fmt.Fprintln(w, "ok")
		})))
	}
	n := func(r *http.Request) int { v, _ := strconv.Atoi(r.FormValue("n")); return v }
	handle("POST /rent", func(r *http.Request) error { return f.Rent(r.FormValue("station")) })
	handle("POST /return", func(r *http.Request) error { return f.Return(r.FormValue("station")) })
	handle("POST /load", func(r *http.Request) error { return f.Load(r.FormValue("station"), n(r)) })
	handle("POST /unload", func(r *http.Request) error { return f.Unload(r.FormValue("station"), n(r)) })
	return mux
}

// recoverOp は、操作の中で起きた panic（表明の破れ）を1行のログにして、その要求だけ 500 で返す。
func recoverOp(logger *log.Logger, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if v := recover(); v != nil {
				logger.Print(v)
				http.Error(w, "internal error", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}

四つの口は、どれも handle を通って登録される。handle は、中身のハンドラを必ず recoverOp で包む。ログの書き先は、main が作って newServer に渡す。NewFleet には手を入れていない。

存在しないステーションや、空のステーションでの貸出のような、外から来るおかしな要求は、これまでどおり error で返る。この口では 409 になる。recoverOp に来るのは、mustBeSane が鳴らした panic だけだ。

どの版でも、表明は一度も止まらなかった。最後の在庫・貸出中・回送中も、明け方の計画も、操作ごとに返す error も、全部一致した。操作のたびに空きラック数を確かめて、一度も負にならなかった。満車の荷下ろしが起きない日なら、在庫がラック数を超えることも無い。だから丸めを消しても、その日の振る舞いは何も変わらない。

Go の FAQ の引っかかりにも、自分の言葉で答えが出せた。panic にするのは、自分のコードの不変条件が破れたときだけだ。それは取り繕えない。取り繕うと、明け方のジョブが落ちる。サーバは、口のハンドラを包む関数で動き続ける。FAQ の言う、サーバが動き続けること、は境界の recover で満たしている。

存在しないステーションのような、外から来るおかしな値は、これまでどおり error で断る。表明を、外から来た値の検査には使わない。

第4幕: 明け方の1行

帆が上がった。

最後の帆環を掛け終えると、作業員の人たちが綱を引いた。三角の帆が、ステイを滑って上がっていく。汐見さんは下から、縁を最後まで目で追った。上の端まで行って、目が止まった。汐見さんが手を上げて、作業員の人たちに合図した。

新しい帆が、風を少しはらんだ。白い布が、ゆっくり膨らんで、また戻った。

帆の陰で、自分は本番に入れる準備をしていた。表明と、recoverOp。直す一行は、まだ入れない。

入れる直前で、手が止まった。

本番の帳簿は、もう壊れている。昨日の満車の荷下ろしで増えた11台が、帳簿に残ったままだ。このまま表明を入れたら、どの操作の要求も、写しを作る前の検めで止まる。壊れた帳簿から始めたら、すべての要求が 500 で返る。

体験航海のとき、訓練生に一冊ずつ配られた航海記録の手帳だ。表紙に船の名前が刷ってある。毎日の天気と、船の位置と、やった作業を書く。自分のは、最後の数頁が白いままになっている。二週間ぶんの頁を、使い切らなかった。

野帳の写し

  • 見たこと: 新しいステイスルの帆環を、下から順に掛けました。掛けるたびにラフを下から見て、十いくつ目までに、裏返しの環と、反対側から掛かった環を一つずつ見つけ、それぞれその場で掛け直しました。久住さんの件: 昨日の操作の記録を、表明を入れた版に流すと、14時10分の Unload st01 4 で止まりました。st01 の在庫16、ラック12。隣へ回した4台を、st01 から引いていませんでした
  • 思ったこと: 久住さんは、計画の行は正しく、トラックの積み下ろしのどれかで自転車が帳簿の上で増えたと見ていました。どこで増えたかは、まだ見ていませんでした。増えたのは、満車の荷下ろしの中でした
  • 調べ方: Fail Fast。問題が起きたら、その場で、目に見える形で止めます。常に成り立つべき台数の関係（不変条件）を表明として書き、操作ごとに、確定させる前に検めます
  • 固定したもの: 本番に残した表明（sane）と、HTTP の口（要求の入口）のハンドラを包む関数（recoverOp）。表明が破れたら、その要求だけを止め、操作名と破れた値を1行のログに出します
  • 変えていないもの: 満車の荷下ろしが無い日の操作の列で、在庫・貸出中・回送中・明け方の計画・返す error が、表明を入れる前と後で一致しました（種を変えて5日分）。丸めを消しても、その範囲では空きは一度も負になりませんでした。ログの出力と処理時間は比べていません
  • まだ見ていない所: sane に書いていない関係（自転車1台ごとの位置、ほかのサーバとの台数の食い違い）。止まった1件の帳簿の手当て（人がします）。止まった荷下ろしは帳簿に残らないので、そのあとの要求のごく一部が 409 で断られることがあります（止まった直後の要求は 200 でした）。一つのプロセスの帳簿を前提にしています。複数のサーバで帳簿を分け持つ場合は見ていません
  • 船について: （聞いた話）甲板の後ろの、後から載せた構造物は、訓練生の居住区でした。二段の寝台が八つ。定員を増やすために後から載せたと、当時の甲板長が話していたそうです
