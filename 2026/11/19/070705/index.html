第1幕: 綴りの箱

去年わたしが出した査定の報告書の数字が、同じツールで計算し直すと合わない。十件のうち九件は合う。合わないのは一件だけで、差は三十万円。誰かに指摘されたのではない。自分で流して、自分で気づいた。監査の締め切りは来週の金曜日だ。

段ボール箱の底が、腕の内側に食い込んでいた。

ドック事務所の外階段は、鉄の板を組んだだけのものだった。一段ごとに、靴の下で板が鳴る。手すりは錆びていて、つかめば手のひらが赤茶になる。両腕が箱で塞がっているので、つかめない。

箱の中身は、二十年前の請求ファイルの写しだ。綴りが七冊。会社の書庫から、朝いちばんに出してきた。

北西の風が強い。階段の途中で、細かい水しぶきが頬に当たった。ドックの底から、高圧洗浄機の唸りが上がってくる。水の匂いに、鉄と泥の匂いが混じっていた。

再保険会社の監査が、先月の末に入った。去年わたしが査定した案件から十件を選び、今の査定ツールで計算し直す。その数字を報告書の数字と並べて出す。それが監査の求めだった。

九件は、一円まで合った。

一件だけ、合わなかった。報告書の支払額は二百五十万円。今のツールは二百二十万円を返す。

報告書の数字が間違っていたのか。今のツールが、この一年のどこかで変わったのか。どちらなのかは、まだ分からない。どちらだとしても、わたしの名前で出した報告書だ。

階段を上りきった。事務所の扉は、外開きではなかった。

箱の角で、扉を押し開けた。

事務所は、ストーブの灯油の匂いがした。

入ってすぐの机で、引き揚げ会社の社長が電話をしていた。こちらを見ると、受話器を耳に当てたまま、手のひらで奥を示した。奥の窓際に、もう一つ机がある。

汐見さんは、その机で紙の束を揃えていた。

細かい数字の並んだ記録用紙が、机いっぱいに広がっている。汐見さんは、わたしの抱えた箱に目を留めると、用紙を手早く一つにまとめた。まとめた束を窓枠に載せて、机の上を空けた。それから、こちらへ両手を伸ばした。

箱を渡した。汐見さんは、箱を空いた机の真ん中に置いた。

「鳴海さん。重かったでしょう」

「七冊です。重さは、書類の重さです」

汐見さんは、箱の蓋を開けた。綴りの背表紙には、年が書いてある。汐見さんは胸ポケットから、手書きの一覧を出した。罫線の入った紙に、年が縦に並んでいる。一冊ずつ背表紙を指で押さえて、一覧の年と照らしていく。

わたしは鞄から、持ち出しの記録の用紙を出した。書庫から書類を出すときは、誰が、何を、いつまで預かるかを書いて、預かった人に署名をもらう。

「こちらに、署名をお願いします。返却の予定日は、空けておいてください。決まったら、わたしが書きます」

汐見さんは一覧を照らす手を止めずに、片手でペンを取った。署名をして、用紙をこちらへ戻した。整った字だった。

一覧の最後の年まで照らし終えて、汐見さんは顔を上げた。

「揃ってます」

汐見さんとは、事故の現場で、二度会ったことがある。

一度目は貨物船の座礁で、二度目は漁船の火災だった。汐見さんは国の調査で、わたしは保険の査定で来ていた。立場が違うので、話したのは、どちらも数分ずつだ。どこまで船に近づいてよいか、何を触ってはいけないか。その確認だけだった。

数年前、腕のいい調査官が突然辞めた、という話を、業界の集まりで聞いた。名前は出なかった。先週、汐見さんから会社に電話をもらって、あの話はこの人のことだったのだと、結びついた。

辞めた理由は知らない。訊くつもりもない。保険の仕事は、訊かれたくないことを訊かずに、書類で確かめられることだけで書く仕事だ。

汐見さんは、二度の現場のことには触れなかった。覚えているのかどうかは、わたしには分からない。確かめるつもりもなかった。

用は済んだ、と思った。綴りを渡し、署名をもらった。あとは会社に戻って、監査の一件に取りかかればいい。

汐見さんは箱の蓋を閉じて、立ち上がった。

「綴りを開く前に、少し、外を見ていただけますか」

理由は言わなかった。上着を羽織って、扉のほうへ歩いていく。

ついていった。

外階段の上から、ドックの全体が見えた。

船は、ドックの底に据わっていた。鋼の船体で、マストはまだ無い。甲板の縁から下、船の横腹にあたる所を、作業員が二人、高圧洗浄機で洗っている。

汐見さんが、階段を下りながら言った。

「今日は、外板を洗って、厚さを測る日です」

外板というのは、船体の外側を覆っている鋼の板だ。船の皮にあたる。保険の仕事で、損傷の見積書には何度も出てくる語だ。

噴き付ける水の筋が往復するたびに、外板の泥と付着物が削げていく。削げた跡に、錆の地肌がのぞく。古い塗膜が、ところどころに島のように残っていて、色がまだらになっていた。

洗い終えた所には、チョークで格子が引いてある。別の作業員が、格子の交点に円筒形の探触子を押し当てていた。線の先の計器を見て、数字を小さな札に書き、札を交点の脇に貼っていく。

「超音波の厚さ計です。片側から当てて、板の厚さを測ります」

汐見さんの説明は、それだけだった。

厚さが減っていれば、その分、板は弱くなっている。わたしの仕事でも、厚さの計測表は修繕の見積もりの根拠になる。札の数字を、目で一つ拾った。読む前に、汐見さんが手で制した。

「そちらは、風下です」

汐見さんは、船首寄りの、水しぶきの届かない場所を指さした。そこに立った。さっきまでいた場所の地面は、黒く濡れていた。

汐見さんは船尾のほうへ歩いていった。ついていくと、船尾の甲板の縁で、立ち止まった。

甲板の縁には、腰の高さほどの低い壁が立ち上がっている。舷墻（げんしょう）という。甲板から人や物が落ちないための壁だ。その外側に、木の板が一枚、取り付けてあった。

洗い終えたばかりらしい。板の表面は濡れて、黒っぽく光っている。浮き彫りの文字が三つ並んでいて、その溝に、まだ水が残っていた。

船の名前は、法律で外板に記すことになっている。船尾の外板にも、塗膜の剥げた白い文字の跡があった。この板は、それとは別の、名を掲げるための飾りの板だ。練習船が、こういう板を付けることがある。

汐見さんは、板の前で立ち止まった。何も指さず、わたしのほうも見ずに、待っていた。

文字を読んだ。

暁凪丸。

「……あかつき、なぎ、で、いいんでしょうか」

「あかつきなぎまる、です」

暁凪丸（あかつきなぎまる）。

請求ファイルの表紙に書いてあった名前だ。書類の上では、何百回も見た。この三文字を実物で読むのは、初めてだった。

汐見さんは、板から目を離して、こちらを向いた。

「鳴海さん。お願いがあります」

「はい」

「綴りを全部読み終えるまで、今日はここに居ていただけませんか。持ち出していただいた書類を、持ち主のいない所で開きたくないので」

書庫から出した書類は、わたしの責任で預けている。持ち主のいない所で開きたくない、というのは、わたしが書類を人に預けない理由と、同じだった。

腕時計を見た。十時二十分。

監査の件は、ノートパソコンでここでもできる。リポジトリは手元にある。

「承知しました。夕方まででしたら」

汐見さんは頷いて、事務所の階段のほうへ戻っていった。

事務所に戻ると、汐見さんは綴りを机に広げた。一冊目の表紙を開き、目次の頁から読み始めている。

わたしは、隣の空いた机を借りた。ノートパソコンを開いた。

査定ツールは、うちの部の社内のツールだ。Go で書いてある。部の若手が書き始めて、三年前に異動した。それからは、わたしが保っている。独学だが、読めるし直せる。

ツールが計算するのは、保険で払う額だ。船が事故で傷めば、修繕の見積もりが出る。そこから、新旧交換控除と、免責額を引く。

新旧交換控除は、古い部品を新品に替えた分を差し引く控除だ。二十年使った鋼板を新しい鋼板に替えれば、船は事故の前より良くなる。その良くなった分は、保険では払わない。差し引く率は、船齢、つまり船ができてから満何年たったかの区分で決まる。免責額は、契約で決めた、船主が自分で負担する額だ。

去年の一件を、もう一度並べた。

差は三十万円。修繕費のちょうど一割だ。最初にそれを見たとき、率の表そのものが変わったのだと読んだ。

三十三件。上が新しく、下が古い。このツールのリポジトリには、手順書もメモも一緒に入れてある。だから、計算に関わらない件名が多い。

この一週間、これを上から読んできた。件名を見て、計算に触れていそうなものは差分を開く。

怪しいと読んだのは、二つだった。

一つは、b38a9ac の料率表の改定。控除の率の表の値を、今年の改定に合わせて書き換えている。差が修繕費のちょうど一割なら、率が変わったと読むのが筋だった。

二つ目は、08381dc の端数処理の統一。支払額の千円未満を切り捨てる。支払額の計算に、直に触れている。

二つとも、今の main の上から git revert --no-commit で戻して、去年の一件を流した。戻した版で、数字が直るかを見るためだ。

料率表を戻した。二百二十万円。

戻しを取り消して、端数処理を戻した。二百二十万円。

一円も変わらなかった。

読みが外れたのは、読み方が足りなかったからだ。そう考えた。差分をもっと丁寧に読めば、分かるはずだ。十八年、修繕の見積書と請求書の不備を、目で見つけてきた。見積書の一行に、前の年の単価が残っているのを見つける。それがわたしの仕事だ。

これまでのやり方は、読んで怪しいものから試す、というものだった。それで二回試して、二回とも外れた。

第2幕: FAIL の続き

昼になった。

洗浄機の唸りが止まった。作業員たちは、ドックの脇の詰所へ引き上げていった。急に静かになって、風が窓を叩く音だけが残った。

汐見さんは、机の端に自分の弁当を広げた。わたしは、途中のコンビニで買ったおにぎりを、鞄から出した。

おにぎりの包みを片手で剥がしながら、もう片方の手で差分を送った。料率表と端数処理のほかに、まだ読んでいない差分がある。

「仕事の、ですか」

汐見さんの声で、手が止まった。汐見さんは箸を持ったまま、わたしの画面を見ていた。差分の、赤と緑の行が並んでいる。

一瞬、言い淀んだ。それから、正確に言うことにした。

「監査の準備です。去年わたしが出した査定の報告書を、今のツールで計算し直しています。十件のうち一件だけ、支払額が合いません。報告書が二百五十万円、今のツールが二百二十万円。差は三十万円です」

汐見さんは、黙って聞いていた。箸は止まっていた。

「この一年の変更を読んで、怪しいものを二つ戻しました。どちらでも変わりませんでした。今は、三つ目を探しています」

汐見さんは、少しだけ間を置いて、訊いた。

「報告書を出した時点の版は、分かりますか」

「タグを付けてあります。report-2025 です。その版で流すと、二百五十万円が出ます。報告書と一致します。それは、先週、確かめました」

確かめてあることは、確かめてあると言える。それだけは、言えた。

汐見さんは頷いた。箸を置いて、綴りの次の頁を開いた。

わたしは、おにぎりを置いた。

三つ目を、差分から選んだ。

1714006 parseYM を parseYearMonth に改名する（途中）。

parseYM は、竣工の年月や事故日の文字列から、年と月を取り出す関数だ。日付の扱いに触れている。それに、件名に「途中」とある。途中のまま入った変更は、書類でも、いちばん危ない。

今度は、戻すのをやめた。1714006 を今の main の上から戻そうとすると、後の変更とぶつかる。同じ関数の名前を、次のコミットが書き換えているからだ。

そこで、やり方を変えた。1714006 と、その一つ前の e8cfc8f を、それぞれチェックアウトする。それぞれで go test ./... を流す。既存のテストが一つ前で通って、1714006 で落ちれば、そこで何かが変わった印になる。

一つ前を流した。ok。

1714006 を流した。FAIL。

身を乗り出していた。左手が、机に置いた去年の報告書の、支払額の行を指でなぞっていた。

これだ、と思った。日付の読み取りを変えて、途中で止まったコミット。船齢が変わって、控除の率が変わる。筋が通る。

このコミットは、関数の名前を parseYearMonth に変えていた。でも、呼び出している側は、古い名前の parseYM のままだった。だから、ビルドが通らない。テストは、一つも走っていない。FAIL は、テストが落ちたという意味ではなかった。ビルドができなかったという意味だった。

次のコミット、0113b6b で、呼び出し側が新しい名前に置き換えてある。一つのコミットの中だけで、名前の変更が途中だった。

背もたれに、体を戻した。

FAIL の一語で、決めかけていた。確かめたのは、FAIL が出たことだけだ。去年の一件の数字が、このコミットで変わったことは、何も確かめていない。

保険の仕事でも、似たことがあった。若い頃、修理業者の請求書を、署名と社印の欄だけ見て通しかけた。中身の明細を見たのは、課長に戻されてからだ。欄が埋まっていることと、中身が正しいことは、違う。

おにぎりの残りを、食べた。味は、あまりしなかった。

食べ終えて、画面に戻った。

怪しいものは、もう残っていなかった。

読んで怪しいと思ったのは、三つ。料率表、端数処理、改名。三つとも違った。

残りの三十件を、一つずつ前後で試すか。一件に数分。来週の締め切りには、間に合わなくはない。でも、途中にビルドのできない版が、まだあるかもしれない。そのたびに FAIL の続きを確かめるのか。

それとも、差分を読み直すか。

そこで、引っかかった。三回、読んで選んで、三回とも外れた。

去年の報告書を、裏返して机に伏せた。

git log --oneline の一覧を、画面の上から下まで、ゆっくり一度スクロールした。

一番下が、去年の版だ。report-2025。そこでは、去年の一件が合う。先週、確かめた。

一番上が、今の版だ。main。そこでは、合わない。

その間に、三十三件のコミットが、一本の列で並んでいる。枝分かれはない。

どこかで一度、合わなくなった。途中で一度直って、また壊れた、ということもありうる。ただ、そういう修正の件名は一覧に無い。一度壊れて、そのまま戻っていない、と置いてみる。

だとすると、ある版で去年の一件が合うなら、それより下の版は、全部合う。合わないなら、それより上の版は、全部合わない。合うと合わないの境目は、一本の列の中に、一つしかない。この置き方が崩れていたら、半分ずつの探し方は、境目のどれか一つを返すだけになる。

だから、真ん中の版を一つ試せば、半分が要らなくなる。

真ん中で合えば、境目は真ん中より上にある。下の半分は、もう見なくていい。合わなければ、境目は真ん中かそれより下にある。上の半分は見なくていい。

	"os/exec"

func main() {
	if exec.Command("go", "build", "./...").Run() != nil {
		os.Exit(125)
	}
	os.WriteFile("lastyear_test.go", lastYearTest, 0o644)
	err := exec.Command("go", "test", "-count=1", "-run", "TestLastYearReport", ".").Run()

ビルドが通れば、去年の一件のテストを作業ツリーに置いて、go test を流す。終わったらすぐに消す。チェックアウトされた版に、余計なファイルを残したまま次の版へ進まないためだ。テストが落ちれば 1。壊れている、という答えだ。

さっきのスクリプトとやっていることの違いは、最初の go build で 125 を返す段があるかどうか、それだけだ。

出口が三つになった。確かめられない版は、良いの側にも悪いの側にも入らない。

判定プログラムは、リポジトリの外でビルドして、外に置いた。

公式のドキュメント（git-bisect の Bisect run の節）の例でも、判定のスクリプトはリポジトリの外に置くよう勧めている。理由は、読めば分かった。bisect は、古い版を次々にチェックアウトする。古い版に切り替わると、中に置いた判定のファイルは消えたり、古い中身に戻ったりする。判定が版ごとに変わったら、良い悪いの物差しが揺れる。

入渠（にゅうきょ）は、船をドックに入れることだ。水から上げて、船体の検査や修理をする。

改修の記録があること自体は、保険の人間には、ありふれている。

func yearsBetween(from, to string) int {
	fy, fm := parseYearMonth(from)
	ty, tm := parseYearMonth(to)
	years := ty - fy
	if tm < fm {
		years--
	}
	return years
}

去年の一件を流した。二百五十万円。報告書の数字と、一円まで一致した。

直して変わるのは、どの案件か。保険の書類の書き方で、条件を付けて考えた。

直した一段が効くのは、事故の月が竣工の月より前のときだけだ。そのときだけ、船齢が一年減る。さらに、一年減ったことで船齢の区分が変わる案件でなければ、控除の率は変わらない。支払額も変わらない。

だから、直す前と後で支払額が変わるのは、事故の月が竣工の月より前で、しかも船齢が区分の境目にかかる案件だけだ。

それを、代表の案件をテストに流して確かめた。事故の月が竣工の月と同じ案件では、直す前も後も同じ額が出た。月が後の案件も、同じだった。月が前でも、船齢が区分の境目から離れている案件は、やはり同じ額だった。挙動が変わったのは、去年の一件のような、境目にかかる案件だけだった。

比べたのは、Assess の返す支払額だ。bisect の出力も、判定の回数も、処理の速さも、査定の結果ではないので外した。

判定プログラムと bisect は、製品のコードに、一行も足していない。判定プログラムはリポジトリの外にある。去年の一件のテストも、判定のあいだは持ち込んで、終わるたびに消していた。製品のファイルに差分がないことを、git status で確かめた。

それから、去年の一件のテストを、TestLastYearReport のまま、製品のテストに加えた。判定に使ったものを、そのまま入れた。次に誰かが船齢の計算をまとめ直しても、この一件が落ちる。

ここで、一つ気になった。

今日は、運が良かったのではないか。ビルドのできない版が、原因の be066e0 から離れていた。1714006 と be066e0 の間には、良い版が何件か挟まっていた。

もし、ビルドのできない版が、原因のすぐ隣にあったら。

条件を変えて確かめるのは、査定の癖だ。手元のノートパソコンで、同じ形の小さな履歴を作った。良い版から、計算に触れないコミットを何件か積む。ビルドのできない改名の途中のコミットを置く。そのすぐ次に、船齢をまとめるコミットを置く。このコミットは、Assess の中の古い名前の呼び出しを yearsBetween へ置き換えるので、ここでビルドは通る。改名の続きはその後にして、残りを積む。十二件の小さな履歴だ。

判定は四回。最後に、候補が二つ並んで止まった。

一つは改名の途中のコミットで、もう一つは船齢をまとめるコミットだ。最初に悪くなったのは、このどちらかだ、と書いてある。

理屈をたどった。改名の途中の版では、ビルドができない。判定プログラムは、分からないと答えた。船齢をまとめた版では、去年の一件が合わない。改名の前の版では、合う。

だとすると、悪くなったのは、改名の途中の版かもしれない。その版がビルドできたなら、そこでもう合わなくなっていた可能性を、誰も否定できない。だから、二つまでしか絞れない。

判定プログラムは、嘘をつかずに、分からないと答えた。その結果、二つまで絞って止まった。分からない版を悪いと言わせていたら、一つに絞った顔で、改名の途中のほうを返していたはずだ。昼に書いた、わたしの最初の判定のように。

そこから先は、人が見る。改名の途中の版の呼び出し側だけ直して、そこで試す。あるいは、二つの差分を見比べる。二つなら、見比べられる。

汐見さんに、画面を見せた。

野帳の写し

  • 見たこと: 鳴海さんの件: report-2025 で去年の一件は合います。main で合いません。料率表・端数処理を戻しても変わりません。1714006 はビルドできません。判定プログラムで6回、be066e0 が残りました。外板: 船尾側の左舷を洗い、測点の半分を測りました
  • 思ったこと: 料率表が原因（外れでした）。端数処理が原因（外れでした）。改名の途中のコミットが原因（外れでした。ビルドできないだけでした）
  • 調べ方: git bisect（git bisect run）。良い版と悪い版の間のコミットの並びを二分探索し、判定の終了コードで、最初に悪くなったコミットを特定します
  • 固定したもの: 判定プログラム（リポジトリの外。0 良い・1 壊れている・125 調べられない）と git bisect log を残しました。去年の一件を TestLastYearReport として製品のテストに加えました
  • 変えていないもの: 判定プログラムと bisect は、製品のコードに触れていません。直したあとも、事故の月が竣工の月と同じか後の案件、月が前でも船齢の区分が変わらない案件では、支払額が直す前と一致します。bisect の出力・判定の回数・所要時間は、照合から外しています
  • まだ見ていない所: ビルドできない版が原因のすぐ隣にある場合（2つまでしか絞れません）。判定が揺れる場合。持ち込んだテストのほうが古い版でビルドできない場合（今回は Claim と Assess の形が全版で同じでした）。読めない測点（チョークの丸）は、塗膜を落として測り直します
  • 船について: （記録）沈没の4年前の入渠で、甲板上に構造物を増設する改修が行われています
