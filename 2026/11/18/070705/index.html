切断計画の夜間バッチが停止しました。

送り主は、俺が書いた監視だ。夜間バッチが止まると、携帯にこれを送ってくる。二年前に自分で仕込んだ。仕込んだときは、こんなに何度も読むことになるとは思っていなかった。

午前二時十四分。一晩目も二晩目も、だいたい同じ時刻だった。

朝までに切断計画が出ないと、工場の切断機が止まる。職人が、切る板の前で待つことになる。三朝続けて、俺が事務所で計画の一部を手で作って間に合わせた。親父には言っていない。

吐いた息が、携帯の画面の上で白く広がった。

遠くで、漁船のエンジンがかかった。海の匂いが、霜の匂いに混じって流れてくる。

今日ここに来たのは、仕事のためじゃない。この船を造ったのは、祖父の造船所だ。俺が生まれる前の話で、祖父はもういない。祖父が竜骨を据えた日の写真が一枚だけ家に残っていて、今朝、それを胸ポケットに入れてきた。

胸ポケットの上から、写真の角を指で一度確かめた。

声は低く、短かった。

「槙田造船の、槙田です。今日、竜骨の検査があると、港で聞いて」

それだけでは用件にならない。分かっていて、言葉が続かなかった。

「この船、うちの祖父が造ったんです。……竜骨を、見せてもらえませんか。作業の邪魔はしないので」

順番がめちゃくちゃだった。言い直そうとして、やめた。

今、目の前にあるのは、それと同じものの、錆びた底だ。

汐見さんは俺の横を抜けて、底への階段に足をかけた。底では、作業員たちが集まり始めていた。俺は線の外から、それを見ていることになった。

作業員は五、六人いた。汐見さんは、その輪の真ん中で、今日の手順を短く伝えていた。上にいる俺にも、声はそのまま届いた。

携帯の時刻を見た。六時四十分。

楔の音を聞いているうちに、口が勝手に開いていた。

「うち、切断計画の夜間バッチがあって」

汐見さんが聞いているのかどうか、確かめなかった。

「毎晩、翌日に切る部材の一覧を読んで、どの鋼板のどこから切るかを出すんです。それが、三晩続けて止まってる」

部材表というのは、船体のブロックごとに、切り出す部材を一行ずつ並べた表だ。部材番号、長さ、それと、どの鋼板から切るかの指定。俺のツールはそれを読み込んで、鋼板の上に部材を割り付け、切る順番を決める。紙とスプレッドシートでやっていたのを、二年前に置き換えた。Go で書いて、二年、一人で面倒を見てきた。

先月、フェリーの船体ブロックを受注した。その部材表が、約800行あった。それを流した晩から、止まるようになった。

「一晩目は、表をスプレッドシートで開いて、上から一行ずつ見ました。長さの桁、鋼板の番号、部材番号の重複」

これまでの不具合は、全部それだった。長さの桁を一つ打ち間違えた行。在庫に無い鋼板の番号を書いた行。一行ずつ見ていけば、どこかで見つかった。

「二晩目は、長さで並べ替えて、極端に長いのと短いのを探しました。鋼板の番号で並べ替えて、在庫に無い番号も探した。無かった」

三晩目は、panic のメッセージの数字を疑った。capacity 12000。行の数か何かの上限だと思って、行数を数え直した。800行。12000 とは、何の関係も無かった。

「一行ずつ、見たんです。どの行も、まともだった」

だから、どこが悪いのか分からない。そこまで言って、口を閉じた。

楔の音が止まっていた。汐見さんは鉛筆を止めて、こちらを見上げた。

「小さい部材表だと落ちない、というのは、どれくらいの小ささまでですか」

答えようとして、口を開けた。

閉じた。

流したことがあるのは、800行のこの表と、これまでの受注の表だけだ。これまでのは、多くて二百行くらい。その間の大きさは、流したことが無い。

落ちる表と落ちない表の間を、俺は一度も試していない。

「……分かりません」

汐見さんは、それには何も返さなかった。作業員の一人が手を上げた。盤木が外れた合図らしい。汐見さんは足もとの台車を引いて、区画の下へ歩いていった。

俺は軽トラックに戻った。助手席に置いてきた鞄を、引っ張り出す。

本当は、作業が始まる前に竜骨だけ見て、事務所に戻るつもりだった。

黄色い線の外に、木箱が一つ置いてあった。道具が入っていたらしい空の箱だ。その上に、ノートパソコンを置いた。

// Plan は部材を鋼板に割り付ける。夜間バッチと、事務所の画面の試しの機能から呼ばれる。
// どの板にも載らない部材は、ここでは切り出さない。
func Plan(parts []Part, plates []Plate) []Cut {
	slots := make([]*slot, len(plates))
	byID := map[string]*slot{}
	for i, pl := range plates {
		slots[i] = &slot{plate: pl, marks: make([]byte, pl.Length)}
		byID[pl.ID] = slots[i]
	}

	var cuts []Cut
	var auto []Part

	// 指定のある部材を先に、指定の鋼板に表の順で並べる
	for _, p := range parts {
		s := byID[p.Plate]
		if s == nil || s.used+p.Length > s.plate.Length {
			auto = append(auto, p) // 指定が無い（載らない）部材は、あとで自動に回す
			continue
		}
		cuts = append(cuts, Cut{Part: p.ID, Plate: s.plate.ID, Start: s.used, End: s.used + p.Length})
		s.used += p.Length
		next := s.marks[s.used : s.used+1] // 次の切り始めの位置に印を付ける
		next[0] = 1
	}

	// 指定の無い部材を、余りが残る鋼板に先頭から詰める
	for _, p := range auto {
		for _, s := range slots {
			if s.used+p.Length < s.plate.Length {
				cuts = append(cuts, Cut{Part: p.ID, Plate: s.plate.ID, Start: s.used, End: s.used + p.Length})
				s.used += p.Length
				next := s.marks[s.used : s.used+1]
				next[0] = 1
				break
			}
		}
	}
	return cuts
}

鋼板は、長さだけを持つ帯として扱っている。本物の板は縦横があるが、このツールが扱うのは、帯状の板から長さで切り出す部材だけだ。部材の長さは、切りしろ込み。切りしろというのは、切断で溶けて消える幅のことで、その分を足した長さを表に書く約束にしている。

部材表の行に鋼板の指定があれば、その部材は指定の鋼板に、表の順で並べる。板取り――一枚の板からどの部材をどう切り出すかの段取り――を、職人が歩留まりのために決めた指定だ。歩留まりは、板のうち、部材として使えた分の割合をいう。指定の無い部材は、在庫の鋼板に先頭から詰める。

指定を先にしたのは、職人の板取りを崩したくなかったからだ。二年間、毎晩、これで動いてきた。既存のテストも、小さい部材表で通っている。

鋼板ごとに、使った長さの used と、切り始めの印の marks を持っている。部材を一つ置くたびに used を足し、次の切り始めの位置に印を付ける。どこが悪いのかは、読み返しても分からなかった。

在庫の鋼板の一覧、plates.csv も開いた。鋼板の番号と長さが、百行並んでいる。どれも12000。うちが仕入れている定尺の板だ。

汐見さんの問いが、頭に残っていた。落ちる表と落ちない表の間。

部材表をスプレッドシートで開いて、上下に割った。上の400行と、下の400行。それぞれを CSV に書き出した。事務所の画面には、表を試しに流す機能を付けてある。夜間バッチと同じ Plan を呼ぶ。それをノートパソコンの上で立ち上げた。

どちらかの半分で落ちる、と思っていた。落ちたほうを、また半分にすればいい。それをまた半分に。800行なら、九回か十回で一行になる。

前半を流した。

落ちない。

後半を流した。

落ちない。

画面を見たまま、しばらく動けなかった。

もう一度、前半を流した。落ちない。後半を流した。落ちない。

半分が大きすぎるのか。今度は四つに割った。200行ずつ。一つ目、二つ目、三つ目、四つ目。

四つとも、落ちなかった。

ノートパソコンの画面を、半分まで閉じかけた。指が蓋の縁にかかったところで、開き直した。携帯の時刻を見た。七時半。

一行の誤りなら、その行は、四つのどれかに入っている。その行が入った一つは、落ちるはずだ。どれも落ちない。だとすると、一行じゃない。

一行じゃないなら、大きさで落ちているのか。panic のメッセージの、capacity という語が浮かんだ。行が多すぎて、どこかの容れ物が溢れたのか。だったら、どの行も悪くない。表を分けて流すしかない。でも、分けて流せば割り付けが変わる。歩留まりが下がる。職人が指定した板取りも崩れる。

それとも、もっと細かく割り続けるか。百行、五十行。でも、半分でも落ちないものが、細かくして落ちるとは思えなかった。

どっちにも進めなかった。

キーボードから手を離して、上着のポケットに突っ込んだ。指先が、胸ポケットの写真の角に触れた。

蓋は開けたまま、木箱を離れて黄色い線の際まで歩いた。手が止まったときは、目を別のものに置く。仕事場で、いつもそうしている。

事務所には、今日は戻らない。そう決めた。ここで続ける。

二つ目の区画で、作業員が楔を叩いていた。抜いた楔を脇に置き、ジャッキで木の層との間に隙間を作る。盤木が一つ、また一つと、竜骨の下から外れていく。

船は、少しも動かなかった。

外れた区画の前と後ろに、盤木の列が残っている。船は、その上にそのまま座っていた。

汐見さんが、台車に仰向けに寝た。足で床を押して、外れた区画の下へ滑り込んでいく。台車の車輪が、コンクリートの上で小さく鳴った。灯りが、竜骨の底を下から照らした。錆の色が、そこだけ赤茶に浮かぶ。スクレーパーで付着物を削る、硬い音がした。何度か、場所を変えて。

しばらくして、台車ごと出てきた。汐見さんは起き上がって、野帳に一行書いた。何を書いたのかは、ここからは見えない。書く手の動きだけが見えた。

作業員が、外した盤木を据え直していく。前と同じ位置ではなかった。少しずらした所に置いている。それから、次の区画の盤木のほうへ移っていった。

近くを通りかかった作業員の一人に、小声で訊いた。

「なんで、全部いっぺんに外さないんですか」

全部外したら船を支えきれない、と作業員は言った。残っている盤木で支えているのだという。それだけ言って、楔を拾いに行った。

木箱の上の画面を、振り返った。

俺は、表を割るたびに、切り出したほうだけを流していた。前半だけ。後半だけ。四分の一だけ。

四分の一を一つ外して、残りの四分の三を流したことは、無い。

落ちなかった四分の一には、悪い行が無い。そう決めていた。でも、それは確かめていない。確かめたのは、その四分の一だけでは落ちない、ということだけだ。

盤木の区画を外しても、船は残りの盤木に座っている。外した所を見ているあいだ、船を支えているのは残したほうだ。

汐見さんたちは、竜骨を見るために盤木を外している。何かを絞り込むためじゃない。それは分かっている。ただ、形だけ借りて考えた。外したほうじゃなく、残したほうに、船はある。

木箱に戻った。

スプレッドシートで、一つ目の四分の一を消した。残りは600行。書き出して、流した。

落ちた。

画面に、あの panic が出ていた。三晩、メールで読んだのと同じ文字だった。

二つ目の四分の一を消した残りを作って、流した。落ちない。四つ目を消した残りを流した。また落ちた。

どの四分の一を外すかで、落ちたり、落ちなかったりする。

木箱の前で、ここまでに流したものを一枚に書き出した。どこまでが確かめたことで、どこからが俺の思い込みだったのかを、分けておきたかった。

破線の札だけは、一度も確かめていなかった。外したほうではなく残したほうを流して、初めてそこに穴があると分かった。

落ちる600行が、手に入った。ここから先を、どう割ればいい。どこで止めればいい。それが分からなかった。手でこれを続けたら、一日かかる。

第3幕: 外しても落ちるうちは

小屋の窓は、内側から曇っていた。外側には、まだ霜の花が残っている。

十時を回った頃、汐見さんが小屋の前に出てきた。湯の入った器を両手で持っている。湯気が、器の縁で白く立っていた。

ノートパソコンを抱えて、そっちへ行った。

「一つ、訊いてもいいですか」

汐見さんは頷いた。

「さっき、盤木を五分の一ずつ外してましたよね。半分ずつじゃ駄目なんですか。半分なら、二回で終わる」

「半分外すと、残りの盤木では、船を支えきれません」

汐見さんは湯を一口飲んでから、続けた。

「残りが支えられる分だけを、外します。このドックでは、五分の一にしています」

それはそうだ、と思った。船を造る家で育って、そのくらいは分かる。

本題は、そっちじゃなかった。

画面を汐見さんに向けた。四分の一を外した600行が、落ちた結果が出ている。

// Outcome は判定の3値。
type Outcome int

const (
	Pass       Outcome = iota // 落ちない
	Fail                      // 例の panic と同じ壊れ方で落ちる
	Unresolved                // 別の壊れ方で落ちる
)

// stillFails は「この部分入力で、例の panic がまだ出るか」を返す関数を作る。
// 在庫の鋼板は、部分入力でも変えない。
func stillFails(plates []cutplan.Plate, want string) func([]cutplan.Part) Outcome {
	return judge(want, func(parts []cutplan.Part) { cutplan.Plan(parts, plates) })
}

// judge は、run を呼んで、起きたことを3値にする。run には Plan を包んだ関数を渡す。
func judge(want string, run func([]cutplan.Part)) func([]cutplan.Part) Outcome {
	return func(parts []cutplan.Part) (out Outcome) {
		defer func() {
			r := recover()
			if r == nil {
				return // 何も起きなければ Pass のまま
			}
			if e, ok := r.(runtime.Error); ok && e.Error() == want {
				out = Fail
				return
			}
			out = Unresolved // 別の壊れ方
		}()
		run(parts)
		return Pass
	}
}

この判定関数は、答えを三つに分ける。Pass は、落ちない。Fail は、例の panic と同じ壊れ方で落ちる。Unresolved は、落ちたが、別の壊れ方だった。汐見さんの言った「別の壊れ方」を、Fail と同じ箱に入れないためにある。ddmin が絞るのは Fail のときだけで、Unresolved は Pass と同じく、絞らない側に入れる。別の誤りの入力へ乗り換えないためだ。今回の800行では、Unresolved は一度も出なかった。

Plan が panic すると、ふつうはプログラムごと止まる。それを止めずに受けるのが recover だ。defer で登録した関数は、呼んだ関数が抜けるときに必ず走る。panic で抜けるときもだ。その中で recover を呼ぶと、panic の値を受け取って、止まらずに戻れる。何も起きていなければ nil が返る。

受け取った値が runtime.Error か、まず確かめる。runtime.Error は、範囲外の添字のような、実行時の誤りで Go が起こす panic の型だ。そのうえで、Error() の文字列が、元の800行で出たものと一字一句同じかを見る。同じなら Fail。どこかが違えば Unresolved。

文字列で比べるのには、前提がある。メッセージには 12000 という数字が入っている。だから、数字の違う同じ種類の誤りは、別物に数える。今回は、削るのは部材表だけで、在庫の鋼板の一覧は削らない。それなら、この数字が入力のせいで変わることはない、と考えた。在庫の板がどれも12000だから成り立つ前提で、長さの違う板が混じるなら、数字を除いて比べることになる。

Plan は、時計も乱数も読まない。同じ部分入力なら、何度呼んでも結果は揺れない。判定がぶれたら、要る行を要らないと見誤って捨てることになる。そこは最初に確かめておいた。

// ddmin は、test が Fail を返す入力 c を、どの1行を外しても Fail にならなくなるまで小さくする。
// logf には、各段の残りの行数と粒度 n と、何で絞ったかを出す。
func ddmin(c []cutplan.Part, test func([]cutplan.Part) Outcome, logf func(string, ...any)) []cutplan.Part {
	n := 2
	for len(c) >= 2 {
		subsets := split(c, n) // c を n 個にほぼ等分する（順序は保つ）
		reduced := false
		// 1. 部分集合だけで落ちるか
		for _, s := range subsets {
			if test(s) == Fail {
				logf("残り%4d行 n=%-3d 部分集合で落ちる -> %d行へ", len(c), n, len(s))
				c, n, reduced = s, 2, true
				break
			}
		}
		// 2. 部分集合を一つ外した残り（補集合）で落ちるか
		if !reduced {
			for i := range subsets {
				rest := complement(subsets, i)
				if test(rest) == Fail {
					logf("残り%4d行 n=%-3d 補集合で落ちる -> %d行へ", len(c), n, len(rest))
					c, n, reduced = rest, max(n-1, 2), true
					break
				}
			}
		}
		// 3. どれも落ちなければ、細かく割り直す。もう割れなければ終わり
		if !reduced {
			if n >= len(c) {
				logf("残り%4d行 n=%-3d どれも落ちない -> 終わり", len(c), n)
				break
			}
			logf("残り%4d行 n=%-3d どれも落ちない -> n=%d に割り直す", len(c), n, min(len(c), 2*n))
			n = min(len(c), 2*n)
		}
	}
	return c
}

コメントの言葉は、汐見さんの話のとおりにした。部分集合は、割ったうちの一部。補集合は、一部を外した残り。n は何個に割るかで、粒度と呼ぶ。split は c を n 個にほぼ等分し、complement は i 番目を外した残りを順序を保ってつなぐ。どちらも数行の関数だ。

書き終えて、汐見さんの三つが、コードのどこにあるかを指でなぞった。

1 の所では、一部だけで落ちれば、そこへ絞る。絞ったら、n を2に戻して、新しい入力を半分から割り直す。

2 の所では、一部を外した残りで落ちれば、残りへ絞る。このときは n を一つ減らして続ける。残りは、さっきまでの n 個のうち n−1 個からできている。だから、n−1 個に割れば、細かさをほぼ保ったまま次を試せる。ただし2より小さくはしない。

3 の所では、どちらでも落ちなければ、細かく割る。n を倍にする。ただし、行の数より大きくはしない。

一行まで減ったときを除けば、止まるのは、3 の中の n >= len(c) の一か所だけだ。そこを指で押さえて、なぜ必ず最小に届くのかを、一段ずつ確かめた。

止まるのは、一部でも残りでも落ちず、しかももう割れないときだけだ。

もう割れないのは、n が残りの行数に達したとき。そのとき、一部は一行ずつになっている。残りは、一行だけを外したものになっている。

その全部で落ちなかったから、止まる。だから止まったとき、どの一行を外しても、もう落ちない。

逆に、どこかで落ちれば、行は必ず減る。どこでも落ちなければ n が倍になるが、行の数を超えないので、行の減らない段も、何回か続けば必ず n >= len(c) に届く。行の数は有限だから、いつかは止まる。

どの要素を一つ取り除いても失敗しなくなる。この状態を 1-minimal と呼ぶ、と論文にあった。ddmin は、止まったときに必ずそこにいる。

Plan の呼び出し元を grep した。出てきたのは二か所。夜間バッチと、事務所の画面の試しの機能だ。どちらも Plan を通る。だから、ここ一か所を直せば、呼び出し側には手を入れなくていい。

このバグを踏まないのは、指定のある部材で、どの鋼板もちょうど使い切らない表すべてだ。直した一行は、使い切ったときにしか効かない。だから、それ以外の表では、直す前と同じ答えになるはずだ。その読みを、代表で確かめた。例の表から、B587 か B213 のどちらかを外した799行。小さい表。指定の無い部材だけの表。同じ板に指定が三つ載って、余りが1残る表。自動の割り付けで、板が埋まる一歩手前まで行く表。

比べたのは、Plan の戻り値だけだ。部材、鋼板、切り始め、切り終わり。ddmin のログと、流すのにかかった秒数は、外した。

もう一本のテストは、使い切る表のほうだ。800行の表と minimal.csv で、直す前は例の panic が出る。直した後は落ちずに、B213 を P39 の0から7000に、B587 を7000から12000に置く。変わるのは、ちょうど使い切る表だけだった。

ちょうど使い切った板は、職人がいちばん喜ぶ板だ。切れ端が一つも出ない。歩留まりのいい板ほど、俺のツールは落ちていた。

800行の部材表を、直したほうで流した。落ちなかった。

今夜のバッチは止まらない。

息を吐いた。白く広がって、すぐに消えた。

汐見さんは、作業員と一緒に、外した楔を道具箱に戻していた。片付けが始まっている。

俺は木箱の前で、チケットの下書きを開いた。分かったことと、まだ分からないことを、二つの段に分けて打った。

分かったほうの段は、こうなった。800行のうち、B213 と B587 の二行がそろうと落ちる。どちらか一行を外すと落ちない。原因は、指定の鋼板をちょうど使い切ったときに、次の切り始めの印を板の外に付けていたこと。直した後は、ちょうど使い切る表でも落ちない。そうでない代表の表では、答えが一つも動かなかった。

まだ分からないほうの段も、埋めた。ddmin は、最小の例を一つ返すだけだ。どちらか一方を外した799行が落ちないので、一行だけで落ちる行は無い。でも、別の二行や三行の組で落ちる誤りが、ほかに無いとは言えない。

それに、1-minimal は、いちばん小さいこと――大域最小――とは違う。一行ずつ外して落ちないことは確かめたが、二行以上を一度に外した組み合わせは試していない。全部の組み合わせを試すと、行の数を |c| として 2 の |c| 乗通りになる。800行では、とても試せない。

判定関数が見分けられない誤りもある。同じ文字列で落ちる、別の原因。それから、うちのツールは帯状の板しか扱っていない。縦横のある本物の板取りは、このツールの外だ。

今日の判定と ddmin が確かめたのは、この800行と、この判定関数の範囲までだ。

それから、名前だけ知っていた go test -fuzz を調べた。

Go には、1.18 から fuzzing が入っている。fuzzing は、自動で入力を作りながらテストを流して、落ちる入力を探す仕組みだ。落ちる入力が見つかると、それを縮める機能が付いている。どれだけ縮めるかは、-fuzzminimizetime で時間か回数を決める。既定は60秒だ。

縮め方は、ソースの src/internal/fuzz のコメントで確かめた。一つの []byte か string を、バイトの単位で縮める。末尾を切る。一バイトずつ消す。範囲を消す。読みやすい文字に置き換える。それと、縮めた候補を採るかどうかは、何かのエラーが出るかで決めていた。worker.go を読んだかぎり、エラーの種類は比べていない。読んだのは今の版のソースで、この先変わるかもしれない。

部材表を行で削るなら、行を単位にして、同じ壊れ方かを自分で決められる ddmin のほうが合う、と思った。バイトで縮めると、行の途中が切れる。切れた行は、別の誤りを起こしうる。種類の照合なら、fuzz の関数の中で同じ判定を使えば補える。補えないのは、バイトの単位で行の途中が切れることのほうだ。fuzz は、まだ誰も知らない落ちる入力を探すときの道具で、縮める機能はその付属だ。今回は、落ちる入力はもう手元にあった。

ddmin を自分で書いたのは、行を単位にしたかったからだ。同じ壊れ方かどうかを、自分で決めたかった。判定と合わせても、数十行で書けた。

野帳の写し

  • 見たこと: 竜骨を5区画に分け、盤木を外して全部見ました。槙田さんの件: 800行の部材表は毎回落ちます。前半・後半、4分の1ずつでは落ちません。ddmin で B213・B587（どちらも P39）の2行が残り、どちらか1行では落ちません
  • 思ったこと: 落ちるのは一行の誤り（外れでした。2行とも、一行としては正しい行でした）。行が多すぎて落ちる（外れでした。12000 は P39 の長さでした）
  • 調べ方: Delta Debugging（ddmin）。失敗を保ったまま入力を削り、どの要素を一つ外しても失敗しなくなる最小の入力を得ます
  • 固定したもの: 最小の失敗例の2行を testdata/minimal.csv に置き、再現テスト TestMinimalCase にしました（目的は再発防止）。判定関数と ddmin は、次に使えるよう残しました
  • 変えていないもの: 判定関数と ddmin は Plan を呼ぶだけで、製品のコードは変えていません。直したあとも、指定の鋼板をちょうど使い切らない部材表では、切り出す位置の一覧（部材・鋼板・始まり・終わり）が直す前と一致します。ddmin のログと、かかった時間は、比べる対象から外しました
  • まだ見ていない所: 別の組み合わせで落ちる誤り。1行だけで落ちる行はありませんが、ほかの最小例が無いとは言えません。同じ文字列で落ちる別の原因。縦横のある板取り
  • 船について: 竜骨に、凹み・擦り傷はありません。全長、5区画、盤木の下を含めて見ました
