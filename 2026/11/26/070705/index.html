第1幕: 窓の外の重り

客の船でだけ、出港前の朝に、私の保守している計算が遅い。契約で約束した応答時間を、先月の朝に何度も超えた。手元では、何度測っても速い。手元で見つけた遅い所を直して入れたが、本番の朝は変わらなかった。

運航管理室の窓際で、私は借りた端末の前に座っている。朝の便が出たあとで、部屋は少し静かになった。机の上には、紙で配られた月次の運用報告がある。

私の勤め先は、船舶設計事務所だ。週に四日、嘱託で通っている。保守しているのは、フェリー会社向けの載貨計算の API で、Go で書かれている。

載貨計算は、積み荷とタンクの中身から、船の重さと重心と傾きにくさを計算することだ。傾きにくさは GM という長さで表す。メタセンタ高さともいう。大きいほど、傾いても戻りやすい。

運航管理者は、出港の前に、その日の積み付けの条件を端末から送る。車両の重さ、旅客の数、各タンクの液面の高さ。API は、喫水と重心の高さと GM、それに傾けたときの戻る力の曲線を返す。戻る力の曲線を GZ 曲線と呼ぶ。運航管理者は、値が基準を満たすのを確かめてから、出港を許可する。

運用報告の表は、時間帯ごとに、平均と p99 を並べている。p99 は、遅いほうから百に一つの応答時間だ。契約の上限は 500 ミリ秒。七時台の p99 が 1.8 秒だった。昼の時間帯は、上限の下に収まっている。

報告に出るのは、エンドポイントごとの時間だけだ。計算の中のどこで時間を使っているかは、どの行にも書いていない。

客の船の測深表は、契約で社外に持ち出せない。測深表は、タンクの液面の高さから、中の液体の量を引く表だ。船の諸元も同じ扱いになっている。だから私は電車で二時間かけて、この港の客の事務所まで来た。私の手元にあるのは、事務所の検証用のサンプル船のデータだけだ。

古い空調が、天井の奥で鳴っている。無線が短く交信して、また黙った。窓の外で、かもめが一羽、手すりから飛んだ。

窓の外に港の水面がある。対岸の岸壁に、白い船体の帆船が係留されていた。乾ドックの外で、水に浮いている。甲板に、同じ大きさの四角い塊が、左右に分けて並んでいた。

重りだ。並べ方で分かった。傾斜試験の重りの置き方だった。調査官だった頃、何度も立ち会っている。

船の名前は、ここからは読めない。読めなくても、私はその船を知っていた。

第2幕: 線から外れる点

昼前、客の情報システムの担当に、昼の間だけ外すと断った。担当は、本番のデータは持ち出せませんから、と念を押した。私は頷いた。

岸壁は、風が弱かった。

船は、思っていたより低く見えた。乾ドックに据わっていた頃の写真を、保存基金の月報で見ていた。あの写真の船は、足場の上で高かった。今は水が船体の下半分を隠している。

目は、先に甲板の重りへ行った。塊の横腹に、白いペンキで番号が振ってある。右舷に四つ、左舷に四つ。それから、ハッチの口に立てた目盛り板へ行った。調査局にいた頃の目の順番だ。退官しても抜けない。

ハッチの中から、綱が一本、上がってきた。綱を片手で送りながら、人が上がってくる。束ねた黒髪と、日焼けした腕。首にタオル。作業つなぎの上半身を脱いで、腰で結んでいる。

汐見は、ハッチの縁に膝をついたところで、顔をこちらへ向けた。

「柘植さん」

一度だけ、そう呼んだ。私は軽く頭を下げた。汐見も同じくらい下げた。それで挨拶は済んだ。

汐見は作業員のほうを向いた。

「三番を、左舷へ。四メートル二十、確認します」

最後の数字は、綱の長さだった。手の中の綱を、目盛りの付いた所まで送って読み上げている。読み終えると、汐見はハッチの中へ戻っていった。

手伝ってください、とは言われなかった。試験の最中なのだ。私は乗り込まずに、岸壁の端に立った。立ち会いを頼まれていない。

二十年ほど前、この船が沈んだあとで、私は調査局のチームにいた。この船の復原性を計算したのは、私だ。復原性は、傾いた船が元に戻ろうとする性質のことだ。船には触れなかった。船は海の底にあった。図面と完成時の資料から、計算で組み立てた。

訓練生への聞き取りの記録も読んだ。どこで寝て、何を食べていたか。そういう記録だった。読んだ、というだけだ。

汐見が局を辞めるとき、辞表を受け取ったのは私だった。

作業員が三人がかりで、重りを一つ、右舷から左舷へ移した。

船が、ゆっくり傾いた。目で見て分かるかどうかの傾きだ。マストの先が、空の中でわずかに寄った。

ハッチの口の目盛り板の上で、振り子の先が揺れている。止まりきらない。振り子のおもりは、ハッチの底の桶に沈めてある。桶の液が揺れを吸って、振れが少しずつ小さくなっていった。

私は手帳を開いていた。開いたのは自分の手だ。岸壁から目盛りを読み、万年筆で数字を一つ書いた。百四十八ミリ。

ハッチの中から、汐見の声が上がってきた。

「百四十八」

同じ数字だった。

頼まれてもいないのに、読んでいた。私は万年筆のキャップを閉めずに持ったまま、次の重りが動くのを待った。

重りの列の向こう、甲板の後ろ寄りに、構造物が一つ載っている。後から載せたものだ。私の覚えている図面には、あれは無かった。目がそこで一度止まり、目盛り板へ戻った。

点を打つ

昼過ぎ、汐見がハッチの横から、こちらへ手を一度上げた。言葉は無かった。私は舷梯を上がった。

ハッチの横に、板が立てかけてある。板に記録用紙が挟んであった。複写式の用紙だ。

傾斜試験は、船の上で、重さの分かっている重りを横に動かし、船がどれだけ傾くかを測る試験だ。傾き方から、船の重心の高さと GM を出す。計算ではなく、実物から求める。

汐見の手順は、移動のたびに同じだった。作業員が重りから離れるのを待つ。振り子が桶の中で止まるのを待つ。目盛りを読む。記録用紙の方眼に、点を一つ打つ。

横軸は、重りの移動で生じたモーメントだ。重りの重さに、動かした距離を掛けたもの。縦軸は、振れを振り子の長さで割ったもの。傾きの正接にあたる。ほかの力が働いていなければ、点は一直線に並ぶ。

汐見は一度だけ作業員に言った。

「舫いは張らないでください。緩めたままで」

私は頷いた。知っていることだった。船を綱で縛ると、船は自分で傾かない。

用紙の右上に「設計値」の欄がある。1.20 メートルと書いてあった。完成時の復原性の資料から写した GM だ。私はそれを一度見て、ただの設計値として読んだ。

四つ目の点が打たれた。四つとも、きれいに一本の線に乗っている。

計算と合っている、と私は思った。

ところが、線の傾きから出る GM は 1.04 メートルほどで、設計値より小さかった。4 トンの重りを 6 メートル動かして、振れが 150 ミリ。設計値の GM なら、130 ミリ前後で済むはずの移動だ。振り子は 4.2 メートルあるから、傾きは片舷で 2 度ほどだ。GM は頭の中で式を回して出した。船の教科書に載っている式だ。

午後、風が出てきた。

旗が鳴りはじめた。五つ目の点と六つ目の点が、線から外れた。

汐見は、外れた点を消さなかった。

そのまま、甲板を歩きはじめた。係留の綱を一本ずつ見て回る。船首側の一本が、潮で張っていた。汐見はそれを指さし、作業員に緩めさせた。

次に、板から別の紙をめくった。朝、全部のタンクを測深した記録だ。測深は、タンクに巻尺を下ろして液面の高さを測ることをいう。傾斜試験の前には、タンクを空か満水にしておく。中途半端な液面だと、傾いたときに液が低い側へ寄り、傾きを大きく見せる。

汐見はタンクの口を一つずつ開けて、巻尺を下ろした。巻尺を引き上げ、濡れた目盛りを読む。四つ目のタンクで、手が止まった。

「二番の右。朝より二十ミリ上がっています」

雨水だろう、と作業員の一人が言った。汐見は担当を呼んで、抜かせた。

私は自分の手帳を見た。開いた頁の上のほうに、私の字で「測深表」と書いてある。私の仕事の言葉と、汐見の手の言葉が、同じ字だった。私は何も言わずに、頁を戻した。

最後に、汐見は旗を見上げた。旗は、まだ鳴っていた。

私は言った。

「設計値と食い違う分は、測定のほうに残った誤りだと思う。綱とタンクを潰して、まだ風が残っている。そういうことか」

調査官の頃の訊き方だった。自分の見立てを先に言い、それを確かめる。

汐見は記録用紙から目を上げなかった。

「測定の誤りは、潰した分だけ潰しました。綱が一本、タンクが一つです。風は、まだです」

どちらが正しいかは、言わなかった。

汐見は作業員たちのほうを向いた。

「今日はここまでにします。明日の夜明け、風の無いうちに、最初の移動からやり直します」

作業が止まった。

計算は、完成時の資料の値から出している。資料は正しい。風さえ無ければ、明日は設計値に近い値が出るはずだ。私はそう考えていた。

手元のサンプル船

作業員たちが帰り支度を始めた。汐見は振り子の綱を上げずに、桶に覆いをかけた。私は、まだ岸壁へ下りなかった。

ここで黙って見ているだけで帰るのは、落ち着かなかった。私がなぜこの港にいたのかを、汐見に話しておきたかった。訊かれたからではない。

「客の載貨計算の API を、一人で見ている」と私は話しはじめた。「この港のフェリー会社だ。朝だけ遅い」

汐見は記録用紙の点を見ていた。顔はこちらに向かないが、手は止まっている。

私は続けた。手元のサンプル船で、ベンチマークを回しながら CPU プロファイルを取った。CPU プロファイルは、プログラムがどの関数で CPU を使っているかを数えた記録だ。打ったのは、この二行だ。

だから私は、GZ 曲線の刻みや計算の順序をいじる案を、手帳に並べた。値が変わる案は採らない。運航管理者が見る値を、私の都合で変えるわけにはいかない。値を変えずに速くする手を探して、何日かたった。そのうちの一つを入れたが、本番の朝は変わらなかった。

// timed は、Compute の前後で時間を測って、計算全体で1行ログに残す。
func timed(compute func(model.Ship, model.Condition) model.Result) func(model.Ship, model.Condition) model.Result {
	return func(ship model.Ship, cond model.Condition) model.Result {
		start := time.Now()
		res := compute(ship, cond)
		log.Printf("compute ship=%s tanks=%d took=%s", ship.Name, len(ship.Tanks), time.Since(start).Round(time.Millisecond))
		return res
	}
}

朝は、全便の運航管理者が、出港の前に一斉に計算を送る。客のサーバは社内の一台で、コアの数にも限りがある。要求が重なると、順番を待つ分が積もる。一件 53 ミリ秒でも、待ちが積もれば 500 ミリ秒を超える。昼は要求がまばらで、待ちが積もらない。朝だけ遅いわけを、私はそう見ていた。

// VolumeAt は、液面の高さから、タンクの中の容積を引く。
// 隣り合う2行の間は直線で補間する。表の範囲の外は、端の行の値。
func VolumeAt(t model.Table, levelMM int) float64 {
	i := rowIndex(len(t), func(i int) bool { return t[i].LevelMM >= levelMM })
	if i == 0 {
		return t[0].VolumeL
	}
	if i == len(t) {
		return t[len(t)-1].VolumeL
	}
	lo, hi := t[i-1], t[i]
	return lo.VolumeL + (hi.VolumeL-lo.VolumeL)*float64(levelMM-lo.LevelMM)/float64(hi.LevelMM-lo.LevelMM)
}

// rowIndex は、ge(i) が初めて真になる最小の i を返す。見つからなければ n。
func rowIndex(n int, ge func(i int) bool) int {
	for i := 0; i < n; i++ {
		if ge(i) {
			return i
		}
	}
	return n
}

rowIndex は、表の先頭から一行ずつ ge(i) を確かめる。手元では軽い関数だった。手元の -top では四位にいる。私はそこで目を止めなかった。

傾けすぎない

「本番で、計算の中を測る手はある」

私は自分から言った。

Go には、動いているサーバから、どの関数が CPU を使っているかを取る仕組みがある。net/http/pprof というパッケージだ。名前は知っている。本番に入れたことは無い。

入れない理由も、私の中では決まっていた。本番に計測を入れれば、本番が変わる。朝の、いちばん遅い時間に測れば、いちばん遅い時間をさらに遅くする。客の朝を、私の調べ物のために壊したくない。調べるなら、手元で再現してから直す。それが本番に対する礼儀だと思ってきた。

調査官の頃も、そうだった。沈んだ船には触れられない。記録と設計値から計算で組み立てるしかない。それで多くの事故を説明してきた。

「本番を測れば、本番がもっと遅くなる。だから測るなら手元だ。汐見も、そう思うか」

汐見は、すぐには答えなかった。

甲板の重りの一つに歩いていき、白い番号の上に手を置いた。

「今日は、片舷に 2 度まで傾けました。4 トンを 6 メートルです」

// newDebugMux は、製品の mux とは別に、デバッグ用の mux を組み立てる。
// net/http/pprof は blank import にせず、必要なハンドラだけをここで登録する。
func newDebugMux() *http.ServeMux {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /debug/pprof/", pprof.Index)
	mux.HandleFunc("GET /debug/pprof/profile", pprof.Profile)
	return mux
}

net/http/pprof は、よく import _ "net/http/pprof" の形で読み込まれる。名前を使わない blank import だ。この形だと、パッケージの init() が、http.DefaultServeMux に /debug/pprof/ 以下を勝手に登録する。製品のサーバが DefaultServeMux を使っていれば、その口がそのまま外に出る。

名前を付けて import しても、init() は走り、DefaultServeMux への登録は起きる。外に出さないのは import の形ではない。製品のサーバが DefaultServeMux を使わないことだ。newServer は自分で組み立てた mux を返す。だから、DefaultServeMux に何が載っていても、製品の口には出ない。

そのうえで、デバッグ用の口は、自分の mux に自分の手で登録した。どこに何を載せたかが、コードの上で見えるようにするためだ。登録したのは、一覧の pprof.Index と、CPU プロファイルの pprof.Profile の二つだ。pprof.Index は /debug/pprof/ 以下を受けるので、heap や goroutine のプロファイルもここから取れる。それでも、このマシンの中からしか届かない口なので、そこまでは許すことにした。起動時の引数を返す cmdline は登録しない。

// rowIndex は、ge(i) が初めて真になる最小の i を返す。見つからなければ n。
func rowIndex(n int, ge func(i int) bool) int {
	return sort.Search(n, ge)
}

標準ライブラリの sort.Search は、二分探索で、ge が初めて真になる最小の i を返す。二分探索は、並んだ表の真ん中を見て、目的の行がどちらの半分にあるかで、もう半分を捨てていく探し方だ。表が 10 倍になっても、見る回数は数回しか増えないはずだ。刻みが等間隔なら、高さから行の番号を直接計算する手もある。ただ、表の刻みがどのタンクでも揃っている保証は無い。rowIndex の形を変えずに中身を一行替えるだけで済む、二分探索を選んだ。

前提が一つある。ge が、ある行から先はずっと真であること。測深表は液面の高さの昇順に並んでいるので、「液面以上の行」は、ある行から先が全部そうなる。前任者が、探す処理を述語を受ける形で一か所にまとめてくれていた。だから、この一行で済んだ。

rows  ge calls
  100       100
 1000      1000
10000     10000

行数と同じ回数だ。行数が 10 倍になれば、回数も 10 倍になる。直したあとは、こうだ。

1
2
3
4

rows  ge calls
  100         7
 1000        10
10000        13

行数が 10 倍になっても、3 回しか増えない。

おおよそ 2 を底にした行数の対数で、7・10・13 はそのとおりに並んでいる。ただ、sort.Search の回数がこう増えることは、ドキュメントに数式として書かれていない。だから数えた。

-top の最上位にいた for の行は、客の船にしか無い長い表に比例して仕事が増える行だった。

テストを壊してみることもした。直した rowIndex を先頭からのループに戻すと、回数のテストが落ちる。ge の比較を >= から > に変えると、同じ値のテストが落ちる。同じ高さの行を選ばなくなるからだ。デバッグ用の登録を製品の mux に混ぜると、404 のテストが落ちる。

担当に、今夜の保守時間でもう一つ版を入れてほしいと頼んだ。テストの名前を見せた。値は変わらない、と書いてある名前だ。担当は頷いた。

机を片づけながら、一つ思った。ここまで、私一人で来たのではない。昨日、汐見が訊いた「違うものを一つ」。それから、「少しだけ傾ける」。その二つが、順に効いた。

思っただけだった。

従来の使い方

昼過ぎ、ドックへ向かうバスに乗った。

揺れる座席で、昨夜読んだ Go の診断ドキュメントの続きを読み返した。本番のサービスは、周期的にプロファイルを取ってもよい。同じプロセスのレプリカが多いなら、ランダムに一つ選ぶ。Y 秒ごとに X 秒ずつ取り、結果をためて見比べる。プロファイルは互いに干渉するので、同時に取るのは一つ。そう書いてあった。

そこから、Google の論文に辿った。Ren らの「Google-Wide Profiling」だ。2010 年の IEEE Micro に載っている。データセンターの何千台ものマシンを巡回して、低い負荷でプロファイルを取り続け、ためて比べる仕組みだ。継続的プロファイリングと呼ぶ。

論文は、負荷の数字を二つ書いていた。一台でプロファイルを取っている間の負荷は、どの場合も数パーセント未満に抑えるよう、取る頻度の上限を決めている。もう一つが 0.01% 未満という数字で、こちらはデータセンター全体で集計した負荷だ。一台を測っている間の負荷ではない。

私は手帳に、二つの数字を別々の行に書いた。一台の間の上限、数パーセント未満。全体の集計、0.01% 未満。並べて一行にすると、いつか取り違える。

設計値の欄

午後、岸壁に着いたとき、試験は終わっていた。

夜明けの、風の無いうちに、汐見は 8 回の移動を最初からやり直していた。最後の一回は、重りを元に戻して零点を確かめる移動だ。

汐見が、記録用紙の板を、ハッチの縁に、私のほうへ向けて置いた。何も言わなかった。

点は、一本の線に並んでいた。外れた点は無い。

線から出る GM は、昨日と同じだった。1.04 メートル。設計値より小さい。

私は用紙を見た。綱は緩めてある。タンクは空か満水で、測深の記録も揃っている。風は無かった。点は一直線に並んだ。

「測定には、誤りは残っていないな」と私は言った。

汐見は頷いた。

私は、用紙の右上の「設計値」の欄を見た。1.20 メートル。

昨日も見た数字だ。今日は、目がそこから離れなかった。

その数字を、私は知っていた。二十年ほど前、この船の復原性を計算したとき、私が計算に使った数字だった。完成時の資料の値だ。

甲板の後ろ寄りの、あの構造物に目が行った。私の覚えている図面には無かったものだ。完成時の資料の値は、あれを載せる前の船の値だった。改修で甲板の上に構造物を増やす前の、船の値だ。

「当時、私が計算したのは、改修の前の船だった」と私は言った。「今朝まで手元で計算していたのが、手元の船だったのと、同じ形だ」

汐見は、板を自分のほうへ戻した。「設計値」の欄の横に、測った値が並べて書いてある。その所を、指で一度押さえた。

それから、汐見は携帯を出して、保存基金の担当に電話をかけた。

「傾斜試験、終わりました。GM は 1.04 です。設計値は 1.20 です。記録用紙は今日中に送ります」

短い電話だった。何度か、はい、と言って、汐見は電話を切った。

汐見は私のほうを向いた。

「居住区を撤去してから出航する、と基金が決めました」

甲板の後ろ寄りの構造物のことだった。

第4幕: 足場

夕方、岸壁で、作業員たちが居住区の撤去の段取りを話していた。足場の材料を何本、いつ運び込むか。私は少し離れて、手帳を開いた。

今朝、私が測ったのは、一台のサーバの、30 秒の、CPU を使っている時間だけだ。

CPU プロファイルは、CPU を使っている時間しか見ない。ディスクやネットワークを待っている時間や、ロックを待っている時間は、ここには出ない。待ちで遅いなら、別のプロファイル（block や mutex）か、別の道具を使う。

10 ミリ秒ごとの標本は、平均して時間を食っている関数には強い。代わりに、標本の間隔の 10 ミリ秒より短い一回きりの遅さや、ごく一部の要求だけが遅い尾は、拾いにくい。標本を集めて平均にしてしまうからだ。今回の遅さは、全部の要求が一様に遅い常態だった。だから届いた。尾を追うなら、実行トレースのような別の道具が要る。

今朝の 30 秒は、Google の論文が巡回して取り続けているものの、一回分にあたる。論文は、一台のマシンの上で、必要なときにプロファイルを取る使い方を、「従来の」使い方として書き分けている。私がしたのは、その従来の使い方だ。

客がサーバを増やしたら、一台ずつ取るのでは足りなくなる。何台もを巡回して、周期的に取り、ためて比べる仕組みが要る。Go の公式が勧め、論文が組んだ形だ。それは、私一人の保守で作るものではない。客の情報システムの担当と決めることだ。私は手帳に、そう書いた。

デバッグ用のサーバは、残す。127.0.0.1:6060 で待ち、外からは届かない。そのポートへの経路を誰が開けられるかは、担当の領分だ。取るのは担当が、サーバのコンソールで取る。次に遅くなったら、同じ手順で、30 秒で取れる。

汐見は振り子をハッチから外し、綱を肘に巻いていた。私の手帳のほうは見なかった。

控えの裏

綱を巻き終えるのを待って、私は言った。

「今日の頁を、写させてもらえないか」

測った人の記録を、一枚、手元に持っておきたかった。

汐見は記録用紙の板を取り上げ、用紙の端をめくって見せた。複写式で、下にもう一枚ついている。汐見はその控えを、ミシン目に沿って切り離した。点の列が、薄い青で写っている。裏は白かった。

汐見は控えを私に渡し、防水の表紙の野帳を抜いた。今日の頁を開いて、私の横の重りの上に置いた。それから、綱の残りを巻く作業に戻った。

私は重りの横にしゃがみ、控えの裏に、野帳の頁を写した。万年筆の字は、汐見の字よりずっと遅かった。

写し終えて、控えを手帳に挟んだ。表には点の列があり、裏には写しがある。

窓

三日目の朝、私はまた、運航管理室の窓際にいた。

昨夜の保守時間に、二つ目の版が入った。七時台の山を過ぎたところで、担当が画面を見せてくれた。今朝の七時台の p99 は、180 ミリ秒。上限の 500 ミリ秒の下に収まっていた。一件の計算は、手元の同じ負荷で 4 ミリ秒ほどになっている。一件が軽くなれば、朝に要求が重なっても、待ちは積もらない。

私は担当に、プロファイルの -top の表を一枚、社内の連絡に添えて送った。添えた文は、一つだけだ。関数の名前と数しか載っていません。

窓の外に、対岸の岸壁が見える。船の甲板の後ろ寄りに、銀色の管が組まれはじめていた。居住区を外すための足場だ。

近くの席で、運航管理者が計算を送った。端末の画面は、送ったと思ったときには、もう値を返していた。

私は手帳を閉じた。

野帳の写し

  • 見たこと: 風の無い朝に、8回の移動をやり直しました。点は一直線に並び、GM は 1.04m でした。設計値は 1.20m です。柘植さんの件: 本番から30秒取ったプロファイルの最上位は、測深表を引く関数（rowIndex）でした。手元のサンプル船では、最上位に出ていませんでした
  • 思ったこと: 柘植さんは、計算の値が正しく、測定に誤りが残っていると見ていました。綱を1本・タンクを1つ・風を潰しても、値は変わりませんでした。柘植さんは、手元の GZ 曲線の計算が遅いと見ていました。本番で時間を使っていたのは、表を先頭から引く行でした
  • 調べ方: 本番でのプロファイリング。本番のプロセスから、低い負荷のサンプリングで、時間を使っている関数を特定します。今回は1台のサーバから、必要なときに30秒取りました
  • 固定したもの: 製品とは別の口（127.0.0.1:6060）に残したデバッグ用のサーバと、担当がサーバのコンソールで取る手順。表を引く処理は二分探索（sort.Search）にしました
  • 変えていないもの: 全部の液面の高さ（表の範囲の外まで1mmごと）で、表を引いた値が直す前と後で一致しました。Compute の結果も、短い表の船と長い表の船の両方で一致しました。製品の口の応答（ステータスと本文）は、デバッグ用のサーバがあっても無くても同じでした。比べたのは製品としての振る舞いだけで、プロファイルの出力と処理時間は、この一致の比較に含めていません
  • まだ見ていない所: 待ち（I/O・ロック）で遅い場合。一部の要求だけが遅い尾。サーバが増えたときの巡回と、継続的な収集。CPU 以外のプロファイル
  • 船について: （測った）居住区を撤去する前の状態で行った傾斜試験で、GM が設計時の値を下回りました。結果を受けて、居住区の撤去が決まりました
