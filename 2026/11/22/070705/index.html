どこにも代入していないのに、マスタの単価が勝手に安くなる

どこにも代入していないのに、共有している部品マスタの単価が、二件目の見積から安くなる。名前で全部探しても、書いた行が見つからない。値の置かれた場所を見張り、書き換えられた瞬間に止めて、書いた行を見ます（ウォッチポイント・delve の watch）。

店の見積ツールが、照明用ケーブルの単価を安く出す。メートル四百二十円のはずが、三百七十八円。コードのどこでも、単価は書き換えていない。昨夜、単価を書き換える行を、名前で全部探して、全部読んだ。どれも正しかった。

// NewLightingQuote は、照明セットにケーブルを cableMeters メートル足した見積を作る。
func NewLightingQuote(c *Catalog, cableMeters int) *Quote {
	lines := c.Set("照明")
	lines = addCable(lines, c, cableMeters)

	qty := make([]int, len(lines))
	for i := range qty {
		qty[i] = 1
	}
	qty[len(qty)-1] = cableMeters

	total := 0
	for i, p := range lines {
		total += p.UnitPrice * qty[i]
	}
	return &Quote{Lines: lines, Qty: qty, Total: total}
}

func addCable(lines []Part, c *Catalog, meters int) []Part {
	p := c.Find("CB-2")
	if meters > 50 {
		p.UnitPrice = p.UnitPrice * 9 / 10
	}
	return append(lines, p)
}

addCable は、マスタからケーブルを一つ取り出す。Find は部品を値で返すので、p はマスタのケーブルの写しになる。五十メートルを超えたら、その写しの単価を一割引く。写しに書いても、マスタには届かない。それから、見積の明細の後ろに一行足して返す。

名前で書いた行が全部正しいなら、名前の出ない書き込みがあるはずだ。

スライスは、配列の一部を指す窓になる。窓の要素に代入すれば、元の配列の要素に書く。それも本で読んだ。ここまでは知っている。

まず、二件目を手元で起こしたかった。親父の控えの上で起きていることを、自分の画面の上で起こす。

マスタをテスト用に組み立てて、八十メートルの見積を一件作る。続けて、三十メートルの見積を一件。二件目のケーブルの単価が、マスタの元の単価のままか。マスタの単価も、元のままか。

画面に収まったのは、頭の十六行だけだった。上から読み始めた。

一行ずつ、append の最初の引数を見る。その変数が、どこから来たか。その関数の中で作ったものなら、マスタとは関係が無い。引数で受け取ったものなら、呼んでいる側を探して、そこで何を渡しているかを見る。渡しているものが、また別の関数の戻り値なら、その関数を開く。

orders.go の六十四行目は、発注書の文面を作る関数だった。足す先は、その関数の頭で作った空のスライスだ。マスタとは関係が無い。違う。

行によっては、そう簡単にいかない。一行に、ファイルを三つ開いた行もあった。

十分で、七行。

quote.go の三十三行目まで来た。addCable の return append(lines, p)。

そこで一度、手を離した。

スライスには、長さのほかに容量がある。容量は、窓の後ろに、まだ使える余りがいくつあるかの数だ。append は、余りがあれば新しい配列を作らずに、その余りに書く。余りが無ければ、新しい配列を作って、中身を写してから書く。本で読んだのは、そこまでだ。

lines は、Set の戻り値だ。Set は、マスタの窓を返す。

窓の後ろの余りは、窓の持ち分だ。append は、そこに一つ足すだけで、窓の中の照明器具とスイッチには触らない。マスタの、今ある要素を書き換えるわけではない。

この行も、違う。印を付けて、次へ進んだ。

csvload.go の三十四行目は、読み込みの関数の中で作った部品の並びに足している。違う。

その先、画面の外にも、在庫と、客の台帳と、作業の予定の行が続いている。

## watch
Set watchpoint.

	watch [-r|-w|-rw] <expr>

	-r	stops when the memory location is read
	-w	stops when the memory location is written
	-rw	stops when the memory location is read or written

-w は、そのメモリの場所に書き込みがあったときに止まる。-r は読まれたとき、-rw はどちらでも。

節の見出しのすぐ下に、watchpoint、とある。ウォッチポイント。初めて見る語だった。

ウォッチポイントは、変数の置かれたメモリの場所を見張るデバッガの機能だ。そこに書き込み（または読み出し）が起きた瞬間に、プログラムを止める。

トリガは、値がしきい値を割ったら止まる。これは、値が何であっても、その場所に書いたら止まる。

同じ語で、もう少し探した。CPU には、決まった場所への書き込みを見張る仕掛け、デバッグ用のレジスタがあって、デバッガはそれを使う、という説明に行き当たった。だから、見張れる大きさにも、見張れる数にも、上限がある。delve の注意書きには、見張れるのは一つの場所で八バイトまで、とあった。

教科書の側にも、名前があった。デバッグの教科書、Zeller の『Why Programs Fail』。観察の章、8章の講義スライドに、データブレークポイント（ウォッチポイント）という項目が一行あった。スライドの項目を見ただけで、本の中身は読んでいない。

道具を使う前に、使える条件を知りたかった。何を見張れるのか。

ドキュメントには、見張る場所を、print と同じ式で書く、とあった。変数の名前でも、アドレスでも書ける。一度に指定するのは、一つの場所だ。

デバッガは、使ったことが無い。いつも Println を足して見てきた。使うコマンドを、同じドキュメントで先に読んだ。

break は、ソースの行に止まる所を置く。ブレークポイントという。continue は、次に止まる所まで走らせる。print は、止まっている所で、式の値を出す。stack は、今いる関数を、誰がどの行から呼んだかを、上へ順に出す。frame は、stack の何段目かを選んで、そこで print などを打つ。

// Set は、セットの部品が並んでいる区間の写しを返す。
func (c *Catalog) Set(name string) []Part {
	from, to := c.setRange(name)
	return slices.Clone(c.parts[from:to])
}

slices.Clone は、渡されたスライスの中身を、新しい配列に写して返す。返ってきたものに何を足しても、マスタには届かない。

読んだだけで、試していない。もう一度、delve を起こして、二十四行目で止めた。

(dlv) watch -w c.parts[2]
Command failed: can not watch variable of type wakamatsu/shop/quote.Part
(dlv) watch -w c.parts[2].Name
Command failed: can not watch variable of type string

断られた。部品の構造体は、見張れない型だと言われた。名前の文字列も、同じだった。Go の文字列は、中身の置き場所を指す値と長さの組で、一つの値に収まらない。

指で、画面の二行をなぞった。

壊れた行を見つけられたのは、壊れる実行を手元で起こせたからだ。二件目が安い、と親父が気づかなければ、起こす手順も無かった。ウォッチポイントは、壊れる実行を走らせて、初めて掛けて待つ場所ができる。

見張れるのは、八バイトまでの値一つ。どの値が壊れるかが分かっていたから、その一つに掛けられた。

場所は、実行のたびに変わる。print & を打ち直すと、さっきとは別の値が出た。毎回、print & から掛け直す。

dlv debug は、最適化を切ってビルドする。止まった行は、その条件で止まった行だ。最適化すると、関数が呼んだ側に埋め込まれたり、値がメモリでなくレジスタに置かれたりするので、止まる行や見張れる場所が変わりうる。店で動かしている本番のバイナリで、同じ行に止まるかは、確かめていない。

止まった行は、書いた行だ。書いた理由ではない。なぜそこに書けたのかは、容量の話を自分で読んで、自分で言った。

手元の Mac は、Apple のチップだ。そこで、delve 1.27.2 で、この手順が動いた。ほかの環境で動くかは、確かめていない。どの環境で使えるかの一覧は、ドキュメントの中に見当たらなかった。

床が、低く鳴った。

作業員が、ジャッキで扇形の腕を押していた。ハンドルを、一段、また一段と下ろす。

腕は、動かなかった。ジャッキの鉄が、軋む。

作業員が一度手を離し、浸透剤をもう一吹きした。もう一度、押す。

鈍い音がした。腹の底に響く、重い音だった。

舵柱が、回った。

目盛りの針が、左の端の止めを離れて、ゆっくり目盛りの上を動いた。作業員がジャッキを付け替えて、反対から押す。針は、真ん中まで戻された。

汐見さんが、目盛りの前にかがんだ。梯子の側から読む。投光器を持ち替えて、船尾の側へ回る。もう一度、かがんで読む。

野帳を開いて、書いた。さっきの行の、すぐ下だった。

ノートパソコンの画面から目を上げて、それを見ていた。梯子の脇から、野帳の頁が見えた。字の形として、二行並んでいた。

野帳は、開いたままだった。汐見さんは作業員と、舵柱の回り具合を確かめはじめた。

ノートパソコンに戻った。

直した Set を、リポジトリに入れた。二件目の単価を確かめるテストも、そのまま残した。次にまた誰かが窓を返せば、このテストが赤くなる。

店のツールの README に、三行足した。止めたい行に break を置いて走らせる。print & で値の場所を出して、watch -w を掛けて continue。止まったら stack。

次に値が勝手に変わったら、これを開くのは、俺だ。

昼を少し過ぎて、舵機室の測定が全部終わった。電動機、発信器、非常用の電路。成績書の表の欄が、全部埋まった。

バインダーをめくって、成績書の裏を見た。白紙だった。

「汐見さん」

汐見さんが、振り向いた。

「今日の野帳の頁、ここに写していいですか。この部屋の記録と、俺の測った記録を、一緒にしておきたいんで」

それから、少し間を置いて、足した。

「俺の件も、あの書き方で残しておきたい」

「若松さんの件は、書いていません。言ってもらえれば、書き足します」

見たこと。思ったこと。俺が言ったことを、汐見さんは丁寧語に直して書いていった。単価を書けるのは、単価の名前を左に書いた行だけだと思っていた。そう言うと、思ったこと、の欄に書かれた。若松さん、と括弧で付けてあった。

書き終えると、汐見さんは野帳を開いたまま、床に座った俺の膝の、バインダーの横に置いた。

成績書の裏に、自分の手で写した。見たこと。思ったこと。調べ方。一項目ずつ、頁と見比べながら。

野帳の写し

  • 見たこと: 若松さんの件: 単価の名前の出る代入は、二か所とも正しかったです。watch -w で、マスタのケーブルの単価の場所に書き込みが起きた所で止まりました。addCable の append の行（quote.go 33行目）でした。舵機室: 舵柱は固着していました。浸透剤とジャッキで外しました
  • 思ったこと: 単価を書けるのは、単価の名前を左に書いた行だけ（若松さん）。名前の出ない append が、マスタの窓の後ろに書いていました。append は窓の後ろに足すだけで、マスタを書き換えない（若松さん）。容量に余りがあると、マスタの次の要素に書きます
  • 調べ方: ウォッチポイント。変数の置かれたメモリの場所を見張り、そこに書き込みが起きた瞬間にプログラムを止めるデバッガの機能です。止まった行が、書いた行です
  • 固定したもの: Set が、窓でなく写しを返すように直しました（part.go 34行目）。二件目の単価を確かめるテストを残しました。delve の手順（print &・watch -w・stack）を、店のツールの README に書きました
  • 変えていないもの: Set の戻り値の中身（品番・名前・単価・長さ）。セットだけ・ケーブル30mと50m・セットを使わない単品・80mの一件目の見積の、明細と合計と見積のあとのマスタ。実行時間とメモリの割り当て回数は比べていません
  • まだ見ていない所: 最適化したビルドで、同じ行に止まるか。手元の Mac 以外の環境。マスタの単価以外の値への書き込み。舵機室: 電動機の巻線の中
  • 船について: 舵機室の舵柱の頭の舵角目盛は、左舷 35度（一杯）を指していました。針は目盛りの端の止めに当たり、舵柱は固着していました
