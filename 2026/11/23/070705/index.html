50回に3回落ちるテストを、再実行で通すのをやめて原因を分ける

コードを変えていないのに、50回に3回落ちるテスト。再実行で通して先へ進むのをやめ、単独で流す・順序を変える・-race・遅延の注入を一つずつ当て、非同期の待ち／並行性／順序依存のどれに依存するかを分けます（Flaky テストの切り分け）。

第1幕: 通った、の行

第3幕: 条件を一つずつ

一本ずつ、を自分の件に写してみることにした。

最初にしたのは、チャットの記録を表にすることだった。落ちた日時を左の列に並べる。右に、そのとき何が違っていたかを書く。コードの変更、テストの順、CI のマシン。

右の列が、全部空いた。

八回とも、コードは同じ。テストの順も、マシンも、チャットからは分からない。違いを外から集めようとしても、集めるものが記録に残っていない。

外から集めるのをやめた。自分で一つずつ変える。

表の列を先に書いた。回数を重ねる。単独で流す。順序を変える。競合検出を付ける。待ちより長い遅延を入れる。左から一つずつ当てて、落ちる数が動くかを見る。

列ごとに、先に予想を書いておいた。単独で流して数が減れば、ほかのテストに引きずられている。順序を変えて数が動けば、順に左右されている。競合検出で報告が出れば、ゴルーチンどうしが同じ値を取り合っている。遅延を入れて数が跳ねれば、待ち方に左右されている。動かなければ、その列の線は細る。結果は、この予想と照らして読む。

その前に、手元で落ちる形にしておく必要があった。工房の CI では、戻す処理の所要時間がマシンの混み具合で揺れる。手元のノートパソコンは空いているので、そのまま流しても、たぶんほとんど落ちない。揺れの源を、こちらで決めて入れることにした。変えたい条件は、外から差し込めないと、一つずつ変えられない。

func (l *Ledger) ReleaseExpired(now time.Time) <-chan struct{} {
	done := make(chan struct{})
	go func() {
		defer close(done)
		time.Sleep(l.workDelay())
		l.mu.Lock()
		defer l.mu.Unlock()
		for id, r := range l.holds {
			if !r.until.After(now) {
				l.stock[r.item] += r.n
				delete(l.holds, id)
			}
		}
	}()
	return done
}

ゴルーチンを一つ起こして、期限を過ぎた取り置きを在庫に戻す。在庫と取り置きは sync.Mutex（同時に一つのゴルーチンだけが触れるようにする鍵）で守ってある。戻し終えたら、done というチャネルを閉じる。チャネルは、ゴルーチンのあいだで値や合図を受け渡す管だ。close で閉じると、その管を待っていた側に「終わった」が届く。

戻り値は、この done だ。最初に見たテストの l.ReleaseExpired(...) の行は、この戻り値を受けていない。

time.Sleep(l.workDelay()) の行が、帳票の書き出しの代わりだ。帳票を書く処理そのものは、ここには載せない。かかる時間だけを workDelay が返す。その時間を、外から渡せるようにした。期限の判定に使う時計も、同じように外から渡す。

渡し口は buildLedger にまとめた。本番は、これまでどおり NewLedger() を呼ぶ。NewLedger() の形は変えていない。中で buildLedger を呼び、システムの時計と、本番の所要時間を渡す。

func NewLedger() *Ledger {
	return buildLedger(systemClock{}, realWork)

// realWork は、在庫の帳票を書き出す所要時間の代わり。
func realWork() time.Duration { return 3 * time.Millisecond }

// buildLedger は時計と所要時間を受け取って Ledger を組み立てる。
func buildLedger(clock Clock, workDelay func() time.Duration) *Ledger {
	return &Ledger{
		stock:     map[string]int{"canvas": 12},
		holds:     map[string]reservation{},
		clock:     clock,
		workDelay: workDelay,
	}
}

// 乱数源は seed ごとに一つ。-count を重ねても同じ列が先へ進む。
var sources = map[uint64]*rand.Rand{}

// drawDelay は戻す処理の所要時間を一つ引く。普段は1〜5ms、混んだときは30〜60ms。
func drawDelay(r *rand.Rand) time.Duration {
	if r.IntN(16) == 0 {
		return time.Duration(30+r.IntN(31)) * time.Millisecond
	}
	return time.Duration(1+r.IntN(5)) * time.Millisecond
}

// newTestLedger は、固定の時計と、seed から引いた所要時間を buildLedger に渡す。
func newTestLedger(t *testing.T, seed uint64) *Ledger {
	t.Helper()
	r, ok := sources[seed]
	if !ok {
		r = rand.New(rand.NewPCG(seed, seed))
		sources[seed] = r
	}
	// 引くのは組み立てるとき。戻す処理のゴルーチンの中で引くと、乱数源を取り合う。
	d := drawDelay(r)
	if *fixedDelay > 0 {
		d = *fixedDelay
	}
	return buildLedger(fixedClock{noon}, func() time.Duration { return d })
}

所要時間は、普段は一〜五ミリ秒。十六回に一回くらい、混んだ日として三十〜六十ミリ秒を引く。二つの幅は、あいだを大きくあけた。実際の時間の細かな揺れで、結果がひっくり返らないようにするためだ。

乱数の種（seed）は固定した。同じ種からは、毎回同じ列が出る。

func TestEquivalentWhenFast(t *testing.T) {

// 所要時間が待ちより長い回は、Sleep だけが戻る前の在庫を見る。
func TestOnlySleepFailsWhenSlow(t *testing.T) {
	for _, d := range []time.Duration{30 * time.Millisecond, 60 * time.Millisecond} {
		if got := stockAfterSleep(d); got != 7 {
			t.Errorf("sleep, delay %v: Stock = %d, want 7 (戻る前)", d, got)
		}
		if got := stockAfterDone(d); got != 12 {
			t.Errorf("done, delay %v: Stock = %d, want 12", d, got)
		}
	}
}

工房の CI では、事情がまた違う。CI はパッケージをいくつも同時に流す。-parallel が効くのは、一つのテストのプログラムの中だけだ。パッケージどうしを同時にいくつ流すかは、-p という別の指定に従う。

汐見さんが、帆の向こう側で作業員と話していた。私は帆のふちを回って、そちらへ歩いた。

「汐見さん。さっきの表、最後の列まで埋まりました」

遅延を六十ミリ秒にすると五十回中五十回落ちたこと。チャネルの閉じるのを待つ形に直すと、〇回になったこと。それを短く伝えた。汐見さんは野帳を出し、今日のページの下に、私の言った数を書き足した。

「今日の野帳、写させてもらえますか」

汐見さんは胸ポケットから野帳を出し、今日のページを開いた。それを帆の上に置き、近くの砂袋の脇から拳ほどの石を一つ拾って、ページの端に載せた。

それから、足場の梯子のほうへ戻っていった。ヤードに残った索を片付ける段取りを、上の作業員に声で伝えている。

私は帆の脇に膝をつき、型紙の束の一枚目の余白に、野帳の文字を写しはじめた。ボールペンで、一行ずつ。風で野帳がめくれそうになるたび、石がそれを止めた。

見たこと。思ったこと。調べ方。項目の下に、短い文が並んでいる。

船について、の行で、ペンが一度止まった。縮帆の小綱のことが書いてあった。

ペン先を紙から上げずに、続きを写した。

写し終えて、野帳を閉じた。石を元の砂袋の脇に戻した。足場の下で、汐見さんがこちらを見上げた。私は手を上げた。汐見さんも、手を上げて返した。

夕方になっていた。

ドックの外の駐車場で、工房の軽バンの運転席に座った。西風がまだ強く、車体が時々揺れる。フロントガラスの向こうで、ドックのクレーンの先が、夕日で赤くなっていた。

携帯が震えた。チャットだった。

「すみません、また赤です。再実行していいですか」

小池さんだった。直したテストは、まだ工房には送っていない。工房の CI では、同じテストが、同じように落ち続けている。十回目だった。

私は、CI の再実行のボタンを押さなかった。

ノートパソコンを膝に開いて、工房の課題の一覧で、新しいチケットを開いた。題に TestReleaseExpired と書いた。本文の一行目を書いた。

「TestReleaseExpired：-count=50 で50回中3回落ちる（10・35・45回目）。-run 単独、-shuffle=1・20260406・777、-race でも同じ3回、DATA RACE の報告なし。-delay=60ms で50回中50回。待ちの time.Sleep(20ms) が、戻す処理より短い回に落ちる。CI の所要時間の揺れは未確認」

通った回数は書かなかった。

二行目以降に、表の列とコマンドを貼った。直したテストの二行の差分を、チケットにつないでコミットした。工房のリポジトリへ送った。

それから、小池さんに返した。

「押さないでください。待ち方が原因とみて、手元で確かめた直しを今送りました。CI が回り終わったら、受注画面の更新を出してください」

送信して、ノートパソコンを閉じた。

野帳の写し

  • 見たこと: ヤードの小綱を一本ずつ緩めました。一本目・二本目と、四本目からあとの畳んだ帆を留める小綱は、緩めた下の帆が垂れました。三本目は垂れませんでした。檜山さんの件: -count=50 で50回中3回落ちました。単独・順序を変えた3つの seed・-race でも同じ3回で、DATA RACE の報告はありませんでした。戻す処理を60msに固定すると50回中50回落ち、<-done で待つと0回でした
  • 思ったこと: 小綱は全部、畳んだ帆を留めるものだと見ていました。三本目で、その見立てが外れました。縮帆の小綱でした。檜山さんは、再実行で通るならコードは壊れていない、と見ていました。落ちる数を動かしたのは、戻す処理の所要時間と、テストの待ちの長さの関係でした
  • 調べ方: Flaky テストの切り分け。同じコードで結果が揺れるテストについて、条件を一つずつ変え、落ち方がどの条件に依存しているかで原因の種類を分けます。分類の名前は Luo ら（2014）の非同期の待ち・並行性・テストの順序依存です
  • 固定したもの: 落ちた回の条件を書き出した表（seed・回数・手ごとの結果）。戻す処理の所要時間を -delay で固定して流すテスト。時計と所要時間は newTestLedger が buildLedger に渡します
  • 変えていないもの: 待ち方を直した差分では、製品の hold パッケージは一字も変えていません。比べたのは在庫数と、取り置きが消えていること。所要時間が待ちより短い回は、二つの待ち方で一致しました。処理時間とログは比べていません
  • まだ見ていない所: -race が流していない道筋の競合。並列度（-parallel・-cpu）を変える手。CI のパッケージ間の並列（-p）。CI のマシンの速さの差そのもの
  • 船について: 主帆の縮帆の小綱が、リーフバンドの穴の列に沿って、ヤードに結ばれたまま残っていました

参考

  • Qingzhou Luo, Farah Hariri, Lamyaa Eloussi, Darko Marinov, “An Empirical Analysis of Flaky Tests”, FSE 2014: https://mir.cs.illinois.edu/marinov/publications/LuoETAL14FlakyTestsAnalysis.pdf
  • Go, Data Race Detector: https://go.dev/doc/articles/race_detector
