同じCSVなのに、ある月だけ取り込めない。違っていたのは中身ではなかった

同じ中身のCSVなのに、ある顧客の月だけ「必須の列がありません」で取り込めず、手元では再現しない。報告者との差を一つずつ揃える再現手順の確立（Reproducing Problems）で、毎回起きる手順と Go の再現テストを作り、原因まで辿ります。

第1幕: 二つの数字

ある団体の寄付者名簿だけが、ときどき取り込めない。画面には「必須の列『氏名』がありません」と出る。ところが、同じファイルをこちらで取り込むと、何事もなく通る。通るものは、直しようがない。二度、「再現しません」とお返しした。今朝、三件目が私の手元に差し戻されてきた。

ドックの底には、まだ雨の匂いが残っていた。盤木の脇に、夜のうちに溜まった水が浅く光っている。私はカメラを首から提げて、船尾側の舷を、端から一枚ずつ撮っていた。

一枚撮るごとに、液晶の画面で写りを確かめる。そのついでに、上着のポケットからスマートフォンを出して、チケットの画面を開いてしまう。さっきから、もう何度目か分からない。

差し戻しのコメントは一行だけだった。

――先方に、もう同じお返事はできません。申し訳ありませんが、一度見ていただけますか。

サポートの担当の宇野さんの一行だ。二度、読んだ。申し訳ないのは、こちらのほうだった。返事の欄に「承知しました。本日中に」と打ちかけて、本日中に何ができるのか分からないことに気づき、消した。画面を閉じた。

私は、非営利の団体向けに寄付と会員の管理サービスを作っている会社で、取り込みと書き出しの処理を担当している。社員は二十人ほど。Go でサーバ側を書くようになって、八年になる。この船を引き揚げた基金は、うちの顧客で、私はその担当でもある。

寄付者に毎月送る月報に、船の写真を載せたい。基金の事務局からそう頼まれて、月に一度、カメラを持ってこのドックに来ている。今日が二度目だった。一度目は、引き揚げの翌週だ。

撮った写真の送り先は、決まっている。基金の理事の皆さん。寄付者に送る月報の担当。それと、基金に頼まれて毎月お送りしている、船長の娘さんの真砂灯さん。

濡れた鋼と錆の匂いがする。ドックの縁のほうで、発電機が低く唸っている。船尾を囲む足場の上で、誰かが金具を叩く音が、乾いた空に二度、三度と響いた。十二月に入ったばかりの空は、雨が上がっても白く曇ったままだ。

私はスマートフォンをポケットに戻した。カメラを構え直し、次の一枚を撮った。

足場の梯子を、誰かが下りてくる音がした。

脱いだ作業つなぎの袖を腰の前で結び、Tシャツの上に綿の入った防寒の上着を羽織っている。首にタオル。後ろで一つに束ねた黒髪。片手に、板に挟んだ用紙を持っていた。前回、基金の事務局の人に紹介されて、挨拶だけした人だ。汐見さんという。

梯子の最後の一段から下りると、汐見さんのほうから声をかけてきた。

「志賀さん。先月撮った写真は、まだカメラに残っていますか」

「はい、残っていると思います。……引き揚げの翌週の分ですね」

「この舷を撮ったものを、見せていただけますか」

カメラの画面を先月の日付まで戻して、差し出した。泥をかぶったままの船体が、横長に何枚も続いている。

汐見さんは一枚ずつ、ゆっくり送っていった。

「一枚ずつ、写っている所を、フレームの番号で言っていただけると助かります」

「フレームの、番号ですか」

答えられなかった。どこの番号なのかも分からない。

汐見さんが、外板を指さした。外板に、白いペンキで数字が書いてある。四十、四十一、四十二。ほぼ等間隔に、船首のほうへ並んでいる。

船体の内側には、肋骨と呼ばれる骨組みが、船首から船尾まで等間隔に並んでいるのだという。外板は、その骨組みに張られている。骨組みの一本一本をフレームと呼び、その位置に番号を振ってある。白い数字は、その番号だった。

先月の写真を見直すと、泥の上に、同じ白い数字が、ちゃんと写っていた。何十枚も撮ったのに、私は一度も、この数字に目を留めていなかった。月報に載せる絵として、船の形しか見ていなかったのだ。

「すみません。これからは、番号が入るように撮ります」

自分で口にしてから、それがいちばん手間のない返事だと分かった。汐見さんは小さく頷いた。

「では、写真は、あとでお借りします」

急かす様子はなかった。汐見さんは用紙の板を脇に挟み、足場の下へ戻っていった。

しばらく撮りながら、少しずつ近づいた。

汐見さんは、足場の下に渡した板の上に、さっきの用紙と、自分の手帳を並べていた。防水の紙の、硬い表紙の手帳だ。手には、太いペンのような円筒を持っていて、それを外板に押し当てている。円筒から伸びた線の先に、手のひらほどの計器がつながっていた。

「それは、何を測っているんですか」

「板の厚さです。超音波の厚さ計です」

汐見さんは計器の表示から目を離さずに答えた。

円筒の先は探触子と呼ばれ、鋼板に当てると、そこから音を送り出す。音は板の裏側で跳ね返って、探触子に戻ってくる。戻ってくるまでの時間から、板の厚さを出す計器なのだという。錆びて薄くなった外板を見つけるために、船体をフレームごとに測っている。計器の表示の隅には、測り方の設定を示す小さな文字が出ていた。外板には、泥の下から出てきた古い塗膜が、まだらに残っている。

横から、並んだ二枚を覗き込んだ。

用紙のほうは、昨日、作業員が測った記録だった。列は、フレームの番号、高さ、測った厚さ、計器の名前、測った人。端に、元の厚さは十二ミリと刷ってある。汐見さんの手帳にも、同じフレームの番号が並んでいて、今朝の数字が書いてある。

数字が違った。フレーム四十二の、高さ一・五メートルの所で、用紙は十一・〇ミリ。手帳は十・四ミリ。ほかのフレームも、どれも用紙のほうが少しずつ厚い。

汐見さんは、足場の上で別の作業をしている作業員のほうへ顔を上げた。

「今日は、昨日の数字を、私の手で出すところから始めます」

作業員が、手袋の手を軽く上げて応えた。

私は、少し迷ってから口を開いた。

「差し出がましいようですが。汐見さんの数字が正しいのでしたら、測り直して、書き換えれば済むのではありませんか。わざわざ違う数字を出し直すのは、お時間がもったいないような気がして」

汐見さんは探触子を外板に当てたまま、短く答えた。

「昨日の十一・〇が、私の手で出るまでは、どちらが板の厚さなのか、私には決められません」

それから、一つだけ付け足した。

「出し方が分からないまま書き換えると、次に同じ出し方をした人が、また十一・〇と書きます。記録が、また揺れます」

「……そうですか」

私はそれだけ返した。正直に言えば、手間の話だとしか受け取れなかった。正しい数字が手元にあるなら、正しいほうを書けばいい。

ただ、私の手で出るまでは、という言い方だけが、喉のどこかに引っかかって残った。

引っかかった理由は、しばらくして分かった。自分のチケットのことを考えていたからだ。

「実は、私のほうにも、似たような話がありまして。いえ、似ているのかどうかも、よく分からないのですが」

言い出してから、汐見さんの仕事の邪魔をしていると気づいた。汐見さんは探触子を外板から離し、計器を膝の上に置いた。こちらを向いて、続きを待っている。

それで、経緯から話すことにした。

「ある団体の会計の方が、毎月、寄付者の一覧をうちのサービスに取り込んでくださっているんです。CSV というファイルで」

ほとんどの月は通る。ところが九月に一度、取り込みの画面で「必須の列『氏名』がありません」と出て断られた。団体ごとに、どの列が無ければ取り込まないかを決める設定があって、この団体は氏名と金額の二つを必須にしている。そのうちの氏名が無い、と言われたのだ、と私は続けた。

汐見さんは、頷きもせずに聞いていた。目だけが、私の話の速さに合わせて動いている。

一件目のとき、サポートの担当が、会計の方からファイルを送ってもらった。寄付者の名前とメールは、そのまま社内で扱えない。だから担当が名前とメールを伏せ字に置き換えて、私に渡してくれた。私はそれを、ステージング――本番と同じ版を動かしている検証用の環境――で取り込んだ。通った。何度やっても通った。それで、再現しません、とお返しした。

十月に二件目が来た。同じやり方で、今度は団体の取り込み設定も、ステージングに写して試した。通った。また、再現しません、とお返しした。

「先週、見出しに空白でも混じっているのかと思って、一行足したんです。見出しの前後の空白を落とす一行を。それで本番に出しました」

試したのは、伏せ字のファイルが通ることだけだった。そう言いかけて、言葉が止まった。

伏せ字のファイルは、直す前から通っていた。

「足したあの一行が、効いたのかどうか。確かめようが、なかったんです」

口に出すと、思っていたより平らな声になった。

今朝、三件目が来た。だから、効かなかったことだけは分かった。けれど、なぜ効かなかったのかは分からない。なぜ効かなかったのかが分からなければ、次に足す一手も、効いたかどうか確かめようがない。また同じことを繰り返すだけだ。

汐見さんは、私が話し終えるまで口を挟まなかった。少し間を置いてから、一つだけ訊いた。

「そのエラーは、志賀さんの手元で、出たことがありますか」

「それは――」

答えかけて、止まった。

私が持っているのは、会計の方の画面を撮ったスクリーンショットが三枚と、伏せ字のファイルだけだった。気づくと、スマートフォンは胸の前から腰のあたりまで下りていた。

あのエラーを、私は一度も、自分の手で出したことがない。出たのを見たのは、他人の画面の写真だけだった。

「……ありません。一度も」

汐見さんは、それについては何も足さなかった。計器を持ち直して、立ち上がった。

「続きを測ります。よろしければ、見ていかれますか」

肩の鞄が、急に重く感じられた。中にノートパソコンがある。事務所の机を借りて、チケットに向き合うべきなのかもしれない。鞄の口に手をかけて、迷った。結局、出さずに、足場の下に立っていた。

第2幕: 紙に無い一行

汐見さんは、昨日の用紙の項目を、上から順に手帳へ写していった。

位置。計器。校正。

用紙には、位置としてフレームの番号と高さの列がある。計器の名前の列もある。用紙の欄外には、試験片で校正済み、という印が押してある。汐見さんはその三つを、手帳の左端に一行ずつ書いた。それぞれの横に、小さな四角を描く。

「揃えたら、ここに印を付けます」

私に見える角度で、手帳を持ってそう言った。

最初は位置だった。外板の、フレーム四十二の白い数字の下に、チョークで描いた丸がある。作業員が昨日測った所に付けた印だ。汐見さんはその丸の真ん中に、探触子を当てた。

十・四。

「この丸が、本当に高さ一・五メートルにあるか、確かめたいんです」

汐見さんは、船尾の外板を見上げた。

「喫水の目盛りが、今は足場の板に隠れています。先月の写真に、写っていませんか」

喫水というのは、船が水に沈んでいる深さのことだ。船首と船尾の外板には、船の底の端からの高さが、目盛りの数字で書いてある。この船の船尾の目盛りは、いま、足場の板と手すりの陰になっていた。

先月の写真を送っていくと、船尾の端まで入った一枚があった。足場が組まれる前で、外板の目盛りの数字が、泥の上に縦に並んで見えている。

二本の指で、画面を拡げた。

目盛りの一・五の高さに、外板の継ぎ目が一本、横に走っている。汐見さんは写真と実物の継ぎ目を見比べて、チョークの丸が、その継ぎ目のすぐ上にあることを確かめた。手帳の「位置」の横の四角に、印を付けた。

私は、まだ画面を見ていた。

拡げた写真の、目盛りのずっと上のほうに、筋があった。外板の上を、横一列に走る、くすんだ帯。水面があった高さに沿って残る、水垢の帯だった。それが、二本ある。少しだけ離れて、平行に。

もう少し拡げると、帯の下地の色が違って見えた。

「あの、汐見さん。ここに、帯が二本あります」

画面を向けた。

「上の帯のほうが、下の塗装が新しく見えます。下の帯の所と、色も、つやも違う」

言い終えてから、それが何を意味するのか、私には何一つ言えないのだと思った。見たとおりを口にしただけだった。

汐見さんは、画面を覗き込んだ。少し長く見ていた。

「もう一枚、上の帯の所を、大きくしていただけますか」

言われた所を拡げた。汐見さんは、帯の高さを、写真の中の目盛りの数字に合わせて読んだ。

「下が三・二。上が三・六です」

そう言って、手帳を一枚めくった。測る箇所を並べた一覧のページらしい。その下の空いた行に、二本の帯の高さを書き足した。それ以上は、何も言わなかった。私も、何も訊かなかった。

次は計器だった。用紙に書いてある計器の名前は、汐見さんの計器と同じ型だった。汐見さんは、腰の袋から探触子をもう一つ出して、付け替えた。用紙の計器と同じ型の探触子だという。もう一度、チョークの丸に当てる。

十・四。

計器の横の四角に、印。

最後は校正だった。汐見さんは、段のついた鋼の小さな塊を出した。段ごとに厚さが分かっている、校正用の試験片だ。いちばん薄い段と厚い段に順に探触子を当てて、計器の表示を合わせる。それから、チョークの丸に戻した。

十・四。

校正の横の四角にも、印が付いた。

汐見さんは手帳を私のほうへ傾けて、印の並んだ三つの四角を、指で上から下へ一度なぞった。用紙の項目は、全部揃った。それでも、数字は十一・〇にならない。

汐見さんは、足場の上の作業員を見上げた。

「昨日は、測り方の設定は、どちらでした」

作業員は手を止めて、少し考えてから答えた。設定は買ったときのまま、いじっていない。通常の方式で測った。そういう答えだった。

汐見さんは、計器のボタンを何度か押した。表示の隅の文字が変わる。測り方の設定を、作業員と同じ通常の方式に切り替えたらしい。もう一度、チョークの丸に探触子を当てた。

表示が変わった。

十一・〇。

思わず、計器を覗き込んだ。昨日の用紙と同じ数字が、汐見さんの手の中に出ている。作業員の数字が、汐見さんの手で出た。

汐見さんは、設定を元に戻した。同じ丸に当てる。十・四。

それから、腰の袋から刃の平たいスクレーパーを出した。チョークの丸のすぐ横を、指先ほどの広さだけ削る。塗膜が剥がれて、鈍い鋼の地肌が出た。設定を通常の方式にして、その地肌に探触子を当てた。

十・四。

「表示は、十一・〇でした」

汐見さんは、計器から目を上げて言った。

「板の厚さは、十・四です」

「どうして、測り方で数字が変わるんですか」

訊かずにはいられなかった。

「塗膜の中は、音が遅いんです。一回の跳ね返りで測ると、塗膜の分が、実際の塗膜より厚く足されます。続けて返ってくる二回の間を測れば、鋼の中だけになります」

汐見さんが使っていたのは、エコー・エコー方式という測り方だった。音は板の裏で一度だけでなく、表と裏の間を何度も行き来して、何度も返ってくる。その続けて返ってくる二つの間隔は、鋼板の中だけで決まる。だから、上に塗膜があっても、鋼板の厚さだけが出る。通常の方式は、一回の跳ね返りで測るので、塗膜の上からだと、塗膜の分まで厚さに入ってしまう。塗膜を削った所なら、どちらの方式でも同じ数字になる。さっきの十・四は、それを確かめたのだ。

汐見さんは手帳を開いて、写した三つの項目の下に、もう一行書き足した。測り方の設定。その横の四角に、印を付けた。

作業員の用紙には、何も書かなかった。代わりに、足場の上へ声をかけて、用紙に測り方の設定の欄を足してほしい、と頼んだ。作業員が、了解の手を上げた。

私は、カメラを下ろしたまま立っていた。

用紙の項目を全部揃えても、数字は合わなかった。用紙に無い一行を揃えたら、合った。

それだけのことを、私はしばらく頭の中で繰り返していた。自分のチケットのほうへ、考えが行きかけた。でも、まだそこへは行かなかった。行けるほど、何かが分かったわけではなかった。

鞄から、ノートパソコンを出した。事務所の机を借りることにした。

事務所の石油ストーブの上で、薬缶が細く鳴っていた。ドックの縁に建つプレハブの、階段を上がった奥の机を空けてもらった。窓から、足場に囲まれた船尾が見える。

// Import は、アップロードされた CSV を寄付者の一覧にする。
func Import(r io.Reader, cfg Config) ([]Donor, error) {
	records, err := csv.NewReader(r).ReadAll()
	if err != nil {
		return nil, err
	}
	if len(records) == 0 {
		return nil, ErrEmpty
	}
	header := records[0]
	for i, h := range header {
		header[i] = strings.TrimSpace(h) // 先週足した: 見出しの前後の空白を落とす
	}
	for _, col := range cfg.Required {
		if !slices.Contains(header, col) {
			return nil, &MissingColumnError{Column: col}
		}
	}
	donors := make([]Donor, 0, len(records)-1)
	for _, rec := range records[1:] {
		d := Donor{}
		for i, h := range header {
			d[h] = rec[i]
		}
		donors = append(donors, d)
	}
	return donors, nil
}

// 先頭に BOM の無い入力（バグを踏まない範囲）では、戻り値が一致する。
func TestEquivalence_BOMなしの入力は同じ答え(t *testing.T) {
	cases := map[string]string{
		"正常（CRLF）":       table,
		"正常（LF）":         strings.ReplaceAll(table, "\r\n", "\n"),
		"必須の列が無い":        "氏名,メール\n見本 一郎,ichiro@example.org\n",
		"空のファイル":         "",
		"見出しの前後に空白":      " 氏名 , 金額 ,メール\n見本 一郎,3000,ichiro@example.org\n",
		"引用符で囲んだ値":       "氏名,金額,メール\n\"見本, 一郎\",3000,ichiro@example.org\n",
		"列数の合わない行":       "氏名,金額,メール\n見本 一郎,3000\n",
		"データ行の途中のU+FEFF": "氏名,金額,メール\n見本" + bom + "一郎,3000,ichiro@example.org\n",
	}
	for name, in := range cases {
		b, a := runBefore(in), runAfter(in)
		if !reflect.DeepEqual(b, a) {
			t.Errorf("%s: before = %+v, after = %+v", name, b, a)
		}
	}
}

table は見本と同じ中身の文字列、bom は "\uFEFF" の一文字だ。runBefore と runAfter は、同じ文字列を直す前と直したあとの Import にそれぞれ渡して、戻り値を比べられる形にまとめる小さな関数。

このバグを踏まずに済むのは、先頭に BOM の無い入力すべてだ。直した行は先頭の3バイトを覗くだけで、それが BOM でなければ何も読み捨てない。だから BOM の無い入力では、直す前と同じ読み込みになるはずだ。その読みが正しいかを、代表で確かめる。改行が CRLF のものと LF のもの、必須の列が無いもの、空のファイル、見出しの前後に空白があるもの。値を引用符で囲んだもの、列の数が合わない行があるもの。それと、データの行の途中に BOM と同じ文字が混じったもの。読み飛ばすのは先頭だけなので、途中の文字には触らないはずだ。

比べたのは、Import の戻り値だけだ。取り込んだ行の中身と件数、エラーの文言と種類。どれだけ時間がかかったかは、比べる対象に入れていない。

同じファイルに、BOM のある入力のテストも置いた。先頭に BOM があると、直す前は必須の列のエラーで断る。直したあとは、BOM の無い同じ内容と、まったく同じ結果を返す。

見出しを引用符で囲むと、直す前の症状は別のエラーになる。bare " in non-quoted-field だ。BOM が先頭の " より前にあるので、その欄は引用符で始まらない値として読まれ、途中に出てくる " が不正とされる。
