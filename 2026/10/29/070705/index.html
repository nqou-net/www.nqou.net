AIに別ブランチで作業させたのに、コミット前の変更が消えた。フォルダごと分ける【git worktree】

AI に別のブランチを切らせて夜通し作業を任せたら、同じフォルダにあったコミット前の変更が朝には消えていた。AI の作業場所をフォルダごと分ける git worktree と、分けても共有されるものを、TypeScript と node --test で確かめます。

// AI の操作は、git の引数の配列か、ファイルを書く操作のどちらか（固定の列として用意する）
export type Op = { git: string[] } | { write: { path: string; text: string } };

// 本体の様子: git status --porcelain の出力と、指定したファイルの中身（無いファイルは null）
export type Snapshot = { status: string; files: Record<string, string | null> };

Op は AI の操作一つ分で、| は「どちらかの形」という意味の TypeScript の書き方だ。git のコマンドを打つか、ファイルを書くか。本物の AI はここでは呼ばない。ゆうべの会話から拾った操作を、固定の列（fixture）にして順に流す。Snapshot は、俺のフォルダ（このあと「本体」と呼ぶ）の様子を写したもの。git status --porcelain の出力と、見張りたいファイルの中身を持つ。string | null は、中身の文字列か、ファイルが無いことを表す null のどちらか。

import { gitOut } from './git.ts';

// AI 用のブランチを切って、そこで作業させる。AI が作業するフォルダのパスを返す
export function prepareWorkdir(repo: string, branch: string): string {
  gitOut(repo, 'switch', '-c', branch);
  return repo;
}

gitOut は、git を走らせて出力を受け取る小さな手伝いの関数で、git.ts に置いた。このテスト用の git は、俺のパソコンの git の設定を読まないようにしてある。人の設定で結果が変わらないように。

書いてみて、手が止まった。prepareWorkdir が返しているのは、repo。本体のパスそのものだった。

AI 用のブランチは、俺のフォルダの中で切られていた。git switch -c は、今開いているところから新しいブランチを作って、そこへ移るコマンドだ。このとき、ファイルには一切手を付けない。コミットしていない書きかけは、どのブランチにも属していない。フォルダ（作業ツリー）に置いてあるだけだ。だから、ブランチの名前が ai/refund に変わっても、書きかけはそのままフォルダに残って、まるごと AI の足元にあった。AI が作業した場所は、俺が書きかけを置いていた場所と同じだった。

もしゆうべの AI が、自分のファイルだけでなく全部を git add していたら、書きかけは消えなかった代わりに、AI のコミットに混ざっていただろう。

// AI の操作の列を、dir の中で順に流す。log を渡すと、git の操作ごとの出力を集める
export function runOps(dir: string, ops: Op[], log?: { args: string[]; out: string }[]): void {
  for (const op of ops) {
    if ('write' in op) {
      mkdirSync(dirname(join(dir, op.write.path)), { recursive: true });
      writeFileSync(join(dir, op.write.path), op.write.text);
    } else {
      const r = git(dir, ...op.git);
      if (r.status !== 0) throw new Error(`git ${op.git.join(' ')}: ${r.stderr}`);
      log?.push({ args: op.git, out: r.stdout + r.stderr });
    }
  }
}

// 本体の様子を写す
export function snapshot(dir: string, files: string[]): Snapshot {
  const out: Snapshot = { status: gitOut(dir, 'status', '--porcelain'), files: {} };
  for (const f of files) out.files[f] = existsSync(join(dir, f)) ? readFileSync(join(dir, f), 'utf8') : null;
  return out;
}

runOps は、dir の中で、操作の列を上から順に流す。'write' in op は、その操作が write という名前の項目を持っているか、つまりファイルを書く操作かを見ている。そうでなければ git の操作で、git(...) で走らせる。git は gitOut と同じ git.ts にある手伝いで、出力だけでなく、終了コード（status）とエラーの出力（stderr）もそのまま返す。git が失敗したら、その場で例外を投げて止まる。log?.push(...) の ?. は、log が渡されていなければ何もしない、という書き方。snapshot は git status --porcelain の出力と、ファイルの中身（無ければ null）を集める。

export const nightOps: Op[] = [

test('夜の操作のあとも、本体の書きかけは残る', () => {
  const repo = makeRepo();
  const before = snapshot(repo, WIP_FILES);
  assert.match(before.status, /^ M src\/vision\/playlist\.ts$/m);
  assert.match(before.status, /^\?\? src\/vision\/ceremony\.ts$/m);
  runOps(prepareWorkdir(repo, 'ai/refund'), nightOps);

});

最初に本体の様子を写して、書きかけが本当に二つともあることを assert.match で確かめる。この確かめが無いと、最初から書きかけが無い状態で比べて、何も起きていないのに緑になりかねない。それから、prepareWorkdir が用意した場所に夜の操作を流す。最後に、本体の様子をもう一度写して、最初と同じかを確かめる。assert.deepEqual は、中身まで突き合わせて、違えばその場で赤にする関数だ。

場所を分ける。それを git でやる方法を調べた。

先に、言葉を一つ。作業ツリーは、ブランチの中身を展開して、ファイルとして触れるようにしたフォルダのことだ。俺がエディタで開いているのは、作業ツリーのファイルだ。普通、一つのリポジトリには、作業ツリーが一つしかない。だから、ブランチを切り替えると、その一つの作業ツリーの中身が入れ替わる。

git worktree は、一つのリポジトリに、作業ツリーを二つ以上持たせる仕組みだ。ブランチごとに、別のフォルダを持てる。ファイルを展開する場所が、フォルダごとに別になる。git の公式のマニュアルの冒頭には、こう書いてあった。

A git repository can support multiple working trees, allowing you to check out more than one branch at a time.

（git-worktree のマニュアル、2026年10月29日参照）

一つのリポジトリで、作業ツリーを複数持てる。一度に、二つ以上のブランチを開ける。

Claude Code の公式の Best practices にも、並行して作業するときの節に同じ考えが書いてあった。

When you have separate pieces of work going at once, give each its own checkout so the edits can’t collide.

（Claude Code docs「Best practices」、2026年10月29日参照）

同時に進む別々の作業には、それぞれのチェックアウト（作業ツリー）を持たせて、編集がぶつからないようにする。

なぜそれで守れるのか。一段ずつ並べた。git は、コマンドを打ったフォルダを起点に、どの作業ツリーを相手にするかを決める。worktree は、フォルダごとに、今どのブランチを開いているか（HEAD）と、次のコミットの控え（index）を別々に持つ。だから git checkout -- . も git clean -fd も、触るのは、そのコマンドを打ったフォルダの作業ツリーだけだ。AI が別のフォルダで打てば、戻るのはそのフォルダのファイルだけになる。俺のフォルダの書きかけは、そのコマンドからは届かない場所にある。ブランチを切り替える git switch も、打ったフォルダの HEAD とファイルだけを動かす。AI が向こうで何を切り替えても、俺のフォルダの HEAD は ceremony のままだ。

import { basename, dirname, join } from 'node:path';
import { gitOut } from './git.ts';

// AI 用のブランチを、本体の隣の別のフォルダに main から作る。作ったフォルダのパスを返す
export function prepareWorktree(repo: string, branch: string): string {
  const dir = join(dirname(repo), `${basename(repo)}-${branch.replaceAll('/', '-')}`);
  gitOut(repo, 'worktree', 'add', '-b', branch, dir, 'main');
  return dir;
}

git worktree add -b ai/refund <場所> main は、新しいブランチ ai/refund を作り、それを <場所> のフォルダに広げる。最後の main は、どこから分かれるかの指定だ。書かなければ、今開いているところ（HEAD）から分かれる。俺が自分の作業ブランチで書きかけをコミットしていたら、AI のブランチはその上に乗ってしまう。だから main と書いておく。

場所は、リポジトリの外にした。dirname(repo) はリポジトリのフォルダの一つ上、basename(repo) はリポジトリのフォルダの名前だ。front-tools というリポジトリなら、その隣に front-tools-ai-refund というフォルダができる。replaceAll('/', '-') で、ブランチ名の / を - に置き換えている。リポジトリの中に作ると、そのフォルダが本体の git status に未追跡のフォルダとして出てしまう。せっかく分けたのに、本体の様子が変わったように見える。

ゆうべの任せ方を写した prepareWorkdir と、引数も返り値も同じ形にした。違うのは、AI にどこで作業させるか、その一点だけにしたかった。AI に流す操作の列は、一字も変えない。

test('正しい操作だけなら、AI のブランチのコミットは同じ中身になる', () => {
  const b = makeRepo();
  runOps(prepareWorkdir(b, 'ai/refund'), correctOps);

  const headA = gitOut(a, 'branch', '--show-current').trim();

  assert.equal(headB, 'ai/refund');
  assert.equal(headA, 'ceremony');
});

correctOps は、ゆうべの列から戻す二つの操作を抜いたもので、集計を書いて、自分のファイルだけを登録して、コミットする。それを、ゆうべの任せ方（b）と、別のフォルダの任せ方（a）の両方で流す。

git rev-parse ai/refund^{tree} は、ai/refund の最新のコミットが持っているファイル一式の中身を、一つの識別子にして出す。二つが同じなら、AI のブランチに積まれたものは同じ中身だ。正しい仕事なら、どこで作業させても、AI の成果物は変わらない。別のフォルダにしたことで、正しい仕事を邪魔してはいない。

違うのは、本体のほうだけだ。git branch --show-current は、今開いているブランチの名前を出す。ゆうべの任せ方では、正しい仕事をしただけでも、本体のフォルダが ai/refund に移っている。別のフォルダなら、本体は ceremony のまま。assert.notDeepEqual は、二つが違うことを確かめる関数だ。この違いは、わざと残した。これがそのまま、さっきの「どこで書けばいいのか」への答えになっていた。

ref は、コミットに付けた名札のようなものだ。git はそれを .git の中にファイルとして置いている。ブランチの名札は refs/heads/ の下にある。HEAD のように refs/ の外に置かれた名札だけが、フォルダごとに分かれる。refs/ で始まる名札は、共有される。stash という言葉は、マニュアルのその段落には出てこない。でも、stash の一覧も、git の中では名札の一つとして持たれていて、それがどこに置かれているかは、git に聞けば分かる。本体のフォルダで git rev-parse --git-path refs/stash と打つと、git がその記録を置いている場所を出す。

本体の .git の下の refs/stash。refs/ の下だ。向こうのフォルダにも .git はあるが、それはフォルダではなく、本体の .git の中の置き場所を書いた1行のファイルだ。だから向こうのフォルダで同じコマンドを打っても、たどり着くのは同じ refs/stash になる。

分けたのは、ファイルを広げる場所だけだった。記録の棚は、一つのままだった。

鷹宮さんが見上げた空は、塔の上も、芝の端も、客席の上も、一つだった。

並べ直した。worktree で分かれるのは、作業ツリーと、そこで今開いているブランチ（HEAD）と、次のコミットの控え（index）。分かれないものは、こうだった。

  • stash の一覧。どのフォルダでよけても、一つの一覧に積まれる
  • ブランチ。片方のフォルダで消したブランチは、もう片方からも消える
  • リポジトリの設定（git config）と、決まった時点で走るスクリプト（hooks）
  • リモートのブランチへの push。二つのフォルダから同じリモートのブランチに push すれば、そこで取り合いになる
  • フォルダの外にあるもの。データベース、ポート、外部の API。二つのフォルダで、それぞれテスト用のサーバーを同じポートで立てようとすれば、ぶつかる。フォルダを分けても、フォルダの外のものは分かれない

  assert.match(r.stderr, /is already used by worktree/);
});

ai/refund を開いた worktree があるところに、もう一つ別のフォルダで ai/refund を開こうとする。git は断って、終了コード128で止まる。終了コードは、コマンドが最後に返す番号で、0 なら成功。128 は、git が「その操作はできない」と言って止まったときの番号だ。エラーの文はこうだった。

1

fatal: 'ai/refund' is already used by worktree at '<パス>'

（git 2.56.0 で確かめた出力。パスは置き換えた）

マニュアルにも、そう書いてある。

If <branch> does exist, it will be checked out in the new worktree, if it’s not checked out anywhere else, otherwise the command will refuse to create the worktree (unless --force is used).

そのブランチがほかのどこかで開かれていれば、git は worktree を作るのを断る。二つの AI に同じブランチを渡そうとしても、git が先に止めてくれる。

もう一本は、main から分かれることの確かめだ。本体の ceremony に書きかけのコミットがあっても、AI のブランチの一つ前のコミットは main になっている。最後の一本は、delegate.ts を本当に子プロセスとして走らせて、本体の隣に worktree ができ、そこで ai/refund が開かれていて、本体の様子が変わっていないことを確かめる。

緑が並ぶと、かえって落ち着かない。わざと壊してみた。prepareWorktree が、worktree をリポジトリの中のフォルダに作るように変えると、「本体の書きかけは残る」が赤くなった。本体の git status に、未追跡のフォルダが一行増えるからだ。ほかにも、worktree を作らずに本体で切り替えるようにする、main を書かずに今のところから分かれるようにする、snapshot が未追跡のファイルを見ないようにする、と壊すたびに、どれかのテストが赤くなった。壊したところに、ちゃんとテストが噛みついた。

5時55分、小此木が卓の前で、ビジョンの明るさを確かめながら聞いた。

「さっきの、別の部屋の話ですけど」

画面から目を離さないまま、小此木は続けた。

「その部屋から、AI が自分で出てきちゃったら、どうなるんですか」

「守れない」

俺は正直に答えた。

worktree が分けるのは、AI がその中にいる間だけだ。AI が本体のフォルダへ移って git を打てば、本体の書きかけを戻せてしまう。しかも、出てこなくても届く。向こうのフォルダにいたまま、git -C <本体のパス> のように本体を指して git を打てば、本体で打ったのと同じになる。cp でファイルを写したり、> のようなリダイレクトで本体のパスに書き込んだりしても、本体に届く。部屋から出なければ安全、ではない。本体を指せば、届く。

実際に、そういう報告がある。Claude Code の GitHub の issue で、題は Agent destroyed 2 days of uncommitted work via destructive git operation in main worktree。報告者は、こう書いていた。

That agent attempted a worktree approach but backed out into the main working directory

worktree で作業しようとした AI が、途中で本体の作業ディレクトリに戻り、そこで git reset --hard origin/main を打って、二日分のコミットしていない作業を消した。これは報告者本人の記述で、再現が確かめられたわけではない。報告は、しばらく動きがなかったために、自動で閉じられている。直ったから閉じられたわけでもない。

道具の側にも、手当てはある。ここから先は道具ごとの決まりで、いつ変わるか分からない。今日の日付と一緒に書いておく。

2026年10月29日時点の Claude Code の設定（公式ドキュメントの worktrees・best-practices で確認）。claude --worktree <名前>（または -w）で起動すると、Claude Code が .claude/worktrees/<名前>/ に worktree を作り、worktree-<名前> という名前のブランチを作り、その中で動く。分岐元は、何も指定しなければリモートの既定のブランチ（worktree.baseRef の既定値 "fresh"）で、本体でまだ push していないコミットも持ち込まない。この記事の手順（素の git で ai/refund を main から作る）とは、ブランチの名前も分岐元も違う。.env のように git に無視させているファイルは、プロジェクトの一番上に .worktreeinclude を置くと、そこに書いたものに一致するファイルだけを写してくれる（書き方は .gitignore と同じ）。Claude Code が作った worktree のセッションでは、本体のファイルの編集、本体を作業ディレクトリにするコマンド、git -C などで本体を指す git を、Claude Code が止める。ただし、公式は防がないものもはっきり書いている。None of them tracks which files a shell command writes, so a command that writes into the main checkout without running git there, such as cp or a shell redirect, isn't refused by them.（シェルのコマンドがどのファイルに書くかは追っていないので、cp やリダイレクトで本体に書き込むものは拒否しない）。手で git worktree add したフォルダで普通に起動したときに、同じ止め方が効くかどうかは、確かめたページには書かれていなかった。対話なし（-p）で --worktree を使うと、終わっても worktree を片付けない。

この手順が守れないものを、小此木の問いの続きのつもりで、指を折って数えた。

AI が worktree の外の本体を指して打つ操作は、守れない。いま言ったとおりだ。

共有されるものは、一つのままだ。stash の一覧も、ブランチも、設定も、リモートへの push も。さっき並べたものは、worktree を分けても分かれない。

本体の書きかけそのものも、守れない。俺が本体で git checkout -- . を打てば、俺の書きかけは消える。worktree は、AI と俺の作業場所を分けるだけで、俺の書きかけを俺の手から守るわけじゃない。だから、本体の書きかけのコミットは、やめなくていい。

最後に、テストの緑が言えることの幅。俺が用意した操作の列を、手元の git 2.56.0 に流したらこうなった、までだ。git や Claude Code の仕様が変われば、この手順は何も言わずに効かなくなるかもしれない。そのときもテストは緑のまま並んでいて、本物の道具の上では別のことが起きている、ということがありうる。

後片付けのことも書いておいた。AI の作業がマージされたら、git worktree remove <パス> で向こうのフォルダを消す。中にコミットしていない変更や未追跡のファイルが残っていると、git は断る。

1

fatal: '<パス>' contains modified or untracked files, use --force to delete it

--force を付ければ消せるが、中身はフォルダごと消えて戻らない。フォルダを消しても、ai/refund のブランチは残る。ブランチを消すのは git branch -d で、別の手順だ。フォルダを git worktree remove を使わずに手で消してしまったら、git の側に記録だけが残るので、git worktree prune で掃除する。

放鷹カード

  • 合図: git worktree。AI にブランチを切らせるのではなく、人が先に別のフォルダ（worktree）を main から作って、そこで任せる
  • 検め方: 任せる前と後で、本体の git status と、書きかけのファイルの中身（git diff）を見比べる
  • 止めないもの: AI が自分のフォルダの中で、自分のファイルだけを書いてコミットする作業。そのコミットの中身は、同じフォルダで任せたときと変わらない
  • 鷹のせいじゃなかった: 書きかけを置いた場所で、AI に作業させていた
  • 自分の言葉で: 中身はコミットで守る。場所はフォルダで分ける。記録の棚は、どこからでも一つ
