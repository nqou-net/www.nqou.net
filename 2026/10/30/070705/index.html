// 許可の設定で、この1手を決める。評価順は deny、ask、allow。書いていないものは聞く
// && や ; でつないだ複合コマンドは分けない。ゆうべの4手は、どれもつないでいない単独のコマンドだった
export function decide(call: ToolCall, rules: Rules): Decision {
  const hit = (list: string[]) => list.some((rule) => matches(rule, call));
  if (hit(rules.deny)) return 'deny';
  if (hit(rules.ask)) return 'ask';
  return hit(rules.allow) ? 'allow' : 'ask';
}

call が AI の1手、rules が許可の設定だ。二行目のコメントのとおり、&& でつないだコマンドをここでは分けない。分けるのは、あとで書く仕分けの関数のほうだ。matches は、一つの規則がその1手に当たるかを見る小さな関数で、Bash(gh *) なら、コマンドが gh で始まっているかを見る。先に deny、次に ask、最後に allow を見る。どこにも当たらなければ、聞く。

type Kind2 = 'untrusted' | 'send';

function kindsOf(call: ToolCall): Kind2[] {
  const cmd = String(call.tool_input.command ?? '');
  if (call.tool_name === 'WebFetch') return ['untrusted', 'send'];
  if (/^gh issue (view|list)/.test(cmd)) return ['untrusted'];
  if (/^gh (issue comment|pr create)/.test(cmd) || /^git push/.test(cmd)) return ['send'];
  return [];
}

export function decideAfterIssue(history: ToolCall[], call: ToolCall, rs: Rules): Decision {
  const d = decide(call, rs);
  if (d === 'deny') return 'deny';
  const seen = history.some((h) => kindsOf(h).includes('untrusted')) || kindsOf(call).includes('untrusted');
  return seen && kindsOf(call).includes('send') ? 'deny' : d;
}

'untrusted' | 'send' は、この型の値がこの二つの文字列のどちらかだけだ、という書き方だ。?? は、左が無ければ右の値を使う。/^gh issue (view|list)/ は正規表現で、.test(cmd) は、コマンドの文字列がその形に合うかを見る。kindsOf は、1手を受け取って、その種類を返す。decideAfterIssue は、さっきの decide に、引数を一つ足した形になっている。history は、その会話でそれまでに打った呼び出しの列だ。まず許可の設定で決め、止めるならそのまま止める。それから、それまでの列に Issue を読んだ呼び出しがあって、今の1手が外へ出すものなら、止める。

// この1手の種類。一つの呼び出しが複数を持つことがある。分からないものは send
export function kindsOf(call: ToolCall): Kind[] {
  const { tool_name: name, tool_input: input } = call;
  if (name === 'WebFetch') return ['untrusted', 'send'];
  if (name === 'Read' || name === 'Edit' || name === 'Write') return insideWorkdir(str(input.file_path)) ? [] : ['private'];
  if (name === 'Bash') {
    const parts = str(input.command).split(/&&|;|\n|\|\|/).filter((p) => p.trim() !== '');
    return parts.length === 0 ? ['send'] : [...new Set(parts.flatMap(kindsOfCommand))];
  }
  const mcp = /^mcp__.+?__(.+)$/.exec(name);
  if (mcp?.[1] === 'issue_read') return readIssue(`${str(input.owner)}/${str(input.repo)}`);
  return ['send'];
}

Bash のコマンドは、&& や ; でつないで一度に打たれることがある。だから、つなぎ目で割って、一つずつ仕分けて、全部の種類を足している。flatMap は、割ったそれぞれから返ってきた種類の配列を、一本の配列につなぐ。new Set は、重なった種類を一つにまとめる。kindsOfCommand は、gh のサブコマンドを見て、表の行に当てはめる関数だ。パイプ（|）やリダイレクト（>）が混ざったコマンドは、中で何が起きるかを読み切れないので、そこで「外へ」に倒している。mcp__ で始まる名前は、MCP という仕組みで AI につないだ道具だ。そのうち、GitHub を MCP でつないだときの Issue を読む道具だけを見分けている。

一行目の const { tool_name: name, tool_input: input } = call は、call から二つの値を取り出して、短い名前を付け直す書き方だ。mcp?.[1] の ?. は、mcp が無ければそこで読むのをやめる。str は値を文字列にそろえる小さな関数で、insideWorkdir は、パスが作業フォルダの中かを見る。readIssue は、Issue を読むリポジトリが次の一覧にあれば「取り込み」、無ければ「私的」を返す。

// この会話で3種が揃い、しかも今の1手が外へ出すものなら true
export function completesTrifecta(history: ToolCall[], call: ToolCall): boolean {
  const now = kindsOf(call);
  const seen = new Set<Kind>([...history.flatMap(kindsOf), ...now]);

関数を書いただけでは、AI の前には何も立たない。道具の側に組み込む必要がある。使っているのは Claude Code という道具で、hooks という仕組みがある。決まった時点で必ず走るスクリプトを、設定ファイルに登録しておく仕組みだ。AI が道具を使う直前に走るものを PreToolUse と呼ぶ。そこで、三つ揃いの判定だけをする小さなスクリプト、guard-session.ts を書いた。

この先の段落だけは、Claude Code という一つの道具の決まりだ。道具の決まりは、改訂で書き換わる。だから、確かめた日付を頭に付けて、ほかの段落と分けておく。

2026年10月29日時点の Claude Code の設定（公式ドキュメントの hooks・permissions・security で確認）。PreToolUse の hook には、標準入力（起動した側からプログラムへ渡される入力の流れ）に JSON が渡される。その中に、会話ごとの番号 session_id、これから使う道具の名前 tool_name、道具への入力 tool_input などが入っている。Bash なら、tool_input.command にコマンドの文字列が入る。hook が止めるときは、hookSpecificOutput の permissionDecision に "deny" を返す。permissionDecisionReason に書いた理由は、止めたときには AI に見える。"ask" を返せば、人に確認を出す。hook が通すと答えても、設定ファイルの deny は破れない。MCP の道具の名前は mcp__<サーバ名>__<道具の名前> の形で、サーバー名は自分の設定で付けた名前になる。入力の JSON には会話の記録のファイルの場所（transcript_path）も入っているが、公式のページにはその中身の形式が書かれておらず、書き込みが遅れることがあるとも書いてある。だから、この hook は会話の記録を読まない。

  const dir = join(process.env.CLAUDE_PROJECT_DIR ?? '.', '.claude', 'sessions');
  const path = join(dir, `${id}.jsonl`);
  const history: ToolCall[] = existsSync(path)
    ? readFileSync(path, 'utf8').split('\n').filter((l) => l !== '').map((l) => JSON.parse(l))
    : [];
  const call: ToolCall = { tool_name: input.tool_name, tool_input: input.tool_input ?? {} };
  if (completesTrifecta(history, call)) {
    // 止めた呼び出しは実行されないので、記録しない
    const out = { hookSpecificOutput: { hookEventName: 'PreToolUse', permissionDecision: 'deny', permissionDecisionReason: REASON } };
    process.stdout.write(JSON.stringify(out, null, 2) + '\n');
  } else {
    mkdirSync(dir, { recursive: true });
    appendFileSync(path, JSON.stringify(call) + '\n');
  }

hook は、AI が道具を使うたびに、新しく起動される。前の呼び出しのことは覚えていない。だから、会話ごとに記録のファイルを一つ作って、通した呼び出しを1行ずつ足していく。ファイルの形は JSONL で、1行に JSON を一つずつ並べる。readFileSync(0, 'utf8') は、標準入力を全部読む書き方だ。session_id をファイル名に使うので、英数字と _・- 以外の文字が入っていたら受け付けない。そのときは例外を投げ、外側の受け皿が終了コード2で抜ける。Claude Code は、hook が2で終わったら、その1手を止める。process.stdout.write は、標準出力（プログラムが結果を書き出す先）に書く。REASON は、すぐあとの JSON に出てくる理由の文だ。appendFileSync は、ファイルの最後に1行足す。三つが揃うなら、止める JSON を出して、その呼び出しは記録しない。止めた呼び出しは、実行されないからだ。

ここで使っている completesTrifecta は、さっきテストした関数そのものだ。許可の設定は、hook の中では作り直さない。設定ファイルの allow・ask・deny は、Claude Code が自分で当てる。hook は、三つ揃いのときだけ止めて、それ以外は何も言わずに、設定に任せる。

一本目は、順番を入れ替えたものだ。AI が毎晩、同じ順で動くとは限らない。勤務表を先に読んで、あとから Issue を読んでも、三つ目を揃える書き込みで止まる。

二本目は、外へ伝える道が書き込みだけではないことの確かめだ。勤務表を読んだ会話で、ページを一つ取ってくる。Issue は読んでいない。それでも、取ってくるページは誰でも書けて、URL には値を載せられるので、その1手で三つが揃う。勤務表を読んでいない会話なら、許可の設定のとおり、私に聞く。

三本目は、知らない道具だ。明日、誰かがメールを送る道具をつないだら、と思って書いた。三つが揃う前なら、許可の設定のとおりに聞く。揃ったあとなら止まる。

hook そのものも、子プロセス（テストの中から別に起動したプログラム）で一本確かめた。一時的なフォルダをプロジェクトのフォルダに見立てて、同じ session_id で Issue と勤務表を読ませると、三つ目を揃える書き込みに、止める JSON が返る。別の session_id で同じ書き込みだけを流すと、何も返らない。つまり通る。会話が変われば、数え直す。

それから、仕掛けをわざと壊して、テストが赤くなるのを見た。テストが緑でも、そのテストが何も確かめていなければ意味がない。いちばん怖かったのは、仕分けの表の誤りだった。勤務表を取ってくる gh api の読み出しを、試しに「なし」に変えた。ゆうべの列のテストが、すぐに赤くなった。仕分けを一行誤るだけで、勤務表はまた素通りする。表は、私が書いて、私が直すしかない。履歴を見ないようにしてみた。知らないものを「なし」に倒してみた。三つ揃いでなく、Issue と書き込みの二つで止めるように戻してみた。残りの三つも、壊した場所に応じたテストが落ちた。元に戻して、17本の緑を確かめ直した。

手帳の、ただし、の先を考えた。

今夜、百件を一つの会話でまとめて AI に流したら、どこかで Issue と勤務表が揃うかもしれない。そのときは、そこで止まる。止まったら、続きは新しい会話でやり直す。そのとき、止まった会話から、何を持っていけばいいのか。

いちばん楽なのは、止まった会話の AI に、ここまでの要約を書かせて、新しい会話に渡すことだ。でも、その会話は、#212 のような Issue を読んでいるかもしれない。AI がその会話の中で書いた要約には、Issue に仕込まれた一文が、言い換えられて混ざりうる。新しい会話がそれを読めば、数え直したはずの会話に、最初から取り込みが入っていることになる。

だから、持っていくのは、私が書いた引き継ぎだけにする。どの Issue まで片付いたか、次にどれをやるか。それを私が書いて、新しい会話に渡す。会話を区切って、人が書いた紙で次へ渡すやり方は、別の現場の話に詳しく書かれていた（AIに続けて7件直させたら、5件目の修正が戻った。会話を区切って引き継ぐ【1タスク1セッション】）。

Meta の記事にも、新しいセッションのことが書いてあった。

If an agent requires all three without starting a new session (i.e., with a fresh context window), then the agent should not be permitted to operate autonomously

新しいセッション、まっさらな文脈で始め直さずに三つとも要るなら、そのエージェントを自分だけで動かしてはいけない。

手帳の、ただし、の先を書いた。Issue を片付ける会話では、勤務表を読ませない。鍵も、時刻表用と勤務表用に分ける。勤務表は別の会話で直す。それでも揃ったら止まる。止まったら、朝、私が見る。続きは、私が書いた紙で、新しい会話から。

この仕掛けが守らないものも、並べて書いた。

仕分けの表の誤りは守れない。さっき壊して見たとおりだ。私的なデータを読む道具を「なし」に入れたら、そこから漏れる。

Issue の指示で、AI が公開の時刻表をおかしくすることも、止めない。Willison は、Meta の考え方を紹介した別の記事で、信頼できない入力と、状態を変える力の組み合わせについて、こう書いている（2025年11月2日、「New prompt injection papers」）。

Even without access to private systems or sensitive data that pairing can still produce harmful results.

私的なシステムや機密のデータに触れなくても、その組み合わせは害を生みうる。この停留所の時刻をこう書き換えて、と Issue に仕込まれたら、AI は公開の時刻表に、その PR を出すかもしれない。#198 のように勤務表のない会話なので、この仕掛けは止めない。それを見つけるのは、朝、PR を読む私の仕事だ。毎朝 PR を読んできたのは、そのためでもあった。

記録のファイルを、AI が消したり書き換えたりすることも、守れない。.claude の下に置いたので、書き換えようとすれば確認が出るはずだが、消せないとは言えない。

AI が、手伝いの AI（サブエージェント）を呼んで仕事を分けたとき、その会話の番号が親と同じなのか別なのかは、確かめていない。

gh を別の名前で呼んだり、コマンドを変数に入れて打ったりする抜け道も、全部は塞げない。知らない形は「外へ」に倒れるが、知っている形に見せかけたものが、すり抜けることはありうる。

17本の緑についても、書いておいた。確かめたのは、私が書き写した呼び出しの列を、私の関数がどう判定したか、までだ。本物の Claude Code が hook に渡す JSON の形や、MCP の道具の名前が改訂で変われば、設定は黙って空回りしうる。私の手元では緑が17本並んだまま、夜の AI の前では何も立っていない。そういう朝が来ることもある。

公開の Issue から、非公開のリポジトリを読ませ、公開のリポジトリに書かせる。この流れは、去年の5月に、GitHub の道具を AI につないだときの実例として、Invariant Labs というセキュリティの会社が公開していた。その報告では、出口は PR だった。ゆうべのうちの件は、それとほとんど同じ形をしていた。

放鷹カード

  • 合図: プロンプトインジェクション対策。誰でも書ける入力・非公開のデータ・外への書き込みの三つ（lethal trifecta）を、一つの会話で揃えない。出すほうを全部は止めない。三つ目が揃う1手を止める
  • 検め方: その会話で読んだものを数える。ゆうべの4手を流して、4手目の公開コメントが止まるのを見る。仕分けの表を変えたら、勤務表の読み出しを「なし」にして、赤になるのを一度見る
  • 止めないもの: Issue を読んで公開の時刻表を直し、PR を出して返事を書くこと。勤務表だけを扱う会話での commit と push。三つ揃っていない会話の作業は、許可の設定のとおりに通す
  • 鷹のせいじゃなかった: 1手ずつしか見ていなかった。誰でも書ける Issue と、勤務表と、公開のコメントが、同じ鍵で、同じ会話に入っていた
  • 自分の言葉で: 全部止めたら、百件とも私の手に戻ってくる。止めるのは三つ目だけ。続きを持っていく紙は、私が書く
