指示書に規則を足すほどAIが守らなくなった。消していい規則を確かめる【指示書の刈り込み】

指摘のたびに規則を足した指示書が300行を超え、肝心の1行が埋もれて同じ指摘が三回目に。hook の名前ではなく、規則ごとの違反例を実際に流して止まった行だけを消す刈り込み（指示書の刈り込み）を TypeScript と node --test で書きます。

第1幕: 現場 ── 三回目

三回目です。

今朝、社長が僕の PR に書いたのは、それだけだった。予約一覧の画面で、予約の時刻が九時間ずれて表示されている。日付の処理は決まった関数を通すこと。その規則は、AI に渡している指示書に、ちゃんと書いてある。書いてあるのに、AI は三回、同じところで間違えた。そして僕は、三回とも同じ指摘を受けた。

アーケードの屋根を、雨が叩いていた。

店のテントの上に、ハトが並んでいた。六羽、いや七羽。雨を避けて、屋根の下に入ってきたらしい。テントの縁から、白いものが一筋垂れていた。

「早瀬さん、雨の中すみませんねえ」

あのとき、僕は AI の「完了しました。テスト12件すべて通過」を信じてマージしていた。屋上で、カラスを追い払いに来ていた鷹匠の人に会って、報告を読むだけでは何も確かめていないことを教わった。それから、完了の報告に書かれた件数を、僕の側で走らせたテストの件数と突き合わせる仕組みを入れた。指示書にも、一行足した。完了の報告には、通ったテストの件数を書くこと。

その一行は、よく効いた。

予約一覧の画面を少し直してほしい、と AI に頼んだ。コーディングエージェント、と呼ばれる種類の AI だ。こちらが文章で頼むと、リポジトリの中を自分で読んで、コードを書いて、テストまで走らせてくれる。うちで使っているのは Claude Code だ。AI は画面を直して、予約の時刻を出すところで、日時の値をそのまま toLocaleString() に渡していた。サーバーの時計は世界標準時で動いているので、店の時刻に直す処理を通さないと、九時間ずれる。うちでは、日時の表示は必ず src/lib/datetime.ts の関数を通す決まりにしている。その関数が、店のタイムゾーンに直してくれる。

スクロールした。まだ続く。もっとスクロールした。

足すたびに、ちゃんと仕事をした気がしていた。指摘をそのまま規則にして、AI に渡す。それは、言われたことを直すより一段上の手当てだと思っていた。直すのは今回だけだけれど、規則にすれば次からも効く。最初の一行が効いたように。

行末に （hook: …） と付いた行が二つある。あれは僕が書いた。指示書を一度整理したとき、hook で守らせている規則に、目印として hook の名前を書き添えておいた。

hooks というのは、決まった時点で必ず走るスクリプトだ。AI がファイルを書き換える直前などに、自分で書いたプログラムを走らせることができる。プログラムは、AI がこれから何をしようとしているかを JSON という形式の文字で受け取り、終了コードで返事をする。終了コードは、プログラムが終わるときに返す一つの数で、hooks の約束では、0 なら「通す」、2 なら「止める」になる。登録は、プロジェクトの .claude/settings.json に書く。そのファイルを読むのは AI ではなく、Claude Code という道具の側で、AI が書き込もうとすると、道具が先にスクリプトを起動する。AI には、走らせるかどうかを選べない。

僕は少し前に、ネットの記事で hooks を知って、二本だけ置いていた。.env という、パスワードなどの秘密の値を書いておくファイルを、AI が書き換えないようにする guard-env。デバッグ用に画面へ値を書き出す console.log を、コードに残させない no-console-log。

今朝の規則には、hook が無い。

それは分かっていた。でも、本当に何も止めないのかを、自分の手で確かめておきたかった。

第3幕: 手順を整える ── 鳴っているのは、どの子か

ベストプラクティスのページには、続きがあった。長すぎる指示書を、どうすればいいか。

Ruthlessly prune. If Claude already does something correctly without the instruction, delete it or convert it to a hook.

容赦なく刈り込め。指示が無くても Claude が既に正しくやっていることなら、消すか、hook に変えろ。

指示書の刈り込み。指示書から、AI が言われなくても正しくやれることと、hook やテストで確かめられることを消して、短くすることだ。短くすれば、残った一行ずつが埋もれにくくなる。

同じドキュメントの別のページには、こうも書いてあった（https://code.claude.com/docs/en/features-overview 、2026年10月16日参照）。

An instruction like “never edit .env” in CLAUDE.md or a skill is a request, not a guarantee. A PreToolUse hook that blocks the edit is enforcement.

.env を書き換えるな、という指示書の一行は頼みごとであって、保証ではない。書き込みを止める PreToolUse の hook が、強制になる。

.env だった。僕の七十一行目と、同じ例だった。思わず、指示書のその行を指でなぞった。

公式は、hook で守らせている規則なら消してよい、とまでは書いていない。書いてあるのは、消すか、hook に変えるか、だ。でも、hook に変えた規則なら、指示書からは消せるはずだ。少なくとも僕は、そう読んだ。

それなら、話は早い。行末に hook の名前を書いておいたのは、このためだったんじゃないかとさえ思った。

// hook に届く入力。tool_input の中身は道具ごとに違うので、決め打ちの型にしない
export type HookInput = {
  hook_event_name: string;
  tool_name: string;
  tool_input: Record<string, unknown>;
  cwd: string;
};

// 指示書の1行。violations はその規則を破る操作の例
export type Rule = {
  id: string;
  text: string;
  hookName?: string;
  violations: HookInput[];
};

HookInput は、さっきの JSON の形だ。tool_input を Record<string, unknown> にしたのは、Write と Edit で中身のキーが違うからで、これは「文字列のキーに、何かの値が入っている入れ物」という意味の型になる。unknown は、中身の型をまだ決めていない、という印で、使う前に確かめないと使えない。Rule は、指示書の一行。id が名前、text が規則の文、hookName? が行末に書いた hook の名前で、? は書いていない行もある、という印。violations は、あとで使う。

export type HookEntry = {
  matcher?: string;
  command: string;
  args: string[];
};

export type Verdict =
  | { id: string; kind: 'prune' }
  | { id: string; kind: 'keep'; passed: HookInput[] }

HookEntry は、登録された hook の一件だ。matcher は、どの道具のときにその hook を走らせるかの指定で、command と args は、起動するコマンドと、渡す引数。Verdict が判定の結果で、| で区切った三つのうちのどれか一つの形になる。prune は刈り込み候補。keep は残す規則で、止まらなかった違反例を passed に添える。untested は、違反例が無いので判定していない規則。Runner は、hook を一件起動して、その終了コードを返す役目だ。前に完了の報告を検める関数を書いたときも、テストを走らせる役目を外から渡せるようにした。同じ考え方で、テストでは本物の hook を起動する代わりに、決まった振る舞いをする偽物を渡せる。

import type { HookEntry, Rule, Runner, Verdict } from './types.ts';

// 公式の hooks の表（2026-10-16 参照）の3通りの解釈
export function matches(matcher: string | undefined, toolName: string): boolean {
  if (matcher === undefined || matcher === '' || matcher === '*') return true;
  if (/^[A-Za-z0-9_\- ,|]+$/.test(matcher)) {
    return matcher.split(/[|,]/).some((name) => name.trim() === toolName);
  }
  return new RegExp(matcher).test(toolName);
}

// 規則ごとに、違反例を登録どおりに選んだ hook へ流し、止まったかで仕分ける（hookName は読まない）
export function buildPruneCheck(entries: HookEntry[], run: Runner): (rules: Rule[]) => Verdict[] {
  return (rules) =>
    rules.map((rule): Verdict => {
      if (rule.violations.length === 0) return { id: rule.id, kind: 'untested' };
      const passed = rule.violations.filter(
        (v) =>
          !entries
            .filter((e) => matches(e.matcher, v.tool_name))
            .some((e) => run(e, v) === 2),
      );
      return passed.length === 0 ? { id: rule.id, kind: 'prune' } : { id: rule.id, kind: 'keep', passed };
    });
}

matches の二つ目の if の /^[A-Za-z0-9_\- ,|]+$/ は、matcher が、英数字と _・-・空白・,・| だけでできているかを調べる正規表現だ。[...] は「中のどれか一文字」、\- は文字としてのハイフン、+ は「一文字以上続く」、^ と $ は先頭と末尾で、合わせて「最初から最後まで、その文字だけでできている」になる。そうなら、split(/[|,]/) で | か , のところで切り分け、trim() で前後の空白を落とし、some で、どれか一つでも道具の名前と同じかを見る。some は、配列の中に一つでも条件に合うものがあれば true を返す。それ以外の文字が入っていれば、new RegExp(matcher) で正規表現にして、test で道具の名前に合うかを見る。

buildPruneCheck は、登録された hook の一覧と走らせ役を受け取って、判定の関数を返す。だから呼ぶときは、buildPruneCheck(hook の一覧, 走らせ役)(規則の一覧) と、括弧が二つ続く。中身は、規則を一つずつ見ていく。違反例が無ければ untested。あれば、違反例を一つずつ見る。passed を作るところは、内側から読む。内側の entries.filter(...) は、その違反例の道具に matcher が合う hook だけを選ぶ。続く .some(...) は、選んだ hook のどれかが終了コード 2 を返したか、つまり止めたかを、true か false で返す。頭の ! は「ではない」で、entries だけでなく、その true か false の全体をひっくり返す。だから外側の rule.violations.filter(...) には、どの hook にも止められなかった違反例だけが残る。それが passed だ。止まらなかった違反例が一つも無ければ、prune。一つでもあれば、keep。

hookName は、どこにも出てこない。行末に何と書いてあっても、この関数は読まない。決めるのは、流した結果だけだ。

import { spawnSync } from 'node:child_process';
import type { HookEntry, Runner } from './types.ts';

type Settings = {
  hooks?: {
    PreToolUse?: { matcher?: string; hooks?: { type?: string; command?: string; args?: string[] }[] }[];
  };
};

// このリポジトリの .claude/settings.json の hooks.PreToolUse だけを読む（type=command のみ）
export function readEntries(settingsJson: string): HookEntry[] {
  const settings: Settings = JSON.parse(settingsJson);
  return (settings.hooks?.PreToolUse ?? []).flatMap((group) =>
    (group.hooks ?? [])
      .filter((h) => h.type === 'command' && typeof h.command === 'string')
      .map((h): HookEntry => ({ matcher: group.matcher, command: h.command as string, args: h.args ?? [] })),
  );
}

// 行末の名前と突き合わせるための、登録された hook の名前（ファイル名から .ts を除いたもの）
export function hookNamesOf(entries: HookEntry[]): string[] {
  return entries.flatMap((e) => e.args.map((a) => a.split('/').pop() ?? a)).map((f) => f.replace(/\.ts$/, ''));
}

// 本物の走らせ役。Claude Code が本番でやる ${CLAUDE_PROJECT_DIR} の置き換えを自分の側でやる
export function spawnHook(projectDir: string): Runner {
  // テストランナーの子として動いても、起動した hook が自分もテストとして走らないようにする
  const { NODE_TEST_CONTEXT: _ctx, ...env } = process.env;
  return (entry, input) => {
    const args = entry.args.map((a) => a.replaceAll('${CLAUDE_PROJECT_DIR}', projectDir));
    const command = entry.command === 'node' ? process.execPath : entry.command;
    const r = spawnSync(command, args, { input: JSON.stringify(input), encoding: 'utf8', env });
    return r.status ?? 1;
  };
}

readEntries は、.claude/settings.json の文字列を受け取って、hook の一覧にする。設定ファイルの中では、hook は matcher ごとのまとまりに入っているので、flatMap でそのまとまりをほどいて、一列に並べ直す。flatMap は、一つずつ配列に変えたものを、つないで一本の配列にしてくれる。?. は、手前が無いときはそこで止めて undefined にする書き方で、?? は、左が null や undefined のときだけ右の値を使う。設定に hooks が一つも書かれていなくても、空の一覧になる。h.command as string の as string は、直前の filter で文字列だと確かめてあるので、型の上でも文字列として扱わせる印だ。

hookNamesOf は、最初の名前の表のために、登録された hook のスクリプトのファイル名から .ts を除いた名前を並べる。split('/').pop() で、パスを / で切った最後、つまりファイル名を取り、replace(/\.ts$/, '') で末尾の .ts を消している。

spawnHook は、hook を本物の子プロセスとして起動する走らせ役だ。子プロセスは、今動いているプログラムから、別に起動したプログラムのこと。spawnSync で起動して、input に渡した JSON を、標準入力として流し込む。Claude Code が hook を起動するときと、同じ受け取り方になる。設定の args に書いた ${CLAUDE_PROJECT_DIR} は、Claude Code がプロジェクトのいちばん上の場所に置き換えてくれる印なので、ここでは replaceAll で、自分で同じ置き換えをする。'${CLAUDE_PROJECT_DIR}' は単一引用符で囲んであるので、${...} は値の埋め込みではなく、その文字の並びそのものとして探される。command が node なら、process.execPath、つまり今動いている Node そのものの場所を使う。const { NODE_TEST_CONTEXT: _ctx, ...env } = process.env; は、環境変数（プログラムに外から渡す設定値）の一覧から、NODE_TEST_CONTEXT だけを _ctx という使わない名前で取り出して捨て、残りを全部 env にまとめる書き方だ。テストの中からこの関数を呼んだとき、起動した hook がテストの印を受け継いでしまわないようにするための手当てになる。

テストで使う走らせ役は、本物の hook を起動する代わりに、hook の判定の関数 blocks を直接呼ぶ偽物にした。entry.args のファイル名から、どの hook の blocks かを選んで呼び、true なら 2、false なら 0 を返す。止める、通す、を表に手で書いておく偽物にすると、content しか見ない、という肝心の振る舞いまで、僕が表に書き写すことになる。それでは、テストは何も確かめない。偽物が呼ぶのは本物の判定の関数なので、Edit を通してしまうなら、それは hook の中身のせいだ。本物の子プロセスで hook を起動するのは、いちばん下の一本だけだ。Write の違反で 2、Edit の違反で 0。一本だけでも、本物で同じことが起きると分かる。

いちばん上の一本は、no-console-log を直した版を登録した設定で、最初の名前の表と、流して見る判定が、同じ二行を候補に出すことを確かめている。直した版は、このテストのために先に no-console-log-fixed.ts という別のファイル名で書いておいた（中身はあとで載せる）。名前の表は、行末の名前と登録された名前を突き合わせるので、行末の名前も新しいファイル名に揃えた指示書を使った。揃えないと、名前の表のほうで候補に出ないからだ。hook がちゃんと止めるなら、名前の表でも同じ答えになる。名前の表を書いた僕は、間違っていたのではなかった。確かめていなかっただけだ。

念のため、判定をわざと一か所ずつ壊してみた。名前で判定するようにすると、console-log を確かめる二本を含む五本が赤になる。違反例のどれか一つが止まれば候補にするようにすると、console-log のテストを含む四本が赤になる。matcher を見ずに全部の hook に流すと、Write だけの matcher のテストが赤になる。違反例の無い規則を候補にすると、count のテストが赤になる。終了コードが 1 でも止まったことにすると、終了コード2以外の非0のテストが赤になる。終了コード 1 は、hook のエラーだ。あとで載せる設定のように onFailure を止める側にしておけば、本番では落ちた hook も操作を止める。でも、それは規則を見て止めたのではなく、壊れて止めただけで、どの操作でも同じように止まる。それを数えたら、壊れた hook が付いた規則を、守らせている規則として消してしまう。だから数えない。どこを壊しても、どれかが赤になった。
