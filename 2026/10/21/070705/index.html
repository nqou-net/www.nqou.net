半年前の私は、AI が出した変更を、どうやって受け入れていたのか。それを、そのままコードに書き写してみることにした。

まず、受け取るものの形を types.ts に決めた。

// skipped は、飛ばされたテスト（skip・todo）の印
export type TestResult = { name: string; passed: boolean; skipped: boolean };
export type TestReport = TestResult[];
export type Verdict = { accepted: true } | { accepted: false; reason: string };

TestResult は、テスト一本の結果。名前と、通ったかどうかと、飛ばされたかどうか。最後の一つはあとで使う。TestReport は、その一覧だ。[] は「その型の配列」という意味になる。Verdict は結論で、受け入れるか、理由を添えて止めるかのどちらかになる。| は TypeScript で「このうちのどれか」を表す書き方だ。受け入れの形には理由が無く、止める形には reason が必須になっている。

import type { TestReport, Verdict } from './types.ts';

// 昨日までの判断: 落ちたテストが無ければ受け入れる
export function acceptReport(report: TestReport): Verdict {
  if (report.every((t) => t.passed)) return { accepted: true };
  return { accepted: false, reason: 'テストが失敗した' };
}

every は、配列の全部の要素が条件を満たすかを調べる関数だ。全部のテストが通っていれば受け入れる。一本でも落ちていれば止める。import type は型の定義だけを読み込む書き方で、読み込み先に .ts まで書いているのは、Node 24 が TypeScript のファイルを、型の記述（型注釈）を取り除くだけでそのまま走らせるからだ。間にファイル名を書き換える変換の段階が無いので、import に書いた名前のファイルがそのまま探される（型が正しいかの検査まではしない）。

じゃあ、どうすればよかったのか。

私は、以前どこかで読んだ、Claude Code の使い方の公式ドキュメントを開き直した。ベストプラクティスのページに、AI に先に質問させる、という節があった。

作り始める前に、AI に質問させる。こちらがどんな機能が欲しいかを短く伝えて、AI のほうから、実装のこと、画面のこと、例外的な場合のこと、気になる点、どちらを取るかの選択を、順に聞いてもらう。答え終わったら、その答えをもとに、AI に仕様書を書かせる。仕様書は、何を作るのかを文章にしたものだ。そして、作らせるのは、仕様書ができたあと、新しいセッションで。セッションは、AI との一回分の会話のことで、新しいセッションの AI は、質問のやりとりを覚えていない。手元にあるのは、書かれた仕様書だけになる。

// 「- R数字: 」で始まる行だけを要件として読む（スコープ外・検証の節の箇条は R で始まらないので読まれない）
export function parseSpec(markdown: string): string[] {
  const ids: string[] = [];
  for (const line of markdown.split('\n')) {
    const m = line.match(/^- (R\d+): /);
    if (m) ids.push(m[1]);
  }
  return ids;
}

文字列から必要なところだけを取り出すことを、パースと呼ぶ。split('\n') で仕様書を一行ずつに分けて、行ごとに match で正規表現に当てる。正規表現 /^- (R\d+): / は、行の頭（^）が - で始まり、R と数字が一つ以上（\d+）続き、コロンと空白が来る行に当たる。丸かっこで囲んだ部分は取り出せて、m[1] に R5 のような番号が入る。当たらない行では m が null になるので、if (m) で飛ばす。スコープ外や検証の節の箇条は - R で始まらないから、何もしなくても読まれない。

import { readFileSync } from 'node:fs';
import { run } from 'node:test';
import { buildAcceptance, parseSpec } from './after.ts';
import type { TestReport, Verdict } from './types.ts';

// Node v24.21.0 で実測。run({ files }) の test:pass / test:fail イベントを集める。
// describe 自身のイベントは details.type === 'suite' なので除く
export async function collectReport(files: string[]): Promise<TestReport> {
  // 親の NODE_TEST_CONTEXT が子のテストランナーの挙動を変えるので外す
  const saved = process.env.NODE_TEST_CONTEXT;
  delete process.env.NODE_TEST_CONTEXT;
  const report: TestReport = [];
  try {
    const stream = run({ files });
    stream.on('test:pass', (e) => {
      if (e.details.type === 'suite') return;
      report.push({ name: e.name, passed: true, skipped: e.skip !== undefined || e.todo !== undefined });
    });
    stream.on('test:fail', (e) => {
      if (e.details.type === 'suite') return;
      report.push({ name: e.name, passed: false, skipped: false });
    });
    // イベントを購読しただけでは流れ切らない。最後まで読み切る
    for await (const _ of stream) { /* drain */ }
  } finally {
    if (saved !== undefined) process.env.NODE_TEST_CONTEXT = saved;
  }
  return report;
}

// check-spec.ts 相当: AI の実装が上がってきたあと、マージの前に手で走らせる
export async function checkSpec(specFile: string, testFiles: string[]): Promise<Verdict> {
  const ids = parseSpec(readFileSync(specFile, 'utf8'));
  return buildAcceptance(ids)(await collectReport(testFiles));
}

test は node:test の関数で、テストの名前と中身を渡して一本登録する。assert は Node に付いてくる、値を確かめるためのモジュールだ。accept は、SPEC.md の fixture から読んだ R1 から R6 の一覧を buildAcceptance に渡して返ってきた、判定の関数だ。assert.deepEqual は、二つの値を中身まで比べる。assertRejected は、結論が「止める」で、理由に狙った文字列が入っているかを見る、テストの中の手伝い役。/R5$/ は「R5 で終わる」という正規表現で、理由に並んだ番号が R5 だけであることを確かめている。

test('本物の run(): skip と todo が skipped: true で届き、describe は結果に混ざらない', async () => {
  const dir = mkdtempSync(join(tmpdir(), 'interview-spec-'));

  const file = join(dir, 'src/orders/orders.test.ts');
  writeFileSync(
    file,
    `import { describe, it } from 'node:test';
describe('注文', () => {
  it('R1: 登録できる', () => {});
  it.skip('R2: 確定前は載らない', () => {});
  it.todo('R3: 22時に出る');
});
`,
  );
  const report = await collectReport([file]);
  const byName = Object.fromEntries(report.map((r) => [r.name, r]));
  assert.equal(report.length, 3);
  assert.equal(byName['注文'], undefined);
  assert.deepEqual(byName['R1: 登録できる'], { name: 'R1: 登録できる', passed: true, skipped: false });
  assert.equal(byName['R2: 確定前は載らない'].skipped, true);
  assert.equal(byName['R3: 22時に出る'].skipped, true);
  // 実際の結果を After に通すと R2・R3 で止まる
  assertRejected(buildAcceptance(['R1', 'R2', 'R3'])(report), /R2, R3/);
});

mkdtempSync(join(tmpdir(), 'interview-spec-')) は、OS の一時置き場に、使い捨ての作業フォルダを作る。join はフォルダの名前をつないでパスにする関数で、mkdirSync の recursive: true は、途中のフォルダもまとめて作る指定だ。writeFileSync に渡しているバッククォートの文字列が、書き出すテストのファイルの中身そのものになる。map は配列の要素を一つずつ別の形に変える関数だ。Object.fromEntries は、[名前, 結果] の組の並びから、名前で結果を引ける表を作る。箱の名前の「注文」が結果に混ざっていないこと、飛ばした二本に skipped が立っていること、それを判定に通すと R2 と R3 で止まることを確かめている。判定の関数は、run() のイベントがこの形で届くことを前提にしているからだ。確かめたのは Node v24.21.0 だった。
