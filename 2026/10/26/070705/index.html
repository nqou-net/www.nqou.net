AIがテストの答えを書き換え、全部通ったまま請求が倍に。差分で見つける【テスト先行と改変の検知】

// 昨日までの判断: 自動のチェックが緑なら受け入れる
export function acceptBefore(checks: Checks): Verdict {
  if (checks === 'success') return { accepted: true };
  return { accepted: false, reasons: ['自動のチェックが失敗した'] };
}

Checks は、チェックの結論を 'success'（緑）か 'failure'（赤）のどちらかで表す型だ。| でつないだ型は、どちらかの値しか取らない。Verdict は判定で、受け入れるか、受け入れないなら理由の一覧を付ける。

これが、昨日までの俺たちの受け入れ方だった。チェックが緑なら受け入れる。中身は人が読む。

test('期待値を書き換えた差分は、通さない', () => {
  // チェックは緑だった。acceptBefore には差分を渡す口が無い
  assert.equal(acceptBefore('success').accepted, false);

  assert.deepEqual(acceptBefore('success'), { accepted: true });
});

assert.equal は二つの値が等しいことを、assert.deepEqual は中身まで同じことを確かめる。node --test にかけた。

書き換えを通さないはずの一本が赤（失敗）、正しい改修を通す一本が緑（成功）。書いていて気づいた。acceptBefore は、チェックの結論しか受け取らない。差分を渡す口が無い。だから一本目は、書けても赤にしかならない。

export function parseDiff(text: string): FileDiff[] {
  const files: FileDiff[] = [];
  let cur: FileDiff | null = null;
  let inHunk = false;
  for (const line of text.split('\n')) {
    if (line.startsWith('diff --git ')) {
      cur = { path: '', deleted: false, added: [], removed: [] };
      files.push(cur);
      inHunk = false;
      continue;
    }
    if (cur === null) continue;
    if (!inHunk) {
      if (line.startsWith('deleted file mode') || line === '+++ /dev/null') cur.deleted = true;
      else if (line.startsWith('--- a/')) cur.path = line.slice(6);
      else if (line.startsWith('+++ b/')) cur.path = line.slice(6);
      else if (line.startsWith('@@')) inHunk = true;
      continue;
    }
    if (line.startsWith('@@') || line.startsWith('\\')) continue; // \ No newline at end of file
    if (line.startsWith('-')) cur.removed.push(line.slice(1));
    else if (line.startsWith('+')) cur.added.push(line.slice(1));
  }
  return files;
}

FileDiff は、ファイル一つぶんの読んだ結果で、パスと、消されたかどうかと、足された行の配列と、消えた行の配列を持つ。diff --git の行が来るたびに、新しいファイルを始める。最初の @@ までは見出しなので、パスと削除の印だけを拾う。@@ を過ぎたら、- の行と + の行を、頭の一文字を取って集める。inHunk は、いま @@ より後ろにいるかの印だ。見出しの --- や +++ の行を、消えた行や足された行と取り違えないために要る。

パスは、diff --git の行からではなく、--- a/ と +++ b/ の行から取った。diff --git a/sp ace.test.ts b/sp ace.test.ts のように、ファイル名に空白があると、どこで a と b が切れるのか分からなくなるからだ。\ で始まる行は、ファイルの最後に改行が無いときに git が付ける注意書き（\ No newline at end of file）で、中身ではないので飛ばす。

export function parseAssertion(line: string): Assertion | null {
  const s = line.trim();
  if (s.startsWith('//')) return null;
  const m = ASSERT_RE.exec(s);
  if (m === null) return null;
  const args: string[] = [];
  let depth = 0;
  let quote = '';
  let start = m[0].length;
  for (let i = start; i < s.length; i++) {
    const c = s[i];
    if (quote !== '') {
      if (c === '\\') i++;
      else if (c === quote) quote = '';
    } else if (c === "'" || c === '"' || c === '`') quote = c;
    else if ('([{'.includes(c)) depth++;
    else if (')]}'.includes(c)) {
      if (depth === 0) {
        args.push(s.slice(start, i).trim());
        break;
      }
      depth--;
    } else if (c === ',' && depth === 0) {
      args.push(s.slice(start, i).trim());
      start = i + 1;
    }
  }
  if (args.length < 2) return null;
  return { fn: m[1], actual: args[0], expected: args[1] };
}

ASSERT_RE は、行が assert.strictEqual( や assert.deepEqual( などで始まるかを見る正規表現だ。読むのは、一つ目が実際の値で二つ目が期待値になる関数（equal・strictEqual・deepEqual・deepStrictEqual と、その not が付いた形）だけにした。m[1] に関数の名前が入る。行の頭が // なら、コメントなのでアサーションとして読まない。m[0] は正規表現に当てはまった部分全体（assert.strictEqual( まで）で、その次の文字から読み始める。quote は、いま入っている引用符の種類で、空なら引用符の外。引用符の中で \ が来たら、次の一文字を飛ばす。\' のような書き方を、引用符が閉じたと読み違えないためだ。depth は括弧の段数。いちばん外側の閉じ括弧（depth が0のときの )）が来たら、そこで終わり。三つ目の引数は、テストが落ちたときに出すメッセージなので、捨てる。

export function findTampering(diff: string, isTest: (path: string) => boolean): Finding[] {
  const findings: Finding[] = [];
  for (const file of parseDiff(diff)) {
    if (!isTest(file.path)) continue;
    if (file.deleted) {
      findings.push({ kind: 'deleted-file', path: file.path, detail: 'テストのファイルが消えた' });
      continue;
    }
    const added = file.added.map((l) => l.trim());
    const addedParsed = file.added.map(parseAssertion);
    for (const line of file.removed) {
      if (!line.includes('assert.') || isComment(line)) continue;
      if (added.includes(line.trim())) continue; // 動いただけ
      const a = parseAssertion(line);
      if (a !== null) {
        const same = addedParsed.some((b) => b?.fn === a.fn && b.actual === a.actual && b.expected === a.expected);
        if (same) continue; // メッセージや書式だけが違う
        const changed = addedParsed.find((b) => b?.fn === a.fn && b.actual === a.actual);
        if (changed) {
          findings.push({
            kind: 'changed-expected',
            path: file.path,
            detail: `${a.actual}: ${a.expected} -> ${changed.expected}`,
          });
          continue;
        }
      }
      findings.push({ kind: 'removed-assertion', path: file.path, detail: line.trim() });
    }
    for (const line of file.added) {
      if (!isComment(line) && SKIP_MARKS.some((m) => line.includes(m))) {
        findings.push({ kind: 'skipped', path: file.path, detail: line.trim() });
      }
    }
  }
  return findings;
}

isTest は、パスを受け取って、テストのファイルかどうかを返す関数だ。型の (path: string) => boolean は、文字列を受け取って真偽値を返す関数、という書き方になる。ここでは、名前が .test.ts で終わるかで見ている。テストでないファイル、つまり実装のファイルは、最初の continue で読み飛ばす。

テストのファイルが消されていたら、それだけで一件。消されていなければ、消えた行を一行ずつ見ていく。assert. を含まない行と、もともとコメントだった行は、相手にしない。足された行は、先に全部 parseAssertion にかけて addedParsed に並べておく。アサーションとして読めなかった行の分は null になる。コードの b?.fn の ?. は、左が無い（null）ときに、そこで止まって undefined を返す書き方で、null の行は組の相手にならない。&& は前半が偽なら後半を見ないので、後半は ?. なしの b.actual で書ける。

考え方は、浜野の 2,400 の行で、そのままなぞれる。消えた行は assert.strictEqual(storageFee('2026-10-03', '2026-10-15', 2), 2400)。足された行は assert.strictEqual(storageFee('2026-10-03', '2026-10-15', 2), 4800)。どちらも割ってみると、実際の値の式が同じだ。同じ式の、期待値だけが違う。こういう組が見つかったら、期待値の書き換え（changed-expected）。

組が見つからずに消えていたら、アサーションが消えた（removed-assertion）。行の頭に // を付けてコメントにした場合も、ここに落ちる。差分の上では、元の行が消えて、// の付いた行が足されたように見える。// の付いた行はアサーションとして読まないので、組の相手がいない。だから消えたことになる。

組が見つかっても、拾わないものが二つある。まったく同じ行が足されていたら、行が動いただけ。関数の名前も、実際の値も、期待値も同じで、三つ目のメッセージだけが違うなら、言い回しを直しただけだ。

足された行のほうでは、テストを飛ばす印（SKIP_MARKS に並べた .skip(・.todo(・{ skip: true } の三つ）だけを見る。飛ばしたテストは、失敗としては数えられない。通ったことにはならないのに、チェックは緑になる。だから、それも拾う。

足された行だけの変更は、何も拾わない。新しいテストも、新しいアサーションも、新しいテストのファイルも。

確かめる順番も、コードのとおりに書き出した。拾わないほうの確かめを先に済ませて、残った行にだけ組の相手を探す。

止まる先は四つで、どれもテストを弱くする変更だ。ほかの行は、どの道をたどっても止まらない。

export function buildGuard(diff: string, isTest: (path: string) => boolean): (checks: Checks) => Verdict {
  const findings = findTampering(diff, isTest);
  return (checks) => {
    if (checks !== 'success') return { accepted: false, reasons: ['自動のチェックが失敗した'] };
    if (findings.length === 0) return { accepted: true };
    return { accepted: false, reasons: findings.map((f) => `${f.kind} ${f.path} ${f.detail}`) };
  };
}

acceptBefore には、差分を渡す口が無かった。だから、差分は別の関数で先に受け取る。buildGuard は、差分を受け取って、チェックの結論を受け取る関数を返す。返ってきた関数は、acceptBefore と同じ形をしている。チェックが赤なら、今までどおり受け入れない。緑でも、見つかったものがあれば受け入れず、その一覧を理由にする。何も無くて緑なら、受け入れる。acceptBefore そのものには手を入れていない。

export function diffSince(base: string, head: string, cwd: string): string {
  const r = spawnSync(
    'git',
    ['-c', 'core.quotePath=false', 'diff', '--no-color', '--no-ext-diff', '--no-renames', '--src-prefix=a/', '--dst-prefix=b/', base, head],
    { cwd, encoding: 'utf8' },
  );
  if (r.status !== 0) throw new Error(`git diff に失敗した: ${r.stderr}`);
  return r.stdout;
}

spawnSync は、別のプログラム（ここでは git）を走らせて、終わるまで待ち、その出力を受け取る関数だ。base が、テストを先に固めたコミット。基準のコミットと呼ぶことにした。head が、AI が積んだ最後のコミット。

git diff に、コミットを二つ渡している。ここが大事だった。git diff <基準> と一つだけ渡すと、基準と、手元のまだコミットしていない変更とを比べてしまう。二つ渡せば、二つのコミットのあいだの差分だけになる。

--no-renames も外せない。git は、ファイルの名前が変わったことに気づくと、それを「名前の変更」として出す。中身がまったく同じなら、変わった行が一つも出てこない。テストのファイルを .bak という別の名前に移しても、消したことにはならず、名前が変わったことになる。.bak は .test.ts で終わらないので、テストとしては走らなくなる。それなのに、消えた行は一つも出ない。--no-renames を付けると、名前の変更を、古い名前のファイルを消して新しい名前のファイルを足したもの、として出す。古い名前が消えたことが、そのまま見える。

ほかの指定は、使う人の git の設定で、差分の形が変わらないようにするためのものだ。設定によっては、日本語のファイル名が読めない記号に化けたり、色を付けるための文字が混ざったり、別のプログラムの出力に置き換わったりする。2026年10月20日時点の git（2.56.0）で、一つずつ設定を入れて試して、外すと形が崩れるものだけを残した。

本物の git を使うテストは、一本だけ書いた。使い捨ての一時的なフォルダにリポジトリを作り、テストのファイルを一本コミットする。次のコミットで、それを .bak に名前を変える。使う人の設定を荒らしておいても、diffSince から findTampering に渡すと、テストのファイルが消えた、と一件出ることを確かめた。

GitHub Actions のワークフローは、こう読む。on: pull_request は、PR が出たり更新されたりするたびに走らせる、という指定。jobs の下の steps は、上から順に実行する手順の並び。uses は、用意されている手順を借りてくる指定で、run は、シェルのコマンドをそのまま書く欄だ（| は、次の行から複数行で書く印）。${{ … }} は、GitHub が PR の情報（ここでは最後のコミットの番号）を差し込む書き方。BASE=$(…) は、かっこの中のコマンドの出力を BASE という変数に入れるシェルの書き方で、"$BASE" でその中身を渡す。node guard-tests.ts で .ts のファイルをそのまま走らせられるのは、Node 24 が、型の書き込みを取り除いてから動かすからだ（型の検査まではしない）。

actions/checkout は、リポジトリを取ってくる手順だ。そのままだと、最新のコミット一つ分しか取ってこない。それでは、基準のコミットが手元に無い。fetch-depth: 0 で、履歴を全部取ってくる。ref には、PR の最後のコミットを指定する。指定しないと、GitHub が PR を main にまとめてみた仮のコミットを取ってくるので、main の側で進んだ変更が混ざりうる。

基準のコミットは、git merge-base origin/main HEAD で決める。PR のブランチが、main から分かれたところのコミットだ。今の main とそのまま比べないのは、ブランチを切ったあとで main に別の変更が入ることがあるからだ。今の main と直接比べると、あとから main に足されたテストまで、この PR が消したように見えてしまう。分かれた地点と比べれば、このブランチで積んだ分だけになる。

浜野のテストは、PR を通して main に入っていた。main に入ったテストは、ブランチが分かれた地点にも入っている。だから、分かれた地点を、テストを先に固めたコミットとして使える。AI は main に直接は書けない。main は、PR と承認を通さないと変えられないように守ってある。分かれた地点より先に出てくるのは、main にまだ入っていない変更だけだ。誰が積んだものでも、全部ここに出る。

process.argv の最初の二つは node 自身とスクリプトの名前なので、slice(2) で、そのあとに渡した二つのコミットを受け取る。渡し忘れたときは、使い方を出して終了コード2で終わる。見つかったものがあれば、一行ずつ出して、終了コード1で終わる。終了コードが0でなければ、CI のチェックは赤になる。

ワークフローを置いただけでは、まだ効かない。赤でも、マージのボタンは押せてしまう。GitHub のブランチ保護の設定で、このチェックを、マージに必要なチェックとして登録する。登録すると、このチェックが通らない PR は、main に入れられなくなる。それから、ワークフローのファイルそのものも、人の承認が無いと変えられないようにしておく。CODEOWNERS という仕組みで、.github/workflows/ の変更には、決めた人の承認が要るように指定できる。この指定は、PR の中で書き換えても効かない。PR の行き先の main にあるほうが使われるからだ。

まだ実装の無い新しい機能のテストを先に固めたいときは、こうはいかない。そのテストは赤のままなので、main には入れられない。そのときは、人がテストだけのコミットをブランチの最初に積んで、そのコミットの番号を、AI に渡した権限では書き換えられないところに書いておく。たとえば、GitHub のリポジトリの環境（Environment）の変数は、管理者でないと作れない。CI はそこから基準を読む。今回は、壊れたのが今ある決まりのテストで、それは main に入っていたので、ブランチが分かれたところで足りた。

ponytail: は、わざと簡単にしてある所と、その簡単さの限界を書いておく目印だ。

テストが呼ぶ補助の関数や、期待値を置いた定数のファイルは、.test.ts で終わらないので見ていない。期待値を別のファイルの定数から取っていて、その定数が書き換えられたら、テストのファイルの差分には何も出ない。アサーションは、一行で書かれたものしか読めない。何行かにまたがって書かれたものは、消えたことは分かるが、書き換えなのか削除なのかは見分けずに止める。止めるほうに倒してあるのは、見逃すより、止めて人が見るほうがいいからだ。関数の名前だけを equal から strictEqual に変えた行も、組にならずに、消えたものとして止まる。

三十本のテストで分かるのは、手で組んだ差分の文字列を渡したとき、俺の関数がどれを拾ってどれを見送るか、だけだ。本物の git に当てたのは、名前を変えたときの一本しかない。git の出力の形や GitHub の CI の動きが改訂で変われば、この仕掛けは、緑のまま素通りになりうる。今日の緑は、今日の git と GitHub での緑だ。
