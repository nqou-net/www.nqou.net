src/shipping/cool-label.ts(3,10): error TS2305: Module '"hakobi-sdk"' has no exported member 'createShipment'.

行の頭の src/shipping/cool-label.ts(3,10) は、エラーのあったファイルと、その3行目の10文字目、という意味だ。

このサイトは TypeScript で書いている。TypeScript は、JavaScript に型を付けた言語だ。公開する前に、tsc というコンパイラで、型が合っているかを調べてから JavaScript に変換する。この工程を、うちではビルドと呼んでいる。Node.js（以下 Node）は、Node 24 なら .ts をそのまま動かせる。ただ、そのときは型を取り除いて動かすだけで、型は調べない。だから、手元で画面が動いても、ビルドで落ちることがある。

TS2305 は、そのモジュールに、その名前の export が無い、というエラーだ。ライブラリは、外から使ってほしい関数や値に名前を付けて、外に出している。これを export と言う。使う側は、import { createShipment } from 'hakobi-sdk' のように、名前で取り込む。エラーは、hakobi-sdk は createShipment という名前を外に出していない、と言っていた。

^5.3.0 は、5.3.0 以上で、6 にはならない範囲なら、新しいものを入れてよい、という指定だ。版の番号は、たいてい三つの数字でできていて、先頭の数字をメジャーバージョンと呼ぶ。先頭の数字が変わるときは、名前が消えたり、変わったりすることがある。だから、先頭が 5 のまま、と決めてある。

// 貼ったページの見出しから、版と名前を抜く
//   # <pkg> v<version> ...
//   ### <name>(...)
export function buildNotesFromDoc(doc: string): ApiNotes {
  const head = doc.match(/^# (\S+) v(\S+)/m);
  if (!head) throw new Error('先頭の見出しに版がない');
  const names = [...doc.matchAll(/^### ([^\s(]+)/gm)].map((m) => m[1]).sort();
  return { pkg: head[1], version: head[2], names };
}

リファレンスのページは、先頭の見出しに # hakobi-sdk v6.0.0 リファレンス のように版が入っていて、関数ごとに ### createShipment(options) のような見出しが付いている。正規表現で、その二つを拾う。\S+ は空白以外の文字の続き、[^\s(]+ は空白と ( 以外の文字の続きだ。末尾の m は行ごとに ^（行の頭）を効かせる指定、g は一致するものを全部探す指定。matchAll は、一致したものを全部取り出す。[...] で、それを配列に広げている。m[1] や head[1] は、括弧で囲んだ部分に一致した文字列だ。

昨日貼ったページを渡すと、版は 6.0.0、名前は七つ出てきた。COOL_TYPES、cancelShipment、createShipment、quoteRates、schedulePickup、trackShipment、validateAddress。昨日の AI は、この七つを、使える名前として受け取っていたことになる。

test('資料の名前は、入っている版にすべて実在する', () => {

  for (const name of installed.names) {

test('資料の版は、入っている版と同じ', () => {
  assert.equal(notes.version, installed.version);
});

notes は、貼ったページから作った資料だ。assert.ok は、中身が真でなければ失敗にする。二つ目の引数は、失敗したときに出す文だ。一本目は、資料に無い名前が混じっていないか（今朝の事故そのもの）を見る。二本目は、使える名前が資料から漏れていないか（書き忘れ）を見る。片方だけだと、もう片方のずれを見逃す。node --test にかけた。

// 依存の名前空間を読む（import() は自分の位置から探すので、dir の node_modules を指す絶対パスを先に得る）
export async function loadNamespace(name: string, dir: string): Promise<Record<string, unknown>> {
  const abs = createRequire(join(dir, 'package.json')).resolve(name);
  return await import(pathToFileURL(abs).href);
}

await import() は、プログラムを動かしている途中で、モジュールを読み込む書き方だ。読み込むと、そのモジュールが外に出している名前が全部入ったオブジェクトが返ってくる。これを名前空間と呼ぶ。名前空間の中では、export の名前がそのままキーになっている。

ただ、import('hakobi-sdk') と名前だけ渡すと、Node は、この関数を書いたファイルの位置から node_modules を探しに行く。テストでは、一時的なディレクトリに置いた見本のパッケージから読みたい。ほかのプロジェクトの依存も読めるようにしておきたい。だから、どこの node_modules を読むかを、dir で外から渡せるようにした。そこで、createRequire を使う。指定したディレクトリの package.json を起点にして、パッケージの探し方を作る関数だ。その resolve で、dir の node_modules にある hakobi-sdk の、本体のファイルの絶対パスを得る。createRequire・join・pathToFileURL、あとで使う readFileSync は、どれも Node に最初から入っている関数だ。戻り値の型 Promise<Record<string, unknown>> は、文字列のキーに何かの値が入ったオブジェクトを、あとで渡すという約束、くらいに読めばいい。pathToFileURL で、そのパスを import() が読める URL の形に直してから、読み込む。

// 素朴版から、default と 'module.exports' を除いた版（default の中身はまだ足さない）
export function namesExclude(ns: object): string[] {
  return Object.keys(ns)
    .filter((k) => k !== 'default' && k !== 'module.exports')
    .sort();
}

export function namesOf(ns: Record<string, unknown>): string[] {
  const names = Object.keys(ns).filter((k) => k !== 'default' && k !== 'module.exports');
  const d = ns.default;
  if ((typeof d === 'object' && d !== null) || typeof d === 'function') names.push(...Object.keys(d));
  return [...new Set(names)].sort();
}

typeof は、値の種類を文字列で返す。default がオブジェクトか関数なら、その中のキーを足す。null も typeof では 'object' になるので、別に除いている。CJS では、モジュール全体が一つの関数になっていることもあるので、関数も見ている。push(...配列) は、配列の中身を一つずつ足す書き方だ。CJS の SDK は、default の中にも同じ名前が入っているので、名前が二回ずつ出てくる。new Set は、重複を除いた集まりを作る。それを [...] で配列に戻して、並べる。

// dir の node_modules に入っている依存そのものから、名前と版を取り出す
// ponytail: dir 直下の node_modules だけ読む（pnpm の非 hoist 構成や親ディレクトリの node_modules は読めない）。そういう構成なら resolve の結果から package.json を探しに上る
export async function buildNotesFromPackage(name: string, dir: string): Promise<ApiNotes> {
  // import() は自分のファイルの位置から探すので、dir の node_modules を指す絶対パスを先に得る
  const abs = createRequire(join(dir, 'package.json')).resolve(name);
  const ns = await import(pathToFileURL(abs).href);
  // resolve(name + '/package.json') は exports を持つ依存で ERR_PACKAGE_PATH_NOT_EXPORTED になるので、直接読む
  const pkg = JSON.parse(readFileSync(join(dir, 'node_modules', name, 'package.json'), 'utf8'));
  return { pkg: name, version: pkg.version, names: namesOf(ns) };
}

readFileSync でファイルを文字列として読み、JSON.parse でオブジェクトに直して、version を取る。ponytail: で始まるコメントは、わざと手を抜いたところの印だ。この関数は dir のすぐ下の node_modules しか見ない。依存を別の場所に置く道具を使っている構成や、親のディレクトリの node_modules に入っている依存は読めない。うちのサイトは、依存がすぐ下にあるので、これで足りる。

// 資料を Markdown にする。引数と型は載せない（名前と版だけ）
export function renderNotes(notes: ApiNotes): string {
  const lines = [
    `# ${notes.pkg} ${notes.version} の API 資料`,
    '',
    ...notes.names.map((n) => `- ${n}`),
    '',
    `引数と型はこの資料に無い。node_modules/${notes.pkg}/index.d.ts を見ること。`,
    '',
  ];
  return lines.join('\n');
}

指示書のファイル（CLAUDE.md）の中に @API-NOTES.md と書いて、取り込ませる手もある。ただ、公式の説明によれば、指示書に取り込んだファイルは、起動のたびに全文が読み込まれる。毎回コンテキストを使うし、作った日の資料が、黙って毎回渡されることになる。頼むときに、頼む文で渡す。

MCP で渡すなら、プロジェクトで共有するサーバーは、リポジトリのいちばん上の .mcp.json に登録する。claude mcp add に --scope project を付けて追加すると、ここに書かれる。ドキュメントを返すサーバーを使うなら、頼む文に版を書く。書き忘れれば、サーバーは、たぶん新しいほうを返す。わたしの資料は、入っている版から機械が作るので、版を書き忘れることが無い。

AI に、@API-NOTES.md を付けて、発送の処理を入っている版で書き直すよう頼んだ。AI は、createShipment を createLabel に、quoteRates を getRates に置き換えて、schedulePickup を使っていたところは、集荷の日時を画面で選ばせるのをやめる形に直した。ここに書いたのは、今日のわたしの頼みに対して返ってきたものだ。同じ資料を付けて頼み直しても、毎回この書き方になるとは限らない。

ビルドを走らせた。

TS2305 は、一つも出なかった。存在しない名前のエラーは、全部消えた。

エラーは、三つ残っていた。三つとも、createLabel に渡しているオブジェクトの、項目の名前が違う、というものだった。v6 の書き方の項目名が、そのまま残っていた。

資料には、名前しか無い。どんな形のものを渡せばいいかは、資料の最後の一行が指している index.d.ts に書いてある。わたしは、AI に index.d.ts を読ませて、三つを直してもらった。もう一度ビルドを走らせると、今度は通った。16時40分だった。

ビルドが通るまでの流れを、昨日の夜の流れと並べて、ノートに書き出してみた。

テストで確かめたのは、資料の中身までだ。資料に載る名前は、入っている版に実在するものだけで、入っている版の名前は全部載る。版も、入っている版のものになる。ページが入っている版のものなら、ページから作った資料と同じ中身になる。

AI がそれで間違えなくなる、とは言えない。ビルドに残った三つが、その一つだ。資料が伝えるのは名前と版だけで、引数も、型も、使い方も伝えない。そこは、index.d.ts と、tsc のビルドで確かめるしかない。AI は、資料に無い名前を、推し量って書いてくることもありうる。資料は AI に渡す入力で、AI の出したものを弾く仕掛けではない。

もう一つ。七本の緑が言っているのは、わたしが手で作った見本のパッケージを、わたしの関数がどう読むか、だけだ。Node のモジュールの読み方や、Claude Code の @ の扱いが改訂で変われば、この仕掛けは、黙って効かなくなりうる。今日の緑は、今日の Node と今日の Claude Code での緑だ。

放鷹カード

  • 合図: 最新ドキュメントを渡す。入っている依存から、名前と版を取り出して資料を作る。頼むときに、その資料を付ける
  • 検め方: 資料の版が、入っている版と同じか。資料の名前が、入っている版に実在するか。引数と型は、index.d.ts と tsc で
  • 止めないもの: ページが入っている版のものなら、ページから作ったのと同じ資料になる。入っている版の名前は、一つも削らない
  • 鷹のせいじゃなかった: 公式のページを、入っている版と比べずに渡した。ページに合わせて、入っているほうを上げようとした
  • 自分の言葉で: AI に渡す資料は、ページからではなく、node_modules から作る。伝わるのは名前まで。形は index.d.ts とビルドで見る
