槙村さんがすぐに言った。腕を組んでいる。

二対一だった。俺はむっとして、言い返した。

槙村さんが黙った。

鷹宮さんも、すぐには何も言わなかった。グラウンドを一周してきた整備の車が、三塁ベースの横を通りすぎるくらいの間があった。

「……違った。今の、なし」

それだけだった。言い訳もしなかったし、言い直しもしなかった。年下の業者の人が、あっさり自分の見立てを引っ込めたのが意外で、俺は拍子抜けした。言い返す先が、急に無くなった。

俺はパソコンの蓋を開け直した。腹立ちの行き場が無くなったので、代わりに、昨日までの俺たちが何をしていたのかを書き出してみることにした。俺たちの目は、どこに向いていて、どこに向いていなかったのか。

AI が出してきた変更を受け取るときに、俺たちが見ていたものは二つある。テストが通ったかどうか。それと、変わったファイルの一覧。一覧のほうは、git diff --name-status で出せる。

git diff --name-status は、変更されたファイルの名前と、変更の種類を、一行に一つずつ出すコマンドだ。行の頭の一文字が種類で、M は中身の変更、A は追加、D は削除。種類のあとにタブ（\t）を一つ挟んで、ファイルのパスが続く。PR の画面に出ていた42行の一覧は、これと同じものだった。

まず、受け取るものの形を types.ts に決めた。

1
2
3

// nameStatus は `git diff --name-status --no-renames` の出力そのもの
export type ChangeSet = { testsPassed: boolean; nameStatus: string };
export type Verdict = { accepted: true } | { accepted: false; reason: string };

ChangeSet は、AI が出した変更のひとまとまり。テストが通ったかどうかと、ファイルの一覧の文字列を持つ。--no-renames については、あとで書く。Verdict は結論で、通すか、理由を添えて止めるかの二通り。| は「どちらかの形」という意味の TypeScript の書き方で、止めるときには必ず理由がつく。

import type { ChangeSet, Verdict } from './types.ts';

// 昨日までの判断: テストが通っていれば受け入れる。nameStatus は受け取っているが見ていない
export function acceptChange(change: ChangeSet): Verdict {
  if (change.testsPassed) return { accepted: true };
  return { accepted: false, reason: 'テストが失敗した' };
}

先頭の import type で読み込んでいるのは型の定義だけ。読み込み先に .ts の拡張子まで付けているのは、変換の手間を挟まずに Node へ直接渡すからだ。ふつう TypeScript は JavaScript に変換してから動かすけれど、Node 24 は型の書き込みを取り除くだけで .ts をそのまま走らせられる（型が正しいかどうかの検査まではしない。enum のように、取り除くだけでは動かない書き方は使えない）。

書いてみると、本当にこれだけだった。テストが通っていれば受け入れる。一覧は受け取っているのに、見ていない。42ファイルの PR を入れたら、テストは緑だから、受け入れる。決済の端数が変わっていても、受け入れる。

テストを書いて走らせた。頼んでいない決済のファイルを含む変更を止めるかどうか、を確かめるテストだ。昨日までの俺たちの関数は、止めなかった。テストは赤くなった。

「ひどいでしょう」

自分で書いておいて、自分で言った。槙村さんは首を振った。

「ひどくはないよ。私だって、昨日まではこれでいいと思ってたもの」

それは、たぶん本当だった。外注の業者は、テストをちゃんと残していってくれた。売店の画面にも、注文にも、決済にも、テストがある。何か壊れたら、どれかが落ちるはずだった。42ファイルを毎回全部読む人手は、うちには無い。それに AI は、たいていは頼んだところを直す。今までの小さな修正では、一度も余計なことはしなかった。

「でも、端数が変わったのに、なんでテストは通ったの」

槙村さんが聞いた。決済の人の顔になっていた。

俺は tax-rounding.ts のテストを開いた。税込の金額が計算できるか、マイナスにならないか、は確かめていた。でも、1円未満の端数をどちらに丸めるかを確かめるテストは、無かった。

「丸め方のテストが、無いです」

槙村さんは小さく息を吐いた。外注の業者と決済の仕様を詰めたのは、この人だ。視線が一瞬だけ画面から外れて、膝の上のペンに落ちた。口には、何も出さなかった。

そのとき、俺はようやく気づいた。

テストが通ったということは、壊れていないということだ。少なくとも、テストが見ている範囲では。でもそれは、触ったファイルが、頼んだ範囲に収まっていたかどうかとは関係が無い。テストは、範囲については何も言わない。番号表示を直してくれと頼んで、決済まで書き換えられても、決済のテストに穴があれば、全部が緑のまま通ってくる。

上を見ると、鷹宮さんが立ち上がっていた。また鷹を手袋に据えたまま、通路を数段上っていく。売店の屋根の上では、ハトの群れが日なたに並んでいる。

「あの」

俺は声をかけた。

「なんで飛ばさないんですか。ハト、あそこにいるのに」

鷹宮さんは立ち止まって、振り返った。

それで終わりかと思った。でも俺は、結論が欲しかった。

第3幕: 手順を整える ── 放す前に、範囲を決める

AI も、このコードを知らなかったんだ。

俺はパソコンの画面を見たまま、そう思った。

俺が知らなかったように、AI も、外注の業者が書いたこのコードを知らなかった。知らないまま、番号表示を直せと言われて、書き始めた。書きながらファイルを開いて、開いた先で、字下げが揃っていないのを見つけて揃えた。使われていない関数を見つけて消した。金額の表示の書き方が番号表示と違うのを見つけて、揃えようとして、端数の処理まで手を入れた。一つ一つは、たぶん親切のつもりだった。

触る範囲を決めていたのは、誰だったのか。俺じゃない。俺は、どこを触ればいいかを知らないまま頼んだ。範囲を決めていたのは、書いている最中の AI だった。書きながら、「ついでに」が一つずつ増えていった。

じゃあ、範囲を書く前に決めればいい。でも、俺はどこを触るべきかを知らない。知らない人が、書く前に範囲を決められるのか。

調べると、この手順にはちゃんと名前があった。探索 → 計画 → 実装。いきなり AI に書かせずに、まずコードを読ませる（探索）。次に、どのファイルを、なぜ、どう変えるかを、計画として書かせる（計画）。人がその計画を読んで承認してから、初めて書かせる（実装）。Claude Code には、このための plan mode がある。plan mode は、AI にコードを読むことと計画を書くことだけをさせて、人が承認するまでソースコードを編集させないモードだ。

Claude Code の公式ドキュメントの Best practices には、この手順がそのまま節の名前になっている。

Explore first, then plan, then code

その下に、理由が一文で書いてあった。

Letting Claude jump straight to coding can produce code that solves the wrong problem.

（Claude Code docs「Best practices」、2026年10月14日参照）

いきなり書かせると、間違った問題を解くコードになりうる。昨日の PR は、まさにそれだった。番号表示を直すはずが、決済の端数まで「直して」いた。

ただ、同じページには、逆のことも書いてあった。

If you could describe the diff in one sentence, skip the plan.

差分を一文で言えるなら、計画は要らない。打ち間違いを直すとか、ログを1行足すとかいった、範囲がはっきりした小さな修正なら、計画を立てる手間のほうが無駄になる、と。

番号表示の修正は、一文で言える。3桁でずれるのを直す。だから俺は、計画なんて大げさだと思っていた。でも、一文で言えたのは、何を直したいか、のほうだった。どこを触るか、は一文どころか、一語も言えなかった。

公式のページは、計画がいちばん役に立つ場面も挙げていた。その一つが、これだった。

when you’re unfamiliar with the code being modified

変更するコードに不慣れなとき。外注のコードを一度もちゃんと読んだことのない俺は、まさにそこにいた。

鷹宮さんが鷹を飛ばさないのも、同じことなんだと思う。初めての球場で、どこに屋根があって、どこに照明塔があって、どこまでが仕事の場所かを知らないまま放したら、鷹は見えたものを追う。だから先に、拳に乗せたまま場所を見せて回る。放すのは、そのあとだ。

俺は、その場で作業用のブランチを切り直した。昨日の PR はいったん脇に置いて、同じ依頼を、今度は plan mode でやり直す。

頼む文に、一つ決まりを足した。計画の最後に、変更するファイルの節を作らせる。

/plan 受け取り口の番号表示が3桁になると桁がずれる。直す計画を立てて。
計画の最後に「## 変更するファイル」の節を作り、1行に1ファイル、
「- 変更: パス」「- 新規: パス」「- 削除: パス」の形で書くこと。
名前を変えるファイルは、旧パスの削除と新パスの新規の2行で書くこと。

頭の /plan は、この一回の依頼を plan mode で始める、という指定だ。この節の形は、俺が決めた取り決めだ。plan mode の計画は Markdown の文章で返ってくるけれど、どういう章立てにするかの決まりは無い。ただ、公式のページにある計画の例でも、AI に What files need to change? と、どのファイルを変えるかを聞いている。その問いの答えを、あとで機械が読める形に固めておくことにした。

AI は、しばらくファイルを読んでいた。画面に、開いたファイルの名前が次々に流れる。売店の画面、注文、受け取り口の表示、決済。何も書き換えずに、読むだけ。やがて計画が返ってきた。

番号を表示している部分の説明。3桁で桁がずれる原因。番号を桁揃えする小さな関数を新しく作ること。テストの追加。そして最後の節。

4行目を見て、また出た、と思った。

正直に言うと、計画を見ても、俺に何かが判断できるとは思っていなかった。どのファイルが要るのか分からないから頼んだのに、計画を読んで判断しろと言われても、と。

でも、計画の本文に、4行目の理由が書いてあった。金額の表示の書き方を、番号表示と揃えるため。

手が止まった。

番号の表示に、税込の端数は要らない。それは、コードを知らない俺にも分かる。番号は番号で、お金じゃない。

「これ」

槙村さんが、身を乗り出して4行目を指した。

import type { ApprovedPlan, ChangeSet, FileChange, PlannedFile, Verdict } from './types.ts';

const KINDS: Record<string, PlannedFile['kind']> = { 変更: 'modify', 新規: 'add', 削除: 'delete' };
const STATUS_TO_KIND: Record<string, PlannedFile['kind']> = { M: 'modify', A: 'add', D: 'delete' };

// 「## 変更するファイル」の節の「- 変更|新規|削除: パス」行だけを読む。それ以外の行は読まない
export function parsePlan(markdown: string): ApprovedPlan {
  const entries: PlannedFile[] = [];
  let inSection = false;
  for (const line of markdown.split('\n')) {
    if (line.startsWith('## ')) {
      inSection = line.trim() === '## 変更するファイル';
      continue;
    }
    const m = inSection && line.match(/^- (変更|新規|削除): (\S+)\s*$/);
    if (m) entries.push({ kind: KINDS[m[1]], path: m[2] });
  }
  return { entries };
}

文字列の中から、決まった形の部分だけを取り出すことを、パースと呼ぶ。parsePlan は、計画を1行ずつ見ていって、## 変更するファイル の見出しの下にいる間だけ、- 変更: パス の形の行を拾う。ほかの節に同じ形の行があっても、読まない。Record<string, ...> は「文字列から値を引く表」の型で、変更 を modify に、git の M を同じ modify に、というふうに、計画の言葉と git の文字を、同じ値に揃えている。PlannedFile['kind'] は、PlannedFile の kind に入りうる値、つまり 'modify' | 'add' | 'delete' のことだ。

正規表現の丸括弧で囲んだ部分は、一致したときに取り出せる。1つ目の括弧（変更・新規・削除のどれか）が m[1] に、2つ目の括弧（空白を含まないパス）が m[2] に入る。空白を含むパスは計画の行として読まれないので、そのファイルを触った差分は、計画にない変更として止まる側に倒れる。inSection && ... は、節の外にいる間は false になって、何も拾わない。

// 改行区切りで読む。引用符付きで出る特殊なパスは計画の行と一致せず、止まる側に倒れる
export function parseNameStatus(text: string): FileChange[] {
  return text
    .split('\n')
    .filter((line) => line.trim() !== '')
    .map((line) => {
      const [status, ...rest] = line.split('\t');
      return { status, path: rest.join('\t') };
    });
}

export function buildScopeGate(plan: ApprovedPlan): (change: ChangeSet) => Verdict {
  return (change) => {
    if (!change.testsPassed) return { accepted: false, reason: 'テストが失敗した' };
    const outside = parseNameStatus(change.nameStatus).filter(
      (c) => !plan.entries.some((e) => e.path === c.path && e.kind === STATUS_TO_KIND[c.status]),
    );
    if (outside.length > 0) {
      const list = outside.map((c) => `${c.status} ${c.path}`).join(', ');
      return { accepted: false, reason: `計画にない変更がある: ${list}` };
    }
    return { accepted: true };
  };
}

parseNameStatus の const [status, ...rest] = line.split('\t') は、タブで切った先頭を status に、残りを rest に受け取る書き方だ。残りをタブでつなぎ直しているのは、万一パスの中にタブが入っていても途中で切れないようにするためだ。

buildScopeGate は、承認した計画を受け取って、判定の関数を返す。関数を返す関数なので、buildScopeGate(plan)(change) のように、括弧を二つ続けて呼ぶ。昨日までの acceptChange の形は変えていない。新しく必要になった計画は、buildScopeGate のほうが受け取る。返ってくる関数は acceptChange と同じく ChangeSet を受けて Verdict を返すので、呼ぶ側は acceptChange をこれに差し替えるだけで済む。

判定は、上から順に一段ずつ足していった。足すたびに、槙村さんが、その段は何を止めるのかと聞いてきた。決済の人は、取りこぼしの向きを気にする。

それから、--no-renames のこと。

git は、ファイルの名前が変わったことを見つけると、ふつうは R100 src/util/fmt.ts src/util/format.ts のように、一行に旧い名前と新しい名前を並べて出す。これだと、旧い名前と新しい名前のどちらを計画と比べればいいのか、という分岐が要る。--no-renames を付けると、git は名前の変更を探さなくなる。その結果、名前の変更は「旧い名前の削除」と「新しい名前の追加」の2行で出てくる。

import { spawnSync } from 'node:child_process';
import { readFileSync } from 'node:fs';
import { buildScopeGate, parsePlan } from './after.ts';
import type { ChangeSet, Verdict } from './types.ts';

// check-scope.ts 相当: 判定の中身は変えず、入力（計画ファイルと git の出力）だけ本物にする。
// AI の作業をコミットしたあと、マージの前に走らせる（main...HEAD はコミット同士の比較なので、未コミットの変更は出ない）
export function checkScope(repoDir: string, planFile: string): Verdict {
  // 親の NODE_TEST_CONTEXT が子の出力を潰すので外す
  const { NODE_TEST_CONTEXT: _ctx, ...env } = process.env;
  const tests = spawnSync(process.execPath, ['--test'], { cwd: repoDir, encoding: 'utf8', env });
  // 三点表記: 作業ブランチで起きた変更だけを見る
  const diff = spawnSync('git', ['diff', '--name-status', '--no-renames', 'main...HEAD'], {
    cwd: repoDir,
    encoding: 'utf8',
  });
  if (diff.status !== 0) return { accepted: false, reason: 'git diff に失敗した' };
  const change: ChangeSet = { testsPassed: tests.status === 0, nameStatus: diff.stdout };
  return buildScopeGate(parsePlan(readFileSync(planFile, 'utf8')))(change);
}

spawnSync を使うと、Node の中から別のコマンドを起動して、それが終わるのを待ってから結果を受け取れる。process.execPath は、いま動いている node 本体の場所で、同じ node でテストを走らせるために使っている。

関数の頭で process.env（環境変数の一覧）から NODE_TEST_CONTEXT だけを抜いているのは、この関数をテストの中から呼んだときのためだ。外側で動いている node --test は、自分用の印をこの環境変数に入れる。それがそのまま内側の node --test に渡ると、内側の出力の形が変わってしまう。{ NODE_TEST_CONTEXT: _ctx, ...env } は、その一項目を _ctx という使わない名前で受け取って、残り全部を env に集める書き方だ。テストは node --test に任せて、戻ってきた終了コードを見る。終了コードはコマンドが最後に返す番号で、0 なら何も失敗しなかったという意味になる。差分は git から取る。判定の中身には手を入れていない。入力を、手で書いた文字列から、本物の計画ファイルと本物の git の出力に差し替えただけだ。

main...HEAD と点を三つ書くのには理由がある。点が三つだと、作業ブランチが main から分かれたところから、作業ブランチで起きた変更だけが出る。点が二つの main..HEAD だと、分かれたあとで main のほうに入ったファイルまで、作業ブランチでは「削除された」ように見えてしまう。たとえば俺が作業している間に、main に src/news/banner.ts が足されたとする。点が二つだと、作業ブランチの差分に D src/news/banner.ts が出て、何もしていないのに計画外の削除として止まる。

もう一つ。main...HEAD は、コミットとコミットを比べている。作業ツリーに残っている、まだコミットしていない変更は、新しいファイルも書き換えも削除も、ここには一切出てこない。AI の作業を見逃さないように、これは AI の作業をコミットしたあと、マージの前に走らせる。走らせるのは、今は俺の手だ。毎回自動で走らせる仕組みは、また別の話になる。それに、止めると言っても、マージのボタンが押せなくなるわけじゃない。判定の結果と理由が画面に出るだけで、それを見てマージしないのは、俺たちの判断だ。

ok(...) はテスト通過済みの変更をこしらえるだけの手伝い役。assertRejected は、結論が「止める」で、その理由に狙った文字列が入っているかを見る手伝い役。assert.deepEqual は、二つの値を中身まで比べて、食い違えばその場でテストを赤くする（node:assert の関数）。

一本目は、計画からはみ出さずに AI が仕事を終えた場合。テストは緑で、差分には計画にあるファイルと種類しか出てこない。この入力には、昨日の判断も今日の判断も、同じく「通す」と答える。正しい仕事は止めない。違いが出るのは、計画の外にはみ出したときだけだ。

二本目が、昨日の PR だ。昨日の PR は、この計画の後に出てきたものじゃない。計画なしで書かれたものだから、これは代役になる。承認したあとで AI がまた同じことをしたら、ここで止まるか。それを確かめたかった。昨日までの俺たちは受け入れ、今日の関数は止める。理由に、決済のファイルの名前が入る。

ほかにも、テストが落ちたら両方とも止めること。計画で変更と書いたファイルを消したら止めること。T のような計画に書けない種類の変更は止めること。名前の変更は、計画に削除と新規の両方があれば通り、片方しか無ければ止まること。計画に変更するファイルの節が無ければ、どんな差分も止まること。引用符付きで出る特殊なパスは、止まる側に倒れること。それぞれをテストにした。

それから一本だけ、手で書いた文字列ではなく、本物の git を呼ぶテストを置いた。一時的なフォルダに小さなリポジトリを作って、ファイルの名前を変えてコミットし、--no-renames を付けた git diff が、本当に削除と追加の2行を出すかを確かめる。判定の関数は、この出力の形を前提にしているからだ。

// 本物の git を呼ぶのはこの1本だけ。git version 2.56.0 で確認した事実の固定:
// 名前の変更は --no-renames で D と A の2行になる（diff.renames=true を渡しても --no-renames が勝つ）。
// user.name/user.email は -c で渡し、利用者の git 設定に依存させない
test('本物の git で、名前の変更が --no-renames では D と A の2行になる', () => {
  const dir = mkdtempSync(join(tmpdir(), 'scope-gate-'));
  const git = (...args: string[]) => {
    const r = spawnSync('git', ['-c', 'user.name=t', '-c', 'user.email=t@example.com', '-c', 'diff.renames=true', ...args], {
      cwd: dir,
      encoding: 'utf8',
    });
    assert.equal(r.status, 0, r.stderr);
    return r.stdout;
  };
  git('init', '-q');
  writeFileSync(join(dir, 'fmt.ts'), 'export const fmt = 1;\n'.repeat(5));
  git('add', '.');
  git('commit', '-q', '-m', 'first');
  git('mv', 'fmt.ts', 'format.ts');
  git('commit', '-q', '-m', 'rename');
  const out = git('diff', '--name-status', '--no-renames', 'HEAD~1', 'HEAD');
  assert.deepEqual(parseNameStatus(out), [
    { status: 'D', path: 'fmt.ts' },
    { status: 'A', path: 'format.ts' },
  ]);
});

mkdtempSync(join(tmpdir(), 'scope-gate-')) で、OS の一時置き場に、テストが終われば用のない作業フォルダを作っている。HEAD~1 は、一つ前のコミットのこと。.repeat(5) でファイルに同じ行を5行入れているのは、中身の同じファイルの名前を変えた、と git が見分けられるだけの中身を持たせるためだ。-c diff.renames=true で、わざと名前の変更を探す設定にしておいて、それでも --no-renames が勝つことを確かめている。

それでも安心しきれなくて、判定のほうに一か所ずつ穴を開けてみた。種類を見ずにパスだけを比べるようにすると、計画で変更と書いたファイルを消すテストが落ちる。計画外の検出を常に通すようにすると、昨日の PR のテストが落ちる。一段目を外すと、テストが失敗した変更を止めるはずのテストが赤くなる。穴を開けるたびに、どれかのテストが赤くなった。緑だったのは、中身のないテストだからではなかった。

槙村さんは、計画に載った3ファイルを、ペンを片手に読んでいた。番号を表示するファイルを読み、桁を揃える関数を読み、テストを読む。ときどきペンの先で画面の一行を追って、止まって、また進む。42ファイルのときは、一覧を下へ送るだけで手が止まっていた。今は、読んでいる手が、ちゃんと最後の行まで動いていた。

この関数が見ているのは、ファイルの名前と種類だけだ。中身は見ていない。計画に載ったファイルの中で何が起きても、ファイル単位では計画どおりだから、通る。だから中身は、今日の槙村さんみたいに、人が読むしかない。それでも、読む範囲は42ファイルから3ファイルに縮んだ。

ほかにも、この関数が保証しないものがある。俺は、一つずつ挙げていった。

計画そのものが間違っていたら、止まらない。今日、槙村さんが決済の行に気づかずに承認していたら、決済の変更は計画どおりとして通っていた。計画を読むのは、人の仕事のままだ。

逆向きのはみ出しも見ていない。計画に載せたファイルを AI が触り忘れていても、この関数は止めない。余計な変更を止める門番であって、やり残しを数える仕組みではないからだ。やり残しは、テストと、計画に載った分を読む人の目で見つける。

変更が正しいかどうかも、見ていない。それはテストと、人の目の仕事だ。

plan mode が、計画を書いている間の編集を必ず止めるとも限らない。公式のドキュメントにも、環境によっては、計画だけにして、という指示で動いているだけで、編集そのものはブロックされない場合があると書いてあった。だからこの関数は、途中で何が起きたかではなく、最後に出てきた差分で見る。

それから、このテストが確かめているのは、俺が書いた fixture に対して、判定が正しく動くことまでだ。Claude Code の計画の保存先や、git の出力の形が変われば、配線は黙って効かなくなるかもしれない。そのときテストは緑のままでも、本物の計画は読めていないことがありうる。だからテストには、どのバージョンの git で確かめた形かを書いておいた。特殊な文字のファイル名で間違って止まることがあるのは、さっき書いたとおりだ。

挙げたものを、判定の段の図の上に置き直した。止まる道と通る道、それから止める段のどこにも当たらずに通ってしまう道を、一枚に描いた。

橙の破線の二本は、どちらも止める札を通らずに受け入れへ届く。その二本を受け止めるのは関数ではなく、計画を読む槙村さんと、計画に載った3ファイルを読む人の目だ。

俺はうなずいた。AI が計画の外に出なくなるわけじゃない。出たときに、こっちで気づけるようになった。そこまでだ。

放鷹カード

  • 合図: 探索 → 計画 → 実装。いきなり書かせない。読ませて、変更するファイルの節つきの計画を書かせて、承認してから書かせる
  • 検め方: 最後の差分を git diff --name-status --no-renames main...HEAD で出して、承認した計画と突き合わせる。計画にないファイルと、計画と違う種類の変更は止める
  • 止めないもの: テストが通っていて、差分が承認した計画に載ったファイルと種類だけで出来ている変更
  • 鷹のせいじゃなかった: どこを触るかを、書いている最中の AI に決めさせていた
  • 自分の言葉で: 承認するのは放す前。差分を見るのは放したあと。読むのは、計画に載った分だけでいい
