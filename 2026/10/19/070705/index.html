AIの『完了しました』を信じたら中身は空だった。証拠で検収する【完了の証拠】

AI の「完了しました。テスト12件すべて通過」を信じてマージしたら、送信処理は空のまま本番に出ていた。完了報告に件数を申告させ、人の側で走らせた実測と突き合わせる検収関数（完了の証拠）を TypeScript と node --test で書きます。

第2幕: 再現 ── 報告どおりに、通ってしまう

僕は手すりの陰に座り込んで、メールを送る関数を開いた。sendConfirmationMail という名前で、AI が金曜に書いたものだ。

それなら、テストはどうして通ったんだろう。

「なんで、空なのに通るんだ」

出力をもう一度見る。一行目に、✔ booking.test.ts とある。テストの名前ではなく、ファイルの名前だ。それで分かった。数えられているのは、テストではなくファイルだった。空のファイルを一つ走らせて、何も失敗しなかったから、ファイル一件を一件の合格として数えている。

続けて echo $? と打って、終わったときの終了コードを見た。0だった。終了コードというのは、プログラムが終わるときに返す一つの数で、0なら「失敗は無かった」という合図になる。CI（変更のたびに自動でテストを走らせる仕組み）も、ふつうはこの数を見て、成功か失敗かを決めている。

でも、失敗が無かったことと、何かを確かめたことは、違う。終了コード0は、何件確かめたかまでは教えてくれない。空のファイルでも、ちゃんと0が返る。

ここだけは、自分の手元で確かめたことをはっきり書いておく。

2026年10月、Node v24.21.0 で確かめた挙動。中身が空のテストファイルを node --test で走らせると、tests 1 pass 1 と表示され、終了コードは0になる。テスト関数を一つも書かずに console.log だけを置いたファイルでも、同じだった。公式ドキュメントにこの挙動を説明した文は見つからなかったので、根拠は手元の実機だけだ。Node のバージョンが変われば、表示も変わりうる。

AI は、テスト12件すべて通過、と言った。実際に走ったのは、空のファイルが一つ。数が合っていない。12という数がどこから来たのかは、分からない。分からないということ自体が、僕が言葉だけを受け取っていた証拠だった。

僕は、金曜に自分がしていたことを、関数にしてみることにした。何を見て、何を見ていなかったのかを、はっきりさせたかった。

export type CompletionReport = { summary: string; claimedPass: number };
export type Verdict = { accepted: true } | { accepted: false; reason: string };

型は types.ts に、金曜の僕の判断は before.ts に置いた。CompletionReport は報告で、claimedPass は AI が「何件通った」と申告した数。Verdict は、受け入れるか、理由をつけて止めるかの判定だ。| は「どちらかの形」という意味で、受け入れるときは理由なし、止めるときは必ず理由つき、という2つの形だけを許している。accepted: true のように、値そのものを型として書くと、その値しか入らない。

import type { CompletionReport, Verdict } from './types.ts';

// 金曜の依頼人がしていたこと: 申告が1件以上なら受け入れる
export function acceptReport(report: CompletionReport): Verdict {
  if (report.claimedPass >= 1) return { accepted: true };
  return { accepted: false, reason: '申告が無い' };
}

import type は、型だけを読み込む書き方だ。ファイル名に .ts まで書いているのは、Node でそのまま走らせるため。

中身は、これだけだった。報告に件数が書いてあって、1件以上なら受け入れる。今日の報告を入れると、申告は12だから、受け入れてしまう。止めるべき報告を止められない。

第3幕: 手順を整える ── 申告を、自分の目で数え直す

僕は、手すりにもたれて考えた。

金曜の僕は、報告を読んだ。それで、中身を確かめたことにしていた。でも、報告を読むことと、中身を確かめることは別だった。報告に書いてあるのは、AI がそうだと言っていることで、そうだったという事実ではない。僕が受け取っていたのは、ずっと、言葉だけだった。

同じことを書いている人は、ほかにもいた。調べてみると、Claude Code を作っている Anthropic が、公式のガイドで同じことを書いていた。AI に作業の報告をさせるだけでなく、確かめられる証拠を出させる。そして、その証拠を見て、終わったかどうかを決める。

Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot of the result.

（出典: Anthropic「Best practices for Claude Code」、参照日 2026-10-13）

成功を言い張らせずに、証拠を出させろ。テストの出力、走らせたコマンドとその結果、画面の写真。僕はこれを、完了の証拠を出させる、と覚えることにした。

ここで、さっきの言葉が戻ってきた。戻ってきたのと、仕事をしてきたのは、別。AI の「完了しました」は、鷹が戻ってきたことだ。僕が見るべきだったのは、その足元のほうだった。

言いかけて、自分で止まった。AI の報告に書いてあるコマンドを、そのまま走らせるのは怖い。報告の文字列が、本当にテストのコマンドだとは限らない。間違ってファイルを消すコマンドが書いてあっても、僕はそれを走らせることになる。テストのコマンドは、プロジェクトで最初から決めてある。それを僕の側で走らせればいい。AI から受け取るのは、何件通ったかという申告の数だけにする。

「……いや、コマンドは、こっちで決めたのを走らせます」

女の人は、さっき鷹が降りたアンテナのほうを、顎で一度だけ示した。

僕は、検収の関数を書き始めた。検収というのは、納品されたものを、注文どおりかどうか確かめて受け取ることだ。今日からは、AI の報告を受け取る前に、必ずこの関数を通す。

判定の順番は、一段ずつ、これは何を止めるのか、と確かめながら決めた。

一段目。そもそも申告が無ければ、止める。件数を言わない報告は、突き合わせようがない。

二段目。走らせたテストの終了コードが0でなければ、止める。テストが落ちている。

三段目。何件通ったかの数が取れない、または0件なら、止める。何も確かめていない。

四段目。申告の数と、僕の側で数えた数が違えば、止める。今日の報告は、ここで止まる。

数を取るには、TAP という出力の形式を使うことにした。TAP は、テストの結果を一行ずつ決まった書式で書き出す形式で、node --test に --test-reporter=tap と付けると、この形で出してくれる。最後のほうに、# pass 12 のように、通った件数だけを書いた行が出る。この一行を拾えば、件数が取れる。さっき見た既定の表示にも ℹ pass 1 の行はあったけれど、あれは人が読むための飾りつきの表示だ。それに、既定の出力の形式そのものが、Node のバージョンアップで変わったことがある。機械で拾うなら、書式の決まっている TAP のほうが安定する。

判定の関数は after.ts に置く。その前に、走らせ役の型を types.ts に足した。

import type { CompletionReport, Runner, Verdict } from './types.ts';

// TAP の「# pass N」行から実測件数を取る。取れなければ null
export function readPassCount(tap: string): number | null {
  const m = tap.match(/^# pass (\d+)$/m);
  return m ? Number(m[1]) : null;
}

// 人の側で決めたテストコマンドを Runner で走らせて、申告と照合する
export function buildCompletionCheck(runner: Runner): (report: CompletionReport) => Verdict {
  return (report) => {
    if (!Number.isInteger(report.claimedPass) || report.claimedPass <= 0) {
      return { accepted: false, reason: '申告が無い' };
    }
    const result = runner();
    if (result.exitCode !== 0) {
      return { accepted: false, reason: 'テストが失敗した' };
    }
    const measured = readPassCount(result.stdout);
    if (measured === null || measured === 0) {
      return { accepted: false, reason: '何も確かめていない' };
    }
    if (measured !== report.claimedPass) {
      return { accepted: false, reason: `申告と実測の食い違い（申告${report.claimedPass}・実測${measured}）` };
    }
    return { accepted: true };
  };
}

readPassCount の正規表現は、末尾に m を付けているので、複数行の出力の各行に ^（行の先頭）と $（行の末尾）が効く。(\d+) で囲った数字の部分が m[1] に入る。

buildCompletionCheck は、Runner を受け取って、判定の関数を返す。戻り値の型の (report: CompletionReport) => Verdict は、「報告を受け取って判定を返す関数」の型だ。走らせ役を先に決めておいて、報告はあとから何度でも通せるように、関数を返す形にした。だから呼ぶときは、buildCompletionCheck(走らせ役)(報告) のように括弧が2つ続く。Runner は、テストを走らせて、終了コードと出力を返す役目のことだ。走らせ役を外から渡せるようにしておくと、テストのときは、本物のテストを走らせる代わりに、決まった出力を返す偽物を渡せる。テスト用に固定した入力や出力のことを fixture と呼ぶ。本物の AI を動かさなくても、AI の申告と中身が食い違ったときの出力を、fixture として何度でも同じ形で再現できる。

ちなみに、僕はこれを TypeScript で書いて、Node 24 でそのまま .ts のファイルを走らせている。ただ、Node が .ts を直接走らせるとき、やっているのは型の注釈を取り除くことだけで、型が正しいかどうかは検査しない。型の誤りを見つけたいなら、別に tsc を走らせる必要がある。最初、Node が型も見てくれていると思い込んでいて、少し恥ずかしかった。

関数を書いただけでは、どこからも呼ばれない。僕は、マージする前に手で走らせる小さなスクリプトを用意した。その中で、本物の走らせ役を組み立てて、判定の関数に渡す。

import { buildCompletionCheck } from './after.ts';
import type { CompletionReport, Runner, Verdict } from './types.ts';

// 本物の Runner。コマンドは人の側で決めた固定のもの（AI の報告からは受け取らない）
export function runProjectTests(testFile: string): Runner {
  return () => {
    // テストの中から呼ぶときは親の NODE_TEST_CONTEXT が子の出力を潰すので外す（手で走らせるときは元々無い）
    const { NODE_TEST_CONTEXT: _ctx, ...env } = process.env;
    const r = spawnSync(process.execPath, ['--test', '--test-reporter=tap', testFile], { encoding: 'utf8', env });
    return { exitCode: r.status ?? 1, stdout: r.stdout ?? '' };
  };
}

// check-completion.ts 相当: 判定の中身は変えず、走らせ役だけ本物にする
export function checkCompletion(testFile: string, report: CompletionReport): Verdict {
  return buildCompletionCheck(runProjectTests(testFile))(report);
}

spawnSync は、別のプログラムを子プロセスとして起動して、終わるまで待つ関数だ。process.execPath は、いま動いている node 本体の場所で、同じ node でテストを走らせるために使っている。子プロセスというのは、今動いているプログラムから、もう一つ別に起動したプログラムのこと。ここでは、node --test --test-reporter=tap を子プロセスとして走らせて、その終了コードと出力を受け取っている。走らせるコマンドは、ここに固定で書いてある。AI の報告から受け取るのは、件数の申告だけだ。

r.status ?? 1 の ?? は、左が null や undefined のときだけ右の値を使う書き方だ。プロセスが途中で強制的に止められると終了コードが null になるので、そのときは失敗扱いの 1 にしておく。

途中の NODE_TEST_CONTEXT を外している一行は、この関数をテストの中から呼ぶときのための処理だ。process.env は環境変数（プログラムに外から渡す設定値）の一覧で、{ NODE_TEST_CONTEXT: _ctx, ...env } と書くと、NODE_TEST_CONTEXT だけを取り出して捨て（_ctx は使わないという印）、残りを全部 env に集められる。テストの中からさらに node --test を起動すると、親のテストランナーが持っている印が子に伝わって、子の出力が親に吸い上げられてしまう。手で走らせるときには、この印は元から無いので、何もしないのと同じになる。

コメントの check-completion.ts 相当 というのは、実際にマージ前に走らせるスクリプトのことだ。そのスクリプトの中身は、checkCompletion を一度呼ぶだけ。AI の報告から件数を僕が読み取って、テストファイルと一緒に渡す。止まったら、その理由が表示される。

配線を書いてみて、分かったことがある。判定の中身は、テストのときも本番のときも、一文字も変わらない。変わるのは、走らせ役が偽物か本物かだけだ。

// fixture の TAP は Node v24.21.0 の `node --test --test-reporter=tap` を実機で走らせて取った出力から、
// 件数の行だけを残したもの（空ファイル=pass 1、12件のファイル=pass 12）
const tap = (n: number) =>
  `TAP version 13\n1..${n}\n# tests ${n}\n# suites 0\n# pass ${n}\n# fail 0\n# cancelled 0\n# skipped 0\n# todo 0\n`;
const check = (r: RunResult) => buildCompletionCheck(() => r);

function assertRejected(v: Verdict, reason: RegExp) {
  assert.equal(v.accepted, false);
  if (!v.accepted) assert.match(v.reason, reason);
}

tap(12) は、12件通ったときの TAP の文字列を作る。check は、決まった結果を返す偽物の走らせ役を buildCompletionCheck に渡して、判定の関数を作る。assertRejected は、止まったことと、止めた理由が指定の言葉を含むことを確かめる、小さな補助の関数だ。assert.equal と assert.match は、Node に入っている node:assert の確かめ方で、値が違えばその場でテストを落とす。

それに、数が合っていれば、この関数は通してしまう。試しに、期待する値を確かめる文を一つも書かない、test('x', () => {}) だけのテストを走らせてみた。pass 1 と出た。期待する値を確かめる文のことをアサーションと呼ぶけれど、アサーションが一つも無いテストでも、通ったことになる。AI が空っぽのテストを12件書いて、12件と申告したら、この関数は受け入れる。テストが何を確かめているかまでは、見ていない。

もう一つ。この関数のテストが確かめているのは、僕が作った fixture に対して、判定が正しく動くことまでだ。Node のバージョンが上がって出力の書式が変われば、# pass の行が拾えなくなるかもしれない。そのときは「何も確かめていない」で止まるはずだけれど、止まった理由を調べるのは、また僕だ。だから fixture には、どのバージョンで取った出力かを書いておいた。

放鷹カード

  • 合図: 完了の証拠を出させる。報告には、通った件数を必ず書かせる
  • 検め方: 決めてあるテストを自分の側で走らせて、申告の件数と数え直した件数を突き合わせる
  • 止めないもの: 申告と実測が同じ数で、終了コードが0で、1件以上通っている報告
  • 鷹のせいじゃなかった: 報告を読んで、足元を見ていなかった
  • 自分の言葉で: 「完了しました」は、戻ってきただけ。何件確かめたかは、僕が数える
