テストで組み立てられないクラスへの機能追加は、新しいクラスを別に起こす【Sprout Class】

既存の在庫クラスはコンストラクタで帳簿ファイルを開くため、テストの中で組み立てられない。判定ロジックを芽生やしクラス（Sprout Class）として別に起こし、既存クラスからは委譲するだけにします。

通り庭を抜けて蔵まで来る道は、三十年のあいだに数え切れないほど歩いてきた。荷を担いだ人がすれ違うだけの、あの細い土間の先に、この蔵はある。以前、通り庭の床下でどこまで響くかを見立てたときのことを、ふと思い出した。あのときは荷の流れる経路の話だったが、今日はその先の、荷が最後に落ち着く場所の話だった。

sub new {
    my ($class, %args) = @_;
    my $path = $args{ledger_file};

    open my $fh, '<', $path
        or die "帳簿ファイルを開けません: $path ($!)";

    my %categories;
    while (my $line = <$fh>) {
        chomp $line;
        next unless length $line;
        my ($item, $category) = split /\t/, $line;
        die "帳簿の書式が壊れています: $line"
            unless defined $item && defined $category;
        $categories{$item} = $category;
    }
    close $fh;

    return bless { categories => \%categories }, $class;
}

「今日入れたいのは、混載かどうかの判定です。これは、帳簿ファイルの中身とは別の話です。品目ごとの区分さえ分かれば、判定そのものは成り立ちます」

package Kura::CategoryJudge;

use strict;
use warnings;

sub new {
    my ($class, %args) = @_;
    my $categories = $args{categories} || [];
    return bless { categories => $categories }, $class;
}

sub judge {
    my ($self) = @_;

    my %seen;
    for my $category (@{ $self->{categories} }) {
        next if $category eq '未分類';
        $seen{$category} = 1;
    }

    my @distinct = keys %seen;
    return '未分類'    if @distinct == 0;
    return $distinct[0] if @distinct == 1;
    return '混載';
}

1;

「三つだけで、いいんですか」

私は、少し不安になって訊いた。

「category_forが、それぞれの品目を正しい区分に変えることは、さっきの書き取りで確かめてあります。Kura::CategoryJudgeが、区分の組み合わせから正しく判定を出すことも、単体のテストで確かめてあります。classify_shipmentがしているのは、品目を区分に変えて渡す、という橋渡しだけです。橋渡しがきちんと動いていることと、荷が空だったときに未分類のまま壊れずに済むこと、この二つさえ示せれば、判定のあらゆる組み合わせをここでもう一度確かめ直す必要はありません」

言われてみれば、確かに、それぞれ別のところで確かめたものを、もう一度重ねて確かめる必要はない。橋渡しの部分と、その境目にある空の荷だけを確かめれば足りるということだった。

「保証するのは、ここまでです」

クロベさんが、区切るように言った。

「今のcategory_forの振る舞いは変わっていません。混載かどうかの判定も、確かめてあります。保証しないのは、区分の判定を、もっと細かくするという話です。今日のKura::CategoryJudgeが背負っているのは、区分が一つか、複数かを見るだけの、単純な判定です。もし今後、混載の中でも生鮮の割合によって扱いを変える、という話が来れば、この単純な判定では足りなくなります」

「今日は、Kura::Ledgerの重さそのものには触れていないんですね」

私が言うと、クロベさんは頷いた。

「触れていません。帳簿ファイルを開く、あの重さ自体を軽くする話は、今日の範囲ではありません。今日は、重さに手を付けず、新しい判定だけを外に置く話でした」

クロベさんは、そこで少し声を落として、続けた。

「一つだけ、正直に言っておきます。新しい部材を起こすたび、今まで一つの中にあったはずの仕事が、あちこちに散らばります。それが正しいこともあれば、ただ今はそうするしかない、というだけのこともあります。今日のこれも、そのどちらかは、しばらく経ってみないと分かりません」

技法の効き目だけを語られると思っていたので、その一言は少し意外だった。だが、嘘や誇張のない言い方だとも思えた。

「じゃあ、新しいクラスは、無闇に増やさないほうがいいんですか」

ナギさんが訊いた。

「無闇に、とは言いません。今日みたいに、母屋の中に置き場所が無いと分かったときは、迷わず外に起こせばいい。ただ、それを毎回の癖のようにはしないでください。外に起こした数が増えるほど、どこに何があるかを、誰かが覚えていなければならなくなります」

蔵の前には、いつのまにか日が差し込み始めていた。土壁の匂いも、朝のうちより少し和らいで感じられる。ナギさんは道具箱――今日は画面だけだったが――を片付け、クロベさんは腕を組んで、しばらくKura::Ledgerの画面を見ていた。

私は帳場に戻ると、いつもより急いで野帳を開いた。今日は、答えより先に、自分の問いのほうを書き付けておきたかった。

新しく起こす所は、誰が決めるんですか。

そう書いてから、クロベさんの言葉を思い出した。置き場所そのものは、今日みたいに、外に建てるしかない場合が分かれば、あとは好きに決めていい。

新しく起こすものの置き場所を自分で決めてよい。

そう書いてから、少し手が止まった。今日クロベさんが示してくれた「入るか入らないかの見極め」――コンストラクタが実ファイルに触れるかどうか――は、まだ自分の言葉にしきれていないと感じた。それは、次に自分で見極めるときの課題として、心のどこかに置いておくことにした。

窓の外で、蔵の戸が軋む音がした。誰かが、今日もあの重い戸を開け閉てしているのだろう。

クロベさんは、まだ画面のほうを向いたまま、独り言のように言った。

「今日は、外に一つ起こしただけです。多く起こしすぎれば、それも見通しを悪くします」

それだけだった。褒めるでもなく、念を押すでもない一言だった。私は野帳を閉じ、表紙の上に手を重ねた。中に足すか、外に起こすか――今日初めて自分で分けたその線が、この一冊の中で、確かに一つ増えていた。

普請控

  • 見立て: 店主から、蔵に生鮮と日用品が混ざって届く荷（混載）のための新しい品目区分を設けたいという要望が来た。既存の蔵の帳簿クラス（Kura::Ledger）は実際の帳簿ファイルを開いて書式を検めるコンストラクタを持ち、テストの中で気軽に組み立てられなかった
  • 手を入れた所: 芽生やしクラス（Sprout Class）を使い、新しい区分の判定ロジックを、実ファイルに一切触れない独立したクラスKura::CategoryJudgeとして起こし、単独でテストした。Kura::Ledgerへは、委譲メソッドclassify_shipmentを一つ、useの一行と合わせて足した
  • 触っていない所: Kura::Ledgerのコンストラクタそのもの（帳簿ファイルを開いて書式を検める重さ）。category_forの中身。区分の判定をさらに細かくする（生鮮の割合で扱いを変える等）かどうかの判断
  • 次の工程へ送ること: コンストラクタが実ファイルに触れるかどうかという、今日の見極めそのものを、次はどう自分の言葉にするか
  • 私が引き受けたこと: 新しく起こすものの置き場所（新しい判定を既存クラスの中に置くか、外の新しいクラスに起こすか）を自分で決めてよい
